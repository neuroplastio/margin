# 2026-08-07.2 — ID-01: stamp stable block ids into the source

Kind: mech
Task: ID-01
Commit: (this one)

## What changed

`parse.go` can now give a block an id that survives the block being reworded,
which is the whole point of anchoring and the thing a content hash could never
do.

`stampID(src, block, id)` inserts the id as its own line, `<!--margin:^id-->`,
immediately after the block's source range. `parseDoc` recognises that shape —
an `*ast.HTMLBlock` matching `idMarkerRE` — and, instead of turning it into a
block of its own, attaches the id to the block immediately before it as its
`anchor`, setting `block.stamped = true`. Every other markdown renderer sees an
ordinary HTML comment, which is to say nothing: that is what makes it
"invisible to other renderers" per the task. `anchorFor`'s content hash is now
explicitly the fallback for a block that has never been stamped, not "the
scheme, for now."

`newBlockID` generates the id itself — 4 random bytes from `crypto/rand`, not
derived from content, since a content-derived id is exactly the problem being
solved.

Getting the insertion point right needed two fixes to `extent()`, both flagged
as caveats in the PARSE-01 journal entry and left for this leg on purpose:

- **Fence-exclusive ranges.** A fenced code block's `Lines()` covers only its
  content — the ``` delimiters are syntax, not content, so goldmark excludes
  them. Stamping at the old `b.stop` landed the marker *inside* the fence,
  between the last line of code and the closing ```` ``` ````, which corrupts
  the fence rather than staying invisible. `widenFence` extends the range to
  include both delimiter lines.
- **Inconsistent trailing-newline handling.** Whether `Segment.Stop` includes
  the newline ending a block's last line turns out to differ by node type — a
  fenced code block's does, a paragraph's inside a blockquote often does not.
  `trimTrailingNewline` normalises every block to one convention (`stop` never
  includes it), so `stampID` can insert unconditionally rather than special
  casing each kind.

Both were caught by writing the marker-placement tests against every block
kind in the fixture, not just paragraphs — the code-fence case is the one that
would have silently corrupted a real document.

Nothing wires stamping into the running app yet — there is no code path that
calls `stampID` today. `ensureThread` still hands out content hashes, and that
is deliberate: ID-02 is re-attachment by a stamped id, and the natural point to
start actually stamping is there, once there is a story for what happens to a
block that has never been commented on yet.

## Notes

`block` gained one field, `stamped bool`, distinguishing an id that came from
the source from one derived on the fly. ID-02 will want this to decide whether
a block missing its expected id is "never commented" or "orphaned."

The extent()/stampID split assumes callers stamp one block at a time and
reparse before stamping the next — `stampID` only guarantees bytes *before*
the stamped block are undisturbed, since insertion always happens after
`b.stop`. That is enough for now: nothing calls this in a loop yet.
