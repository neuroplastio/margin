# 2026-08-07.17 — EXPORT-05: resolved threads excluded from the export by default

Kind: mech
Task: EXPORT-05
Commit: (this one)

## What changed

`vault/feedback/` held nothing but its README and `vault/questions/` had no
open question, so the leg fell through to the board. The board's `Awaiting
review:` is still **PARSE-02**, so only `[mech]` work was eligible. M2's
backlog had only EXPORT-05 left as genuinely unblocked `[mech]` work — THREAD-01
and THREAD-03 both landed in prior legs, and EXPORT-04 is `[felt]` — so
EXPORT-05 is this leg.

D11 already settled the shape and the rationale: resolution is a plain
boolean, and excluding resolved threads from the export by default is *safe*
specifically because undoing an over-eager resolution costs one flip, not lost
feedback. This leg is just wiring that decision into `exportReview`.

**`exportReview` (`internal/review/export.go`)** gains a fifth parameter,
`includeResolved bool`. An item is shown when the block is flagged, **or**
when it has comments and either its thread isn't resolved or the caller asked
to include resolved ones anyway:

```go
show := mark == markFlag || (hasComments && (!resolved || includeResolved))
```

The flag check is deliberately independent of resolution: a block can be
flagged *and* have a resolved thread on it (the reviewer flagged something
after the conversation about it was marked done, or an agent resolved too
eagerly while attention was still wanted elsewhere), and "needs attention"
should not silently vanish because the comment thread happens to say
otherwise. Such an item is still shown, with a header carrying both
`— flagged, needs attention` and `— resolved`.

Two more things follow the existing precedent set for drafts, since "nothing
goes silently missing" (goals.md) applies to resolved threads the same way it
already applies to unsubmitted ones:

- A withheld count: `_N resolved thread(s) not included._`, printed right
  after the (pre-existing) draft count.
- The empty-export message now distinguishes two states that used to collapse
  into one string: **"No comments and nothing flagged"** when there was
  genuinely nothing to say, versus **"Nothing outstanding — every commented
  block is resolved"** when there was plenty said and all of it is done. The
  old single message would have contradicted the withheld-count line sitting
  right above it.

A restored item (shown only because `includeResolved` is true) gets
`— resolved` in its header, mirroring how a flagged item already gets
`— flagged, needs attention` — same convention, extended rather than
invented.

**Wiring:** `model` gains `includeResolved bool`, false on every model a test
builds (`seedModel`/`newModel`/`newModelAt` are untouched); only `Run` sets it,
from a new `RunOptions.IncludeResolved`. Both export call sites — `Y`
(`exportToClipboard`) and `--stdout` — read `m.includeResolved`, so the two
paths can never disagree about which threads are in scope, the same guarantee
`--stdout` already had for everything else `Y` produces. `cmd/margin` gets a
new `--include-resolved` flag (default false) that sets
`RunOptions.IncludeResolved`, documented in the command's long help next to
`--stdout`.

## What this deliberately does not do

No new keybinding. `Y` and `--stdout` behave exactly the same whether or not
`--include-resolved` was passed at the command line — there is no interactive
toggle to flip it mid-session. Adding one would be a felt decision (a new key,
competing with the existing single-letter vocabulary in `interaction.md`) and
nothing in EXPORT-05's board wording asked for it; it named "a flag", and a
CLI flag is the least committal reading that satisfies "so an agent can see
what it already addressed" — an agent re-running `--stdout` with the flag set
gets the full history, no session state involved.

I also did not touch `cobra.ExactArgs(1)` in `cmd/margin` — D10 calls for that
to become `MaximumNArgs(1)` as part of the tree-view work, which is unrelated
to this leg.

I checked the felt-half question before closing this out: does something now
render differently? Only in the exported markdown text (`Y`/`--stdout`), which
is plain `fmt`/`strings` output with no screen to look at — the same reasoning
`stdout_test.go` already relies on (`TestExportReviewContainsNoANSI`). The
board classified EXPORT-05 `[mech]` specifically because this is a filtering
decision whose correctness a test settles, not a layout/wording judgment call
— EXPORT-04 remains the separate, `[felt]` task for the export's overall
wording and shape.
