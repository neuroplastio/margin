## What changed

The maintainer's agent loop reported that every event line is metadata only —
id, anchor, author, type, comment index — so a listener has to re-read the
thread file or an export to see the actual words, and the round-trip is the
same shape every time. The fix: comment-level events now carry the body.

- **`text` field on the JSONL line** (`eventLine.Text`, `json:"text,omitempty"`).
  `comment.posted`, `comment.updated`, `comment.deleted` and `comment.restored`
  write the comment's body as it stood in the thread file at emit time —
  **the full body**, not a prefix or a single line, so a listener never has to
  go read the thread for the words. A multi-line comment stays one physical
  line: JSON escapes newlines, tabs and quotes (the same guarantee D14 already
  leans on for the author field).
- **Thread-level events omit the field.** `thread.*` events have no body, so
  their lines are byte-identical to before, and the *absence* of `text` is
  itself the "thread-level event" signal. `omitempty` makes the old shape the
  new shape for them.
- **Tombstoned comments still carry the body**: a `comment.deleted` event
  includes it, because D11 keeps the body in the thread file even when
  deleted — the event reports exactly what the file holds.
- **Backwards-compatible reader.** A line without `text` (any pre-D15 line, or
  a hand-written one) parses with empty text, per the JSON contract that
  absent optional fields fall back to zero values. No migration; the log is a
  notice and the thread file remains the record (D5).
- **Call sites** — the TUI's submit (`dismiss`, review.go), delete/restore
  (`deleteFocused`, review.go) and `margin comment add` (cli.go) — already emit
  right after the thread write, so they now pass the body they were about to
  write. Nothing new emits; every event that means "a comment changed" is a
  comment-level event.

**What I chose and rejected:** full body over the feedback's "at least the new
line" (a truncated quote is still a second read for an agent that needs the
words); `omitempty` over always writing `"text":""` on thread-level events
(the line stays compact and absence becomes meaningful); capturing the body at
emit time over re-deriving it at read time (the thread file is the record, the
log is the notice — a notice should carry the news). Rejected: raising a
question — the feedback's own implementer note says a new field is additive,
the maintainer asked for it, and the log is a notice (D5) so the shape is
rename-cheap, not a migration.

## For the maintainer to look at

This is a shape change to the log a listener parses, and it is the felt part of
a feedback item the maintainer filed: is embedding the **full** body (every
edit of a comment appends another full copy) the right payload versus a digest,
and is the extra log growth acceptable? Nothing waits on it — an agent that
only wants notifications can ignore `text`.
