# 2026-08-07.3 — ID-02: re-attach threads to blocks by id on open

Kind: mech
Task: ID-02
Commit: (this one)

## What changed

Two additions, both in service of the same guarantee: a thread anchored to a
stamped id must survive its block being reworded, and must be told apart from
one whose block is simply gone.

**`stampAll(src, blocks)` in `parse.go`** gives every not-yet-stamped block in
`blocks` a fresh id, in one pass, and returns the rewritten source plus blocks
reparsed from it. It is the batch counterpart to ID-01's `stampID`, which only
promises safety for one block at a time. `stampAll` walks the document
backwards — the only order in which `stampID`'s guarantee (bytes before the
stamped block are untouched) survives being applied repeatedly without a
reparse in between — which is exactly the property
`TestStampEveryBlockSequentially` (added ahead of this leg) exists to pin
down. Nothing in the running app calls `stampAll` yet; it exists tested and
ready for the point where a session needs to turn several in-memory,
content-hash-anchored threads durable in one write, which is a persistence
concern this leg deliberately left alone (see Notes).

**`reattach(doc, threads)` in `document.go`** is the actual "on open" half of
the task. It needs no bespoke matching — threads are already keyed by anchor,
so a plain map lookup finds the same block a stamped id was written against no
matter how the surrounding text changed, which is the whole point of D4. What
was missing was the *other* outcome: a thread whose anchor matches no block at
all was previously just absent from `rebuild()`'s output, indistinguishable
from a thread that was never there. `reattach` now walks every thread, and
sets a new `thread.orphaned` field when its anchor is not live in `doc`.

`reattach` is wired into `newModelAt` — opening a document now always
reattaches whatever `threads` map it was handed before building the entry
list, so an orphaned thread is flagged rather than silently vanishing.
`model.orphanedThreads()` exposes the flagged set. Nothing renders it: what an
orphan should look like on screen is a felt decision nobody has made, so this
leg stops at making the fact queryable.

## Notes

This can only be exercised end-to-end once a `threads` map actually comes from
somewhere across process runs — today `Run()` still always passes `nil`, so
`reattach` is a no-op in the shipped binary. That is expected: STORE-01 (M2)
is what will load a persisted `threads` map on open, and `reattach` is the
piece it will call into. Recording this now so a future leg does not have to
rediscover it.

Also deliberately left alone: actually calling `stampID`/`stampAll` when a
thread is first created (`ensureThread`), which would need a story for a
failed disk write mid-composer-flow and touches the file the reviewer is
actively looking at. That is real scope, not a detail, so it stays a future
leg rather than riding along on this one.
