# 2026-08-12.4 — code block tabs expand to spaces at their 8-column stop

Kind: mech
Task: Feedback `2026-08-12-code-block-tabs-render` — "Formatted code in fenced
blocks (```go) doesn't render tabs / spaces correctly."
Commit: (this one)

## What changed

A fenced code block's tabs reached the terminal as literal `\t` bytes (chroma's
tty formatter passes them through untouched), and the terminal resolved them
against its *absolute* screen tab stops — every 8 columns from the left edge of
the screen, not from the code's own start. So a tab-indented Go block rendered
with an offset that depended on how wide the gutter happened to be, and margin's
width maths (`visualWidth` counts a tab as one rune) under-measured every
tab-heavy line: overflow detection and the horizontal-scroll bound both said a
line fit when it did not.

The fix: expand tabs to spaces before anything measures or emits them.

- **`expandTabsLine(s, tabWidth)`** — replaces each tab with the spaces a
  terminal would move through to the next tab stop, measured from the line's
  own start (a tab at column `c` advances to the next multiple of `tabWidth`),
  resetting the column at a newline. It skips ANSI escapes while counting, so
  it is safe on an already-styled line. `codeTabWidth` is **8** — the terminal
  and vim default, and chroma's own HTML `TabWidth` — so the expanded rendering
  is exactly what the platform would have drawn, made deterministic and
  measurable. A `--tab-width` flag was rejected: the feedback is that tabs are
  *wrong*, not that the width is a preference, and a flag would be a felt
  surface no one has asked for. (Recorded, not settled — see the demo recipe.)
- **`highlightCode`** expands the joined source before chroma tokenises, so the
  styled output is tab-free. This covers the rendered view, raw mode's code
  lines (they borrow `highlightCode`'s output) and `scrollBlock`'s width maths
  in one place. The error/fallback path expands the plain lines too.
- **Mermaid-fallback** plain source lines (`e.b.lines`) expand in both
  `render()` and `scrollBlock()`, so an unparseable mermaid fence reads the
  same as any other code.
- **Raw mode** measures overflow (`hasOverflow`) and the horizontal-scroll bound
  (`scrollRaw`) on tabs-expanded lines, so a long tab-indented source line is
  detected as overflowing and its tail is reachable.

Verified: chroma really does pass the tab through (probed — `quick.Highlight`
on `"\treturn nil"` returns the `\t` inside the styled run), and the expanded
width is what the terminal draws, so the measurement and the screen now agree.

## Demo

```bash
printf '# T\n\n```go\nfunc f() {\n\tx := 1\n\t\treturn x\n}\n```\n' > /tmp/tabs.md
make build && ./bin/margin /tmp/tabs.md
```

1. The ```go block's `\t` and `\t\t` indentations read at 8-column stops from
   the code's own start — not from wherever the gutter pushed them — in both
   the rendered view and `\` raw mode.
2. Widen the indentation (or the line) past the terminal width and `H`/`L` the
   block: the tail is reachable, and clipping matches the line's true
   (expanded) width.

Maintainer to confirm: is expanding tabs at 8 (the terminal default) the wanted
reading of "doesn't render tabs correctly", or would a smaller tab width (4)
read better? The value is one constant, `codeTabWidth`.
