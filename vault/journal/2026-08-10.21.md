## What changed

The vendored `third_party/mermaid-ascii` was its own Go module (upstream
`github.com/AlexanderGrooff/mermaid-ascii` module path preserved), pulled into
the build by a `replace` directive in the root `go.mod`. A module with
`replace` directives cannot be installed via `go install module@version`: the
go command refuses a go.mod that would be interpreted differently than if it
were the main module. That broke the README's install story.

**The vendored copy is now folded into the host module.** Its `go.mod` and
`go.sum` are deleted, so its packages import as
`github.com/neuroplastio/margin/third_party/mermaid-ascii/pkg/...` and the
root `go.mod` has no `replace` at all. All 16 vendored packages' internal
imports and the dispatcher's five imports in `internal/review/mermaid.go` were
rewritten to the host path; `go mod tidy` promoted `orderedmap/v2`,
`go-runewidth` and `logrus` from indirect to direct requires (the vendored
deltas' D1 requirements). The deltas, `CHANGELOG.md`, `LICENSE` and
`README.md` all stay where they were; the README and CHANGELOG got a
packaging note explaining the fold and why (the `go install @version` rule).

**Verified against the real `go install` path**, not just a local build: a
local bare VCS repo behind a git `insteadOf` redirect let me run the actual
`go install github.com/neuroplastio/margin/cmd/margin@v0.0.0-test`. Before the
fold it failed with exactly the reported error ("The go.mod file for the module
providing named packages contains one or more replace directives"); after the
fold the same command builds and installs the binary. (The `replace`-era
snapshot also trips a second, related rule — the go command rejects a module
zip whose tree contains a nested go.mod off the module root — but the VCS path
is the one the README's `@commit`/`@latest` story uses, and it's the one that
reproduces the reported error.)

**What I chose and rejected:** folding the copy into the host module (the
feedback's option 1) over the feedback's other candidates — a fork pushed to a
real module path (option 2) was rejected because it needs a home to publish to
and a version to tag, which a leg cannot decide or create; a Go `vendor/`
directory (option 3) was rejected because it snapshots the whole module graph
for one library (same rejection as D16) and would not fix the install story.
Folding keeps the changelog upstreamable and the deltas re-appliable, exactly
as before; the only cost is that imports carry the host path instead of the
upstream one, which is invisible outside this repo.

## Notes

- The vendored tests now run as part of the host suite (`make check` builds
  `github.com/neuroplastio/margin/third_party/mermaid-ascii/...`), so a
  future delta to the vendored copy is verified by the ordinary gate.
- `go mod tidy` needed no network: every dependency was already in the host
  module graph (the vendored deltas only ever used D1's three requires).
- The `cmd/testdata` golden files inside the vendored copy are still read by
  `pkg/er`'s golden tests via relative paths — unchanged by the fold.

## Verification

`make check` green (build, test, vet) — including the folded vendored

(before → after) is the leg's real proof; a local build alone would not have
shown the failure.

Tests: no new tests — this is a module-structure change. The gate is the
