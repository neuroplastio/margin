# 2026-08-07.10 — CMD-02: palette matching logic

Kind: mech
Task: CMD-02 (from the command-palette feedback's suggested split — see
`vault/journal/2026-08-07.6.md`)
Commit: (this one)

## What changed

CMD-01 gave every verb a stable id and a `Run`. This leg is the next slice
from the feedback's own ordering: given the registry and a query string,
rank and filter commands — no UI, no `:` key, nothing wired into
`handleKey`.

**Matching.** `matchCommands(cmds []command, query string) []command`
(new `internal/review/palette.go`) is the whole surface. An empty query
returns the registry unranked, in its existing order — the feedback's own
"Not settled" section leaves open whether an empty palette shows commands in
stable or recency order, so this leg does not invent an answer for the
no-query case; it only implements requirement 1's actual ask, which is about
what happens once you start typing.

A non-empty query is scored against both a command's `ID` and its
`Description` — requirement 3 says both are searchable, one name for a
command everywhere — and the better of the two scores wins. A command that
matches neither is dropped from the result entirely, not merely sorted last:
requirement 4 says a command that does not apply "should not be listed at
all rather than listed and failing," and the same read applies to a query
that finds nothing.

**Scoring.** `fuzzyScore(target, query string) (score int, ok bool)` is a
subsequence match — every rune of `query` must appear in `target`, in order,
case-insensitively, the same relationship fzf-style finders use. `ok` is
false when it is not a subsequence at all. When it is, the score rewards two
things a bare substring test would not: a match starting right after a word
boundary (`.`, `_`, `-`, space — the separators that actually show up in
this project's ids, e.g. `mark.reviewed`), and a run of consecutive matched
characters. That is what makes `mark.rev` find `mark.reviewed` ahead of
anything that only has those letters scattered somewhere inside a longer
word — requirement 1's own example. Matching is greedy left-to-right, which
is an approximation (a real optimal-alignment matcher would need dynamic
programming) but is enough to satisfy the requirement as stated, and keeps
the function trivial to read and test.

Ties (equal score) keep registry order, via `sort.SliceStable` plus an
explicit index tie-break — results should not jitter for a reason a
reviewer could not see.

## What this deliberately does not do

No `:` key, no palette rendering, no wiring into `handleKey` or the model at
all — `matchCommands` takes a plain `[]command` and a string and returns a
plain `[]command`, callable and testable with zero UI in the loop. Where
results appear, how many rows they get, whether the empty-query state shows
anything — all of that is CMD-03, a felt leg, and still gated behind the
board's `Awaiting review:`.

## Verification

`make check` is green. `make test-race` also green — same reasoning as
CMD-01: this lands in the same package as key dispatch, even though nothing
about dispatch itself changed.

New file `internal/review/palette.go`, tests in
`internal/review/palette_test.go`:
`TestMatchCommandsEmptyQueryReturnsRegistryOrder`,
`TestMatchCommandsFiltersNonMatches`, `TestMatchCommandsMatchesByID`,
`TestMatchCommandsMatchesByDescription`,
`TestMatchCommandsIsCaseInsensitive`,
`TestMatchCommandsRanksPrefixOverScattered`,
`TestMatchCommandsStableOrderOnTie`,
`TestFuzzyScoreRejectsOutOfOrderQueries`,
`TestFuzzyScoreRewardsWordBoundaryAndRun`. The ranking and boundary/run tests
use synthetic commands with no repeated letters across the query, rather
than the real registry, specifically so greedy left-to-right matching has
only one possible alignment — otherwise a passing assertion could be
coincidence rather than proof the bonus is doing anything (an earlier draft
of the word-boundary test used the real `mark.reviewed` and would have
passed for the wrong reason, since greedy matching picks the first `r` in
"ma**r**k" over the one that actually starts the boundary run).

Note on a test bug caught before commit: the first draft of
`TestMatchCommandsEmptyQueryReturnsRegistryOrder` used
`reflect.DeepEqual(got, commands)`. `command` carries `func` fields
(`Applicable`, `Run`), and `reflect.DeepEqual` never considers two non-nil
funcs equal, even the identical value copied into a new slice — so the test
failed even though the code was correct. Fixed by comparing id order instead
of the whole struct.

No question raised. Board's `Awaiting review:` stays on **PARSE-02** — this
leg did not touch it, and picking a `[mech]` cross-cutting task while the
gate holds M1's felt work follows the same precedent as CMD-01 and
STORE-03.
