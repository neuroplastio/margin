## What changed

The feedback: "Vim mode doesn't receive `ctrl+backspace` or other key combos,
dropping into normal mode unexpectedly." Two distinct bugs, both in the last
mile — the host's decode of the terminal was fine (the real reader turns
`CSI 127;5u` into a clean `{Backspace, ctrl}`), and vt.SendKey's fallback was
losing or mangling everything with modifiers it has no explicit case for
(F1's class):

- **Dropped:** ctrl+backspace, shift+enter, ctrl+shift+letter, ctrl+delete,
  modified F-keys — vt's fallback emits nothing, the key never existed.
- **Mangled:** any alt combo carrying a second modifier — vt prefixes ESC for
  alt, strips the bit, and when its remaining lookup fails the output is a
  **bare ESC**. nvim reads that as Escape: insert mode ends mid-typing. That
  is the "dropping into normal mode unexpectedly" half.

`sendKey`'s modifier branch is now `encodeModifiedKey` (`composer.go`), which
encodes every family itself, in forms fed to a real nvim on a pty and
confirmed to decode as the intended key (recorded as F19): xterm
`CSI 1;<mod><final>` for arrows/home/end, tilde forms for
insert/delete/pgup/pgdn/F5–F12, CSI-u for everything else with shift/ctrl
(`CSI 127;5u` → `<C-BS>`, `CSI 97;6u` → `<C-S-a>`), and legacy meta
(ESC + the no-alt encoding) for alt combos. The one family still deferred to
vt is ctrl-only aliases (ctrl+a..z, ctrl+space, ctrl+[) whose legacy control
bytes double as other keys — ctrl+m must stay CR, ctrl+[ must stay ESC.

Two bindings in `composerInit` give the newly-delivered delete-word keys
their expected meaning: `<C-BS>` and `<M-BS>` (the readline/macOS combo)
both map to `<C-W>` in insert mode. The `<M-BS>` mapping does double duty:
nvim resolves meta keys only when a mapping names them, whatever the
encoding — so the mapping is also what stops alt+backspace collapsing into a
lone Escape.

## What I could not fix, and why

An **unbound** alt combo still drops nvim to normal mode — terminal-vim
semantics in every encoding tried (legacy ESC-prefix, ESC+CSI, CSI-u with
alt): nvim waits for the meta key to complete, finds no mapping, and
processes Escape. No byte choice changes that; only binding the key (as done
for `<M-BS>`) or the emulator speaking the kitty keyboard protocol to the
child would, and x/vt implements neither side of that protocol. Recorded in
F19 with the probe methodology. If the maintainer's "unexpected normal mode"
was a specific combo other than alt+backspace, it is now: works if bound,
Escape if not — same as real terminal vim.

## Verification

`make check` green (build, test, vet); `make test-race` green — composer
change, so the race gate applies.

New tests (`composer_keys_test.go`):

- `TestSendKeyEmitsBytes` — 27 cases pinning the exact bytes `sendKey` emits
  per key family, read off the emulator's output pipe (no child needed;
  F20 — the pipe is synchronous, the reader must start first). Covers the
  previously-dropped class, the alt families (none may be a lone ESC), the
  preserved ctrl-only legacy bytes, and the ctrl+enter intercept.
- `TestCtrlBackspaceDeletesWord` / `TestAltBackspaceDeletesWord` — real nvim,
  end to end: "hello world" + the combo submits "hello".
- `TestCtrlBackspaceDecodesThroughRealReader` — the F16-style chain: raw
  `CSI 127;5u` through the actual uv terminal reader, routed by `handleKey`,
  deletes the word in the child.

What I cannot verify: whether `<C-W>` is what your hands expect from
ctrl+backspace and alt+backspace (it is what other editors and readline do),
and whether the combo that originally threw you into normal mode was
alt+backspace — if it was something else, say which, and it gets a binding or
a look of its own.
