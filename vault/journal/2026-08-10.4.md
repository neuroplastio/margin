## What changed

The feedback, verbatim: "The command palette should show the registered key
binding for each command. If a command has multiple bindings, display just the
first one."

The palette was listing `command id — description` with no hint of the key that
runs it. It now right-aligns the command's **first registered binding** on each
row, dimmed like the description it sits beside. A row reads:

```
▌ move.down — Move focus down                                  j
```

Two pieces of machinery:

1. **`keyBindings` is now an ordered slice** (`internal/review/command.go`), the
   single place a raw key binds to a command id; `keymap` (the O(1) lookup
   `handleKey` uses) is derived from it at init. The slice's order *is* the
   display order, and "first" means first-written — so a command's primary key
   is what the palette shows (`j` for move.down, not `down`; `l` for move.dive,
   not `right`/`enter`; `space` for mark.cycle, not the bare ` `). This replaced
   a plain `map` literal, whose iteration order would have made "first" random
   per process. Nothing else changed: the lookup map, the tests that index it,
   and `handleKey` all behave identically.
2. **`firstBinding(id)`** walks `keyBindings` in order and returns the first key
   for a command — what `renderPalette` right-aligns onto the row
   (`internal/review/review.go`). The binding is skipped on a staged command's
   value rows: `reviewed`/`flagged` are values, not commands, and showing `m`
   next to each would be noise.

**What I chose and rejected:** right-aligned and dim, the same treatment the
title already gets, over a leading `[j]` prefix on the row — a prefix would push
the command id off its left-aligned column and fight the cursor bar. The binding
is purely display metadata, so I rejected adding it to the `command` struct:
`keyBindings` is already the registry of bindings, and a second copy in the
command definition would be two sources of truth with nothing to keep them in
step. One-line `bound to j` hints in the id column were also rejected as
redundant with the description beside them.

## Verification

`make check` green (build, test, vet). Composer untouched — no `test-race` run;
the `keyBindings` restructure only changes the shape of data the palette reads
after `renderPalette`, which no goroutine races on (a `-race` spot-check on the
new tests passes).

Tests in `internal/review/palette_test.go`:

- `TestFirstBindingIsThePrimaryKey` — every registered command's `firstBinding`
  is its written-first key; `mark.cycle` → `space`, `move.pageDown` → `ctrl+f`,
  `selection.yankRef` → `yr`, and so on.
- `TestRenderPaletteShowsKeyBindings` — the rendered `move.down` and `app.quit`
  rows end in their binding (`j`, `q`), ANSI stripped, right-aligned on the row.
- `TestRenderPaletteValueRowsCarryNoBinding` — staged `mark ` value rows
  (`reviewed`/`flagged`) end in the value, not a binding.

Existing tests pass unchanged, including `TestKeymapResolvesToRegisteredCommands`
and `TestEveryCommandIsReachableByAKey`, which both range over the derived map.

No question raised.

## Demo

```bash
make build && ./bin/margin testdata/sample.md
```

1. Press `:` — the palette opens over the document. Each row now ends with the
   key that runs that command: `j` beside "Move focus down", `c` beside "New
   comment", `r` beside "Mark reviewed", `space` beside "Cycle the review
   mark". Judge: is the right-aligned, dim key readable at a glance without
   fighting the description for attention?
2. Type `mark` — the two value rows (`reviewed`, `flagged`) carry no binding,
   because they are values, not commands. Judge: does that read right, or
   should a value row show the key that opened the stage (`m`)?
3. Press `m` directly, and `s` — the staged views look the same as step 2.
   Then backspace out to the bare command list and look at `move.down` vs its
   long-form arrows: the palette shows `j`, the first-registered binding, not
   `down`/`up`. Judge: is "first registered" the binding you want advertised,
   or should some commands prefer a named key?

Questions for the maintainer: is the right-aligned dim binding the right
placement, and is "first registered" (i.e. primary) the right binding to show
when a command has several?
