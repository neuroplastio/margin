## What changed

The maintainer's test run of the event log (2026-08-10.7, D13) asked for three
corrections to the on-disk shape, all made this leg and pinned in **D14**
(which supersedes D13's line shape and nothing else):

1. **JSONL.** Each line is now one JSON object —
   `{"id":"1N7KB52S0NPCH","at":1786363200,"type":"comment.posted","doc":"docs/spec.md","anchor":"^a1b2c3","author":"agent","comment":2}` —
   instead of seven tab-separated fields. The fields are self-describing, and
   `sanitizeLogField` is gone: encoding/json escapes tabs, quotes and newlines
   in free-form fields, so a line stays one physical line whatever an author
   is called.
2. **Compact ids.** 26-char ULID → **13-char Crockford base32**: seven
   characters of unix seconds (35 bits, fixed width) + six characters of
   randomness (30 bits). Fixed width is what keeps the id time-ordered — a
   1-second count encodes as `0000001`, not `1`, so every id of a later second
   sorts after every id of an earlier one. The alphabet is the same one D13
   used, decoder and known-value tests included, minus the 16 chars the ULID's
   80-bit entropy cost.
3. **Unix timestamp at second precision.** `at` is an integer unix seconds,
   not RFC3339Nano.

The wait command's surface is untouched: same exit codes, same raw-log-line
output, same `--since` cursor. `readEventsAfter` still matches the id and takes
everything after its line, so the D13 tie rule generalises unchanged — events
sharing a *second* resolve by file position exactly as shared milliseconds
did, and the tie test (a `ZZZZ…` line before a `0000…` line) survives verbatim
with the new id shape. Torn-tail handling is unchanged: a final unterminated
line is skipped.

**The granularity question, answered:** the compact id's time prefix is at the
*same* granularity as the timestamp (both seconds), and even if it were coarser
the tie rule would not care — the cursor is a position in the file, not a
comparison, so `readEventsAfter` matches the id string and returns everything
after its line whatever the id carries. Id and `at` both come from the same
`time.Now()` in `appendEvent`, so they never disagree.

**What I chose and rejected:** 13 chars (7s + 6r of base32) over keeping the
ULID at a smaller alphabet and over a hex timestamp; unix seconds as a JSON
number over a string, so `jq` reads `at` arithmetically; `"comment": -1` kept
for thread-level events over omitting the field (one shape, as D13's `-`); a
new D14 that explicitly supersedes D13's line shape over editing D13 in place
(the decisions log is append-only). Rejected: keeping TSV with smaller ids
(the feedback names JSONL), any migration of an old log (the feedback says
there is no history), and strict JSON validation beyond id shape + comment
index — absent optional fields fall back to zero values, which is the JSON
contract.

## Verification

`make check` green (build, test, vet). Composer and emulator untouched — no
`test-race` run.

Tests in `internal/review/events_test.go`, updated for the new shape:

- `TestEncodeTimePrefixKnownValues` — the 7-char prefix pinned against
  hand-derived values (0 → `0000000`; 1 → `0000001`; all-ones → `ZZZZZZZ`),
  with a decode helper.
- `TestNewEventIDIsTimeOrdered` — 13 chars, valid alphabet, embeds a current
  second, unique, and 200 ids sort lexicographically in non-decreasing time.
- `TestEventLineShape` / `TestEventLineThreadLevel` — exact JSONL lines
  round-trip; thread-level events carry `"comment": -1`.
- `TestMarshalEventEscapesFreeFormFields` — an author with a tab, newline and
  quote comes back whole, one physical line.
- `TestAppendEventAndReadEventsRoundTrip`, `TestReadEventsSkipsTornTail`
  (torn tail is now a JSON fragment), `TestReadEventsMissingLogIsEmpty`,
  `TestParseEventMalformed` (JSONL malformed cases: bad JSON, short id, an `I`
  in the id, a comment index below -1).
- The readEventsAfter / WaitEvents suite — empty/known/last/unknown cursors,
  the file-position tie, the malformed-line surface, blocking and timeout —
  unchanged in behaviour, ids updated to the 13-char shape.

Smoke-tested by hand against a scratch review root: two `comment add`s produced

```
{"id":"1N7KB52S0NPCH","at":1786358946,"type":"comment.posted","doc":"doc.md","anchor":"^b36ebc","author":"agent","comment":0}
{"id":"1N7KB52Y6GVEV","at":1786358946,"type":"comment.posted","doc":"doc.md","anchor":"^b36ebc","author":"agent","comment":1}
```

— same second, matching 7-char time prefix, distinct random suffixes — and
`comments wait` from the first id returned the second line (exit 0), from the
last id timed out quiet (exit 1).

## For the maintainer to look at

The new line shape, byte-for-byte. Judging it is: does a JSONL line read
better than the TSV it replaced, is 13 chars the right id length, and is
`"comment": -1` the right spelling of a thread-level event? Nothing waits on
it.

## Demo

```bash
make build
./bin/margin testdata/sample.md     # c on a block, comment, ctrl+enter, R resolve, q
cat .margin/events.log              # one JSON object per line, oldest first
./bin/margin comment add testdata/sample.md --anchor <id> --text "reply" --author agent
tail -1 .margin/events.log          # the reply's JSONL line; its id is the next cursor
./bin/margin comments wait --since "$(tail -1 .margin/events.log | jq -r .id)" --timeout 5s
```

1. Does the JSONL line read at a glance — are the field names right, is `at`
   as a bare unix integer the shape you want, and is a 13-char id short enough
   to copy and compare?
2. `jq -r .id` as the next `--since` — does that match how you'd parse the log?

Note: the repo's own `.margin/events.log` (your 10:39 test run, gitignored) is
old-format TSV. The new reader surfaces it as `event log: malformed line` by
design — delete that scratch log before re-testing from the repo.

(What I chose: JSONL with `id/at/type/doc/anchor/author/comment` field names,
a 13-char base32 id (7s time + 6r random), unix seconds as an integer, D14
superseding D13's line shape. What I rejected: a shorter ULID alphabet, a hex
id, keeping TSV, omitting the comment field on thread-level events.)
