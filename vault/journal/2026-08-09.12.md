# 2026-08-09.12 — adding a comment to a thread shows the thread

Kind: felt
Task: (feedback, `vault/feedback/2026-08-09-todo-review-feedback.md`, §1
first bullet — "Show existing comments when adding a comment to a thread

Commit: (this one)

## What changed

Until now `c` on a block that already had a thread swapped the whole thread
for the composer: the box held only the nvim emulator, so the reply was
written blind — against a conversation you could no longer see. The
maintainer's words: it feels like writing a parallel thread.

Now the composer box of a **new** comment renders the thread's visible
comments (and the `✓ resolved` badge, when the thread is resolved) above the
emulator, with a dim full-width `─` rule marking where reading stops and
writing starts. The mechanics:

- The comment-rendering loop of `threadLines` is extracted into
  `appendComments` (`review.go`), shared verbatim between the expanded view
  and the composer box — one renderer, so a comment reads, wraps and
  hit-tests identically whether you are reading the thread or writing into
  it. Tombstones stay hidden unless `V` is on, through the same
  `visibleComments` filter both views already used.
- A new render-pass side channel, `m.paneLead`, records how many box content
  lines sit ahead of the emulator; `View` folds it into `paneTop`, so mouse
  routing, wheel routing and the hardware cursor keep pointing at the
  editor's real first row. It is reset in `render()` and set in
  `threadLines`, the same pattern `spans`/`subspans` already use.
- Comments rendered above the editor keep their subspans, so clicking one
  while composing blurs the editor and lands focus on that comment — the
  same "click's landing spot becomes the focus" rule clicking away already
  followed.

Deliberately unchanged: **editing** (`e`) keeps the composer-only box — the
text being edited is already live in the emulator, and the want the feedback
names (seeing what you are replying to) does not apply. A fresh thread and a
draft-only thread are pixel-identical to before: no conversation exists, so
none is drawn.

Chose the dim rule as the separator over no separator (the last comment line
and the editor's first row are adjacent text; the boundary is invisible) and
over a labelled marker like `── reply ──` (adds words to chrome; the footer
already says "new comment"). Chose showing the resolved badge while composing
(replying to a resolved thread is context worth having) over hiding it.

## Verification

`make check` green; `make test-race` green (the change renders the emulator
from the render goroutine, so the race gate applies).

New tests (`review_test.go`): the conversation renders above the emulator
with both seeded comment bodies present; the rule sits on the line directly
above the emulator's first row; `paneTop` still lands on that row (mouse
routing would otherwise click off the text); both comments keep subspans that
start on their author lines and never reach into the editor. Edit mode keeps
the solo box (`paneLead == 0`, span is `paneRows+3`), and so does a fresh
thread. The pre-existing `TestComposerBoxDoesNotRewrap` passes unmodified,
pinning the no-conversation case.

I cannot see the screen, so I cannot confirm the rule reads as a separator,
that the taller box feels right on a long thread, or that the comments above
the editor are legible in context — that is the demo below.

## Demo

```
make build && ./bin/margin README.md
```

1. `j` onto any paragraph, press `c`, type a line, `ctrl+s` to post. Press
   `c` again on the same block.
2. The box should now show your posted comment (author · age · body) above a
   dim horizontal rule, with the editor below it — you are reading the thread
   you are replying to.
3. Click a comment above the rule: the editor blurs (draft kept) and focus
   lands on that comment. `c` again, then click *inside* the editor: the
   cursor should position there, not blur.
4. Wheel over the comments scrolls the document; wheel over the editor
   scrolls the editor.
5. `e` on a posted comment: the box should be the editor alone, as before.

Questions: does the dim rule read as "reading stops, writing starts", or does
the boundary want words? With a long thread the box grows past its ten editor
rows — does that crowd the document more than it helps, or is it fine because
you asked to write? Should `e` show the rest of the thread too (skipped
comment being edited), or is the solo box right there?
