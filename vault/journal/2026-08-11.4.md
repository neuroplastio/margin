# 2026-08-11.4 — review progress across the whole tree

Kind: felt
Task: M3 tree-view item "Review progress across the whole tree" — the last
unblocked M3 tree item. Directory reviews get a tree-wide progress readout:
each file's `reviewed/total` beside it in the pane, and a whole-tree roll-up in
the footer.
Commit: (this one)

## What changed

A tree review is a sequence of switches between fresh reviews of fresh
documents, and until now every switch threw the previous document's marks away
(`openTreeFile` reset `m.marks`). Progress across a tree was therefore
unanswerable: the only numbers were the open document's, and they reset every
time you moved. This leg makes marks per-document session state and shows the
roll-up.

- **Marks are carried per-document across switches.** `markCache` (keyed by
  rel path, the D9 docPath) holds each document's marks for the session;
  `openTreeFile` saves the outgoing document's map into it and restores the
  incoming document's, so switching away and back keeps your review. The
  current document's marks live in `m.marks` as before and all existing code
  paths are untouched — the cache is only crossed at a switch boundary. Marks
  are still session-local: nothing persists marks on disk (threads are the only
  on-disk review state, D5), so a reopened tree starts clean. Per-document
  *scroll* is deliberately not part of this leg — see Notes.
- **The denominator is the whole tree, opened or not.** `markTotals` holds
  every file's markable block count (`markableTotal`, the same accounting
  `reviewProgress` uses), computed for all files at tree open — the open
  document's from the already-loaded blocks, the rest by a one-time parse —
  and refreshed on `ctrl+r` reload so an agent-rewritten document re-counts.
  A file that will not parse contributes nothing rather than a bogus number.
- **The pane shows each file's progress.** Every pane row gains a fixed
  right-aligned progress slot (`progW = 7`): a file with any marks this
  session reads `n/m` — dim when partially reviewed, green when the whole file
  is reviewed, orange with a trailing `!` when any block is flagged; a file
  nobody has touched (and directory headers) show a blank slot, and the fixed
  slot keeps the document column aligned whatever a row has to show. The pane
  width grows by the slot and the total is still clamped at 36.
- **The footer rolls the whole tree up.** In a directory review the footer's
  progress readout becomes `tree N/M reviewed · F flagged` across every file's
  blocks — untouched files still count against `M`, which is what makes the
  number "progress across the tree" rather than "progress across what I
  happened to open". A single-document review's footer is unchanged.

**What I chose and rejected:** blank slot for untouched files over `0/n` (a
freshly opened tree would be wall-to-wall zeros, which reads as noise; the
footer roll-up already carries the untouched denominator, and the pane row
lights up the moment a file is marked); per-document marks as a session cache
over persisting marks to disk (persistence is a format decision and nothing in
M3 requires marks to survive a restart — threads, the settled on-disk review
state, already do); `n/m` plus a trailing `!` for flagged over separate
reviewed/flagged columns (one compact token per row); the footer showing the
tree roll-up over both it *and* the open document's numbers (the open
document's own count sits on its pane row, right where the eye is looking).

## Notes

- Per-document *scroll* is the other half the 2026-08-11.1 journal named as
  the tree-progress item's shape ("whether switching should carry marks and
  scroll per-document"). This leg carries marks; carrying scroll per document
  (and per-document raw/search/selection state) is a natural next slice and
  was left out to keep the leg small — a document still opens at its top.
- No on-disk format, anchor or thread change. Marks remain in-memory, exactly
  as a single-document review keeps them today; a tree review is now just a
  session with several documents' worth.
- The export (`Y` / `--stdout`) still covers one document, untouched by this
  leg; the tree-wide coverage question stays open.
- The README's "marks and comments all switch to the new document" was now
  wrong (marks carry, comments switch) and is corrected, with a line on the
  per-file progress and the tree footer.

## For the maintainer to look at

Whether a per-file `n/m` in the pane is the right progress surface (vs a
pane-wide summary line, or `0/n` on untouched files); whether the colour rules
— green when complete, orange `!` when flagged, dim partial, blank untouched —
read at a glance; whether the footer replacing the open document's numbers with
the tree roll-up is right (the open doc's count lives on its pane row); and
whether marks surviving across switches is the expected behaviour (it is a
change from the reset-on-switch of 2026-08-11.1, and it is the prerequisite
that makes tree progress meaningful at all).

## Demo

```bash
make build
mkdir -p /tmp/progress/docs
printf '# README\n\nRoot prose one.\n\nRoot prose two.\n' > /tmp/progress/README.md
printf '# Spec\n\nNested prose.\n' > /tmp/progress/docs/spec.md
./bin/margin /tmp/progress
```

1. **The pane starts quiet.** On open the pane lists `README.md` and `spec.md`
   with nothing in their progress slots — every file untouched. The footer
   reads `tree 0/3 reviewed` (the two README paragraphs plus the spec's one,
   the spec counted even though it has never been opened). I chose blank slots
   over `0/n` on untouched files. Does the footer's whole-tree denominator
   read as "everything in this tree", or should it only count what you have
   opened?
2. **Mark a file.** `space` (or `r`) on "Root prose one.", then `j`, `space`
   on "Root prose two." — the README's row now reads `2/2` in green and the
   footer `tree 2/3 reviewed`. Does the per-file `n/m` in the pane read at a
   glance, and is green-for-complete the signal you expect?
3. **Switch and keep your review.** `tab`, `enter` to open `spec.md`, mark its
   paragraph `f` (flag it) — the footer now reads `tree 2/3 reviewed · 1
   flagged` and the spec's row `1/1!` in orange. `tab`, `k`, `enter` back to
   the README: its `2/2` and your marks are still there. This is the
   behavioural change — marks used to reset on every switch. Is carrying them
   per-document what you want, or was the reset a feature?
4. **A flagged file.** Note the spec's row `1/1!` — the `!` marks "attention
   remains". Should a flagged file read differently, or is the `!` enough?
