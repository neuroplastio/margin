# 2026-08-09.8 — fix: composer pane re-wraps the emulator's lines

Kind: mechanical
Task: (from feedback, `vault/feedback/composer-wrapping-misalignment.md`)
Commit: (this one)

## What changed

`vault/feedback/` held two items beyond its README; the oldest was
`composer-wrapping-misalignment.md`, a screenshot-backed report that long
comments typed in the composer wrapped oddly — single short words orphaned
onto their own line despite space to spare — and the cursor ended up
positioned wrong relative to the text. Feedback preempts the board, so this
is the leg.

The root cause was a width mismatch, not nvim's wrapping:

- The composer emulator is created at `m.contentWidth()-2*borderW` columns
  (`newComposer`, `review.go:601`).
- `threadLines` renders that emulator through a lipgloss box built with
  `Width(w - 2*borderW)` (`review.go:1174`).

But lipgloss's `Width` includes the border. So a box declared 74 wide has a
**72-column content area**, two columns narrower than the emulator that feeds
it. The emulator's already-wrapped 74-wide rows were re-wrapped by the box at
72, which is exactly the reported symptom: a word parked in the last two
columns got pushed onto its own line, and the box's rows no longer aligned
one-for-one with the emulator's rows, so the cursor (computed from the
emulator's row/column) sat on the wrong text.

The fix is to size the box at the content width `w`, not `w-2*borderW`, so
its content area is exactly the emulator's width and every emulator row lands
in the box verbatim. One-line change to `threadLines`.

## Verification

`make check` (build, `go test ./...`, `go vet ./...`) green, plus
`make test-race` since this touches the composer path.

New `TestComposerBoxDoesNotRewrap` guards the regression at three levels:
the composer thread's rendered span must stay `paneRows+3` rows (border, rows,
trailing blank — any re-wrap adds rows), the box's top-border dash count must
equal the emulator's width, and each rendered row must equal its emulator row
verbatim. Reverted the one-line fix to confirm the test fails (it does, on
the dash-count check: 72 vs 74), then restored it.

I cannot see the screen, so I cannot confirm the wrapped text now *reads*
right in a real terminal — only that the box no longer re-wraps and the
cursor coordinates align with the emulator rows, which is the mechanism the
screenshot showed failing. The fix is direct and mechanical; the maintainer's
screenshot already told us what was wrong, so no new demo recipe. If a second
look is wanted, type a long comment and confirm words wrap at the box's right
edge and the cursor follows the text.
