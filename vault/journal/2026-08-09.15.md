## What changed

The maintainer marked one header section (their "CMD-05", anchor `^ccd3fc`)
and every sibling header lit up as reviewed. The mechanism was anchor
collision: `anchorFor` derives a content anchor from `sha256(kind\x00text)`
only, so two byte-identical blocks — and a TODO/board document is full of
them, every `*(none)*` placeholder is the same block to the hasher — share
one anchor. `toggleMark` on a heading writes `m.marks[anchor]` for each
anchor in its section; with siblings sharing that anchor, the one write was
read back by every twin's roll-up (`render`'s heading branch) and counted
twice by `reviewProgress`. One mark, every sibling section "reviewed".

The fix is a disambiguation pass at the end of `parseDoc`
(`disambiguateAnchors`, `internal/review/parse.go`): the first occurrence of
a content-derived anchor keeps it bare; repeats gain ordinal suffixes
(`^abc123#2`, `#3`, …). Properties that made this the right shape:

- **An anchor names exactly one block again** — the invariant D4 and every
  consumer (marks, threads, focus lookups, export locators) already assumed.
- **The bare anchor is untouched**, so a thread file written against `^abc123`
  before this pass still finds the first twin. Suffixes cannot collide with a
  real derived anchor, which is always `^` plus hex.
- **Deterministic across parses of the same source**, so anchors are as stable
  as content-derived ids ever were: unchanged while the text *and its position
  among identical twins* is. Stamped ids (the durable kind, ID-01) are not
  touched by the pass at all.

Nothing on disk changes: the thread-file format, the id-marker syntax, and
`stampID`/`stampAll` are all as they were — the pass only rewrites
session-local, never-stamped, content-derived anchors, and only the colliding
ones. Not a decision-log entry: it restores what D4 already says rather than
deciding anything new.

## Verification

`make check` green (build, test, vet). No composer or emulator change —
`parseDoc` runs long before either goroutine pair exists — so `make
test-race` is not required by the gate.

Reproduced first, then fixed: `TestIdenticalSiblingSectionsMarkIndependently`
(`marks_test.go`) parses `## One\n\n*(none)*\n\n## Two\n\n*(none)*\n`, marks
section One, and asserts section Two's roll-up stays unmarked and
`reviewProgress` counts one reviewed block, not both twins — both assertions
failed before the fix (roll-up `markOK`, count 2) and pass after.
`TestIdenticalBlocksGetDistinctAnchors` (`parse_test.go`) pins the pass
itself: first occurrence keeps the bare `anchorFor` output, repeats get `#2`
/`#3`, a distinct block is untouched.

What I cannot verify: the maintainer's original document is not in the repo,
so the reproduction is the mechanism, not their exact file — but the
mechanism reproduces the reported symptom precisely (one section's mark, all
sibling headers lit).

on twin #2 now records `#2` and reattaches to twin #2, where it previously
reattached to twin #1), but a comment still stamps its block on first posting
(ID-01), so that path barely matters. The remaining bullets of the todo-review
