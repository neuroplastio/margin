## What changed

The maintainer's report: "Vim mode displays a strange black background
beneath typed text; erasing text leaves behind persistent black background
artifacts on deleted character cells."

The emulator's own render output was the evidence:
`m.comp.em.Render()` decorated *every* cell — typed text, the empty rows under
it, and the cells a backspace had emptied — with a `48;2;20;22;27` background
SGR. That is `NvimDarkGrey2`, the default colorscheme's `Normal` background:
nvim paints the whole pane with it even when stripped to a textarea, and
`fillchars.eob` only swaps the filler *glyph*, never the background under it.

The fix is nvim-side, not host-side: `composerInit` now forces the
background-bearing groups transparent —

```lua
vim.api.nvim_set_hl(0, 'Normal',       { bg = 'NONE', ctermbg = 'NONE' })
vim.api.nvim_set_hl(0, 'NormalFloat',  { bg = 'NONE', ctermbg = 'NONE' })
vim.api.nvim_set_hl(0, 'EndOfBuffer',  { bg = 'NONE', ctermbg = 'NONE' })
```

`EndOfBuffer` matters because the filler past the last line is where the slab
was most visible; `NormalFloat` for the same reason on any popup. The pane now
renders as plain styled text on the terminal's own background, matching the
document it floats over.

**What was rejected:** stripping `48;` out of `em.Render()` on the host side.
That would be patching a symptom and would break a legitimate background the
moment a real colorscheme or a visual selection wanted one — the emulator
should faithfully report what the child painted, and the child should simply
not paint this. See F21 for the reasoning and the `nvim_set_hl` key gotcha
(`bg`, not `guibg`).

## Verification

`make check` green (build, test, vet); `make test-race` green (composer).

`TestComposerPaintsNoBackground` (composer_keys_test.go) spawns a real nvim,
types "hello world", backspaces five times, and asserts the emulator render
carries no `\x1b[48` background SGR anywhere. It is a felt-adjacent check: the
test proves the SGR is gone, but whether the pane reads as belonging to the
document is a human question.

No open questions raised.

## Demo

```bash
make build && ./bin/margin testdata/sample.md
```

1. Press `j` to a paragraph, `c` to open the composer. The pane should show
   the comment text on your terminal's own background — no dark slab, no
   visible rectangle different from the document around it.
2. Type a line, then backspace over it. The cleared cells should match the
   surrounding pane exactly; no dark marks where text used to be.
3. Type a misspelled word and watch the spell underline still work (the
   underline must survive the transparency).
4. Submit with `ctrl+s` and confirm the pane closes cleanly.

Questions for maintainer: does the transparent pane read as part of the
document (my pick — nvim is a window on the host's page, so it should show
the page's background), or does the editor want a *subtle* tint to separate
it from the prose? The old behaviour — nvim's own dark grey slab — was the
bug; the only real choice is between fully transparent and a deliberate
margin-owned tint.
