# 2026-08-13.1 — import comments from the current GitHub PR

Kind: felt
Task: Feedback `2026-08-13-import-comments-from-gh-pr` — "When opening a margin
doc, the user can use an import action to load comments from the current PR.
Integration via the gh CLI for now."
Commit: (this one)

## What changed

New `margin import-pr FILE.md`: it shells out to the gh CLI — `gh pr view
--json number,url` to detect the PR the current branch is on, then `gh api
--paginate repos/<owner>/<repo>/pulls/<n>/comments` to fetch its review
comments — and writes them as ordinary margin thread files. Each comment that
names this document is attached to the block whose source-line range contains
its line (`line`, falling back to `original_line` for a comment on the old
side of the diff), using the block's own content-derived anchor and a quote of
its text — the exact thread file a reviewer typing `c` would produce. Running
it again is safe: a comment already present in a thread (same author, same
body) is skipped. Comments on other files, and comments whose line maps to no
block, are counted and listed, never dropped. Each imported comment also
appends a best-effort `comment.posted` event (D13/D14), the same notice
`margin comment add` emits, so an agent tailing the log sees the imported
conversation arrive.

Deliberately bounded:

- **Review comments only.** The PR's general conversation comments have no line
  and therefore nothing to attach to; they are left to gh.
- **CLI only.** "An import action" is served by the command; a TUI action (a
  palette command that runs the import from inside an open review) is a later,
  felt leg that calls the same `ImportPR`.
- **No GitHub-shaped format.** This respects goals.md's "not a GitHub client,
  and platform sync must not shape the local design": the import writes the
  local thread format unchanged, so a PR comment becomes an ordinary local
  thread from the moment it lands. No id field, no migration, no new schema.
- **Line-mapped, not id-mapped.** A comment attaches to whatever block now
  sits at the line the comment was made on, best-effort; if the document has
  drifted from the PR head, the landing may be wrong, and the reviewer moves
  or deletes it. Id-anchored PR sync stays in "later, explicitly not now".

## Notes

The command runs gh in the document's directory, not the process cwd, so gh
detects the PR from the checkout the document belongs to even when margin is
invoked from elsewhere. gh's own stderr — `no pull requests found for branch
"main"`, `no git remotes found` — is passed through as the error, because it
is the useful message. See F28.

## Verification

New tests:

- `internal/review/import_pr_test.go`:
  - `TestImportPRWritesThreads` — two comments land on their blocks' threads
    with author, body and gh's timestamp preserved; one on another file and
    one on a no-block line are reported; nothing else is written.
  - `TestImportPRGroupsCommentsOnTheSameBlock` — two comments on one line
    become one thread of two.
  - `TestImportPRIsIdempotent` — a second import skips, never duplicates.
  - `TestImportPRFallsBackToOriginalLine` — a base-side comment lands via
    `original_line`.
  - `TestImportPRPreservesResolvedFlag` — an existing resolved thread keeps
    its flag; the import only appends.
  - `TestImportPRNoPRForTheBranch` / `TestImportPRRejectsMalformedGHOutput` /
    `TestImportPRRejectsMalformedCommentTimestamp` / `TestImportPRNoComments` /
    `TestImportPRFailsBeforeCallingGH` — every failure surfaces, and gh is
    never called for a document that does not parse.

request: gh: exit status 1: no git remotes found`.

## Demo

```bash
cd /path/to/a/repo/with/an/open/PR/that/comments/on/your.md
gh pr view            # confirm gh sees the PR from this branch
make build
./bin/margin import-pr your.md
# then open the review:
./bin/margin your.md
```

1. Run `import-pr` on a document a PR has commented on — do the imported
   threads land on the blocks the comments were about? The mapping is
   line-based against the current document, so a block that has moved since
   the comment was made will get a comment that does not belong to it. I chose
   line-mapping (best-effort, reported when it fails) over a GitHub id-anchor
   scheme, which would change the thread format — exactly the "must not shape
   the local design" thing goals.md forbids. If line-mapping is too loose, the
   lever is importing against `original_line` too, or refusing when the
   document differs from the PR head.
2. Is the report line enough — `imported N comments from PR #42 (owner/repo);
   M already imported; K on other files left alone; J on no matching line` —
   and are the unmapped ones worth listing with their line and first words?
3. Re-run the same command — does skipping already-imported comments (dedupe
   on author + exact body) match your expectation of idempotency?
4. This is the CLI half of "an import action"; should the next leg wire it
   into the TUI as a palette command (`:import-pr`) so it can run from inside
   an open review?
