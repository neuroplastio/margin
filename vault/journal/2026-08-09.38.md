## What changed

The feedback: after `c` with a visual selection (or a line dive) auto-appends
the `L12-18: ` reference, typing should begin immediately after it — "no
intermediate command-line step". It did not: a non-empty buffer opened in
normal mode with the cursor at column 1, so the reviewer had to press `a`/`i`
before the first keystroke. (The reference is the only thing in the buffer, but
the insert-iff-empty rule, interaction.md, does not know that.)

The fix is one branch in the `VimEnter` callback in `composerInit`
(`internal/review/composer.go`), ahead of the existing emptiness check:

- If the buffer is a single line that is **exactly** a line reference — the
  shape comment.new appends: `L12: ` or `L12-18: `, trailing whitespace
  optional — open with `startinsert!` (the `A` form: append at the end of the
  line, then insert), so the reviewer is typing past the reference's trailing
  space on the first keystroke. The reference is the host speaking for the
  reviewer ("about these lines"), not text the reviewer wrote, so the
  insert-iff-empty rule relaxes exactly for this shape.
- Anything else is untouched: an empty buffer still `startinsert`s, and a
  buffer with real text — a resumed draft, or a comment being edited — still
  opens in normal mode with the cursor at {1,0}. The carve-out is shape-exact,
  so "`L12-18: some words`" is still an edit and still needs one `<Esc>` to
  exit.

**What I chose and rejected:** chose the exact-shape detection inside
composerInit over threading a host-side "I scaffolded this" flag through
`newComposer` — the prefix knowledge already lives in both places (Go builds
it, the footer/help document it), and the Lua branch keeps the whole
mode decision in one callback. Chose `startinsert!` after discovering nvim
clamps the cursor *onto* the last character: naive cursor arithmetic sits the
reviewer in front of the trailing space and typing comes out `L3-6:ship it`
(recorded as F22).

## Demo

```bash
make build && ./bin/margin testdata/sample.md
```

1. `V` on a paragraph, `j` to extend across a couple of blocks, then `c` — the
   composer should open *already in insert mode* with the cursor blinking right
   after `L3-6: ` (or whatever the range is). Type immediately; the reference
   stays ahead of your text. Submit (`ctrl+enter`) and the posted comment
   reads `L3-6: your text`.
2. Same, but with a line dive: `l` into the table under "### What changes",
   `j` to a row, `c` — the composer opens in insert mode after `L48: `.
3. Now press `e` on an existing comment, and also resume a draft: both should
   still open in *normal* mode with the cursor at the start — the carve-out
   must not leak into edits or text-bearing drafts. `esc` (once) exits.

Questions for the maintainer: does typing straight after `c` past the reference
feel right, or do you find yourself wanting to edit the reference itself
(deliberately excluded — `e` gives you normal mode for that)? And is the
behaviour on the resumed-prefix edge (`c`, no typing, `esc esc`, `c` again —
insert mode after `L3-6:`, space trimmed) acceptable, or should an abandoned
prefix-only draft behave like any other resumed draft?
