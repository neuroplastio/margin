Kind: felt
Task: RENDER-03
Commit: (this one)

## What changed

No open questions blocked the board and `vault/feedback/` was empty, so this
is the next unblocked M1 backlog item in board order.

A table previously fell into the general `blockRaw` bucket — shown verbatim,
`|` pipes and all, with the alignment row (`| :--- | ---: |`) printed on
screen as if it were a row of data. This leg gives it its own kind and a real
column layout:

- **`blockTable`** (`internal/review/document.go`) is a new block kind,
  carrying a `*tableBlock` (`header []string`, `rows [][]string`, `aligns
  []tableAlign`). It also keeps `lines` — the raw `|` source, same as
  `blockList` already does — purely so `quoteBlock` can reuse the verbatim
  export path unchanged; the interactive renderer reads `table` instead.
- **`tableFor`** (parse.go) walks a `*eastast.Table`'s children: goldmark
  always parses GFM's required delimiter row into a distinct `TableHeader`
  node rather than a plain `TableRow`, so header and body rows are told
  apart by node type, not position. Each cell's raw markdown comes straight
  off `cell.Lines()` (see F14 in findings.md — unlike every other node this
  package reads, a table cell's `Lines()` needs no `extent()`), then through
  `cellText`, which reuses RENDER-06's `parseInline` unchanged to strip a
  cell's `**bold**`/`` `code` ``/`[link](url)` down to plain text.
- **`renderTable`** (review.go) is the render path: a bold header row, a dim
  rule under it, then one row per body row, each column padded to its own
  width and alignment (`tableColumnWidths`/`padCell`). Colours resolve
  against `body` — the same variable that already carries `textStyle` or
  `reviewedTxt` depending on the block's mark — so a reviewed table dims
  exactly like the paragraph and quote text around it; the header's
  `body.Bold(true)` is the same "build on top of body" call RENDER-06 made
  for a paragraph's bold runs, kept for the same reason: markup that dims
  with the rest of reviewed prose, not markup that is fixed regardless
  (RENDER-02/06's call for code and links, which are closer to syntax than
  to data).
- **No vertical bars.** Columns are separated by two spaces, not a `│`
  glyph — RENDER-04 already decided that a block quote's `>` is markdown
  source, not a rendering, and drew a rule instead; the same call applies to
  a table's `|`. The header rule (`─`, dim) is the one border kept, because
  it is the one piece of table structure — "here is where the data starts"
  — that is not simply reproducible by column alignment alone.
- **Column widths narrow to fit, evenly.** `tableColumnWidths` computes each
  column's natural width (its widest cell, header included, in runes) and,
  only if the row would exceed the measure, repeatedly shaves one rune off
  the currently-widest column down to a 3-rune floor until it fits — so a
  table that is already narrow enough is untouched, and one that is not
  loses width from its fattest columns first rather than truncating one
  column to nothing while its neighbours stay full width.

**Cell markup is stripped, not styled.** `cellText` discards `parseInline`'s
run styling and keeps only the text — a table cell is prose too, but
colouring it in place would tangle column-width arithmetic with ANSI byte
counts (`len([]rune(...))` on a styled string counts escape bytes as runes).
Deferred rather than solved, the same way RENDER-06 itself deferred list
items and quotes in its own first pass: `tableBlock`'s field comment names it
explicitly so it is not mistaken for an oversight.

**Export is untouched by all of this.** `quoteBlock`'s `blockTable` case
joins the existing `blockRaw`/`blockList`/`blockQuote`/`blockListItem` bucket
and reproduces the original `|` source verbatim (capped at
`maxQuoteLines`, same as the others) — an agent reading the export gets back
the exact table it would see in the file, not a re-layout of the parsed one.

## Verification

`make check` (build, `go test ./...`, `go vet ./...`) is green. `make
test-race` is also green — not composer/emulator code, but this touches the
shared render loop, the same reasoning RENDER-02 gave for running it.
`gofmt -l` clean.

New/updated tests: `TestTableExtensionKeepsRowsIntact` (updated for the new
kind — asserts `blockTable`, its raw `lines`, and its parsed header/rows, in
place of the old "still blockRaw" assertion RENDER-03 itself made obsolete,
the same way RENDER-02 retired its fenced-code sibling),
`TestTableCellsStripInlineMarkupAndRespectAlignment` (a cell's `**bold**`
comes out plain, and left/right/center alignment from the delimiter row
lands on the right columns), `TestRenderTableAlignsColumnsAndStaysInMeasure`
(every rendered line is the same de-styled width, the rule contains `─`,
a right-aligned column's value sits flush right),
`TestTableColumnWidthsNarrowsToFit` (a table wider than the measure narrows
to fit, no column below the 3-rune floor), `TestTableColumnWidthsLeavesRoomWhenItFits`
(a table that already fits keeps its natural widths exactly).

I cannot see a screen, so I cannot confirm the column layout actually reads
as a table at a glance, that two-space column spacing is enough separation
without a vertical rule, or that the dim header rule is visible enough
against the gutter and surrounding prose. I did print `renderTable`'s
de-styled output for `testdata/sample.md`'s existing table at both the full
measure (76) and a narrow width (30) to sanity-check the layout algorithm
itself — columns line up, narrowing kicks in and truncates with an ellipsis
rather than overflowing — but that confirms the *arithmetic*, not how it
looks in a real terminal. See the demo recipe.

## Demo

```
go run ./cmd/margin testdata/sample.md
```

Navigate (`j`/`k`) to the "Rollout" section — its "Session behaviour" table
(Component / Before / After, four rows, one cell with inline code:
`` Redis `GET`, ~0.4ms p50 ``) is the fixture. Answer:

- Does it read as a table at a glance, or does two-space column separation
  with no vertical bar read as coincidentally-aligned paragraphs instead?
- Is the dim `─` rule under the header enough to mark "this is the header,"
  or does the table need a fuller border (top/bottom, verticals) to read
  clearly?
- Is the header bold enough to stand out, or does it blend into the body
  rows once you are past the rule?
- Resize the terminal narrow (under ~50 columns) and re-open. Does the
  narrowing (columns shrink, then truncate with `…`) degrade gracefully, or
  does the table become unreadable before it should?
- Mark the table reviewed (`space` while it's focused). Does the whole table
  dimming — header included — read as intentional, or does the header lose
  too much contrast against the rule and gutter?
- What I chose: no vertical bars (RENDER-04's block-quote precedent — `|` is
  source syntax, not a rendering), a dim `─` rule as the one border kept,
  even proportional narrowing down to a 3-rune floor, inline markup in cells
  stripped to plain text rather than styled. What I rejected: a full
  box-drawn border (heavier than margin's existing minimalist treatments of
  quotes and lists), styling cell markup in place (defers cleanly — the
  column-width math would need to go rune-aware-of-ANSI to do it, not worth
  it for a first pass).
