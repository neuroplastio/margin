## What changed

Drains `vault/feedback/2026-08-07-stdout-export.md`, which promoted the
`--stdout` item already on the board and pinned two constraints:

**1. The TUI must not render to stdout.** `Run` now takes a `RunOptions{Stdout
bool}`. When set, it opens `/dev/tty` (via a new `openTTY` var, substitutable
in tests) and passes it to `tea.WithOutput` before starting the program, so
the interface draws on the controlling terminal and stdout stays free for the
review. See **F11** in `findings.md` — Bubble Tea defaults its output to
`os.Stdout` unconditionally, so this has to be explicit. Failing to open a
controlling terminal is a reported error, not a silent fall-through to
drawing over the pipe.

**2. Semantics, given persistence has since landed.** The feedback was
written assuming STORE-01 had not shipped, and said `--stdout` should mean
"run the review normally, and on quit write it to stdout instead of requiring
`Y`" — but also anticipated STORE-01 landing and said explicitly *not* to
build a second, non-interactive "print what's already on disk" mode even once
it had, because that is materially different work. STORE-01 and STORE-02 are
in fact both done as of this run, so I checked: the feedback's own text
already covers this case and nothing about it changes. Implemented exactly
what it specified — on quit, `fmt.Print(exportReview(m.path, m.doc,
m.threads, m.marks))`, the identical call `Y`'s `exportToClipboard` makes, so
the two paths can never drift apart. `Y` itself is untouched and still works
in `--stdout` mode.

The board had this filed `[mech]`, which held: every behaviour the feedback
asked for is either already-decided (the `Y` export format, from
`interaction.md`) or a concrete, unambiguous mechanism (the tty redirection,
the "same code path" instruction) — nothing here required a feel judgement,
so no question was raised.

`--stdout` is wired as a cobra flag on the root command; `newRootCmd`'s runner
signature changed from `func(string) error` to `func(string, RunOptions)
error` to carry it, which meant updating `main_test.go`'s `exec` helper and
every test that stubs the runner.

## Verification

`make check` is green. Also ran `make test-race` (14.7s, clean) even though
this leg does not touch `composer.go` — `review.go`'s `Run` is shared
territory and the marginal cost of checking was small.

New tests:
- `internal/review/stdout_test.go`: `TestExportReviewContainsNoANSI` and
  `TestExportReviewOfAnEmptyReviewContainsNoANSI` — the feedback's own ask,
  pinning that the string `--stdout` prints carries no escape codes.
  `TestStdoutRunSurfacesTTYOpenFailure` substitutes `openTTY` to fail and
  asserts `Run` returns that error rather than reaching `tea.NewProgram` (which
  would otherwise block on stdin in a test process with no controlling
  terminal — the test would hang rather than fail cleanly if this regressed).
- `cmd/margin/main_test.go`: `TestStdoutFlagReachesTheRunner`,
  `TestWithoutStdoutFlagDefaultsFalse`, `TestHelpMentionsStdout`.

**What is not, and cannot be, tested here:** that piping actually behaves —
`margin --stdout spec.md | cat -A` showing a clean review with no stray
escape sequences on a real terminal. `Run()` itself opens a genuine
interactive session and isn't exercised end to end by anything in this
package (same boundary `TestLoadDoc` and its neighbours already respect); the
tests above cover the two seams that can fail without one. Worth a spot check
on a real terminal, though this is an infrastructure check rather than a felt
one — nothing about wording, keys, or layout is undecided.
