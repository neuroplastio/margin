# 2026-08-08.3 — Block quotes: a rule down the left edge, not `>` on every line

Kind: felt
Task: feedback/2026-08-08-3-blockquote-rendering.md (RENDER-04)
Commit: (this one)

## What changed

`vault/feedback/` held two items. Feedback preempts the board; by the batch's
own numbering `2026-08-08-3-blockquote-rendering.md` is the older of the two
(`-4-line-level-focus.md` is next), so that is this leg.

A block quote previously fell into the `blockRaw` bucket and was shown
verbatim — every source line with its `>` still attached, unwrapped, exactly
as the feedback complained. Fixed by giving it the same treatment RENDER-04's
sibling `blockList` already got: its own `blockKind` (`blockQuote`, appended
last so no existing kind's ordinal shifts under `anchorFor`'s hash), parsed
from `*ast.Blockquote` in `parse.go`.

- **`quoteLinesFor`** (`parse.go`) strips the leading `>` (and its one
  optional CommonMark space) from each source line, keeping a bare `>` line
  as an empty string so a multi-paragraph quote's internal blank-line breaks
  survive into `block.lines`.
- **`wrapQuote`** (`review.go`) folds consecutive non-blank lines into a
  paragraph and re-wraps each to the measure, the way `collapse()`+`wrap()`
  treats an ordinary paragraph, turning each stripped blank line back into a
  paragraph break in the output.
- **Render** (`review.go`) prepends a dim `"│ "` rule to every line a
  `blockQuote` produces — including blank paragraph-break lines, so the rule
  reads as one continuous line down the passage rather than breaking for its
  own gaps — wrapping at `w-2` so the rule and its padding come out of the
  measure, per the feedback's own note.
- **Export** (`export.go`) needed one line: `blockQuote` joins `blockRaw`,
  `blockList` in the branch that reuses `b.lines` instead of `collapse`d
  text. Since those lines already have their `>` stripped, `quoteBlock`'s
  existing `"> " + l` reconstructs the original markup — not a special case,
  just falling out of the representation choice.

## Choices made without asking, and why

- **Text colour left as ordinary paragraph prose** (`textStyle`/
  `reviewedTxt`), not `rawStyle` the way `blockList`/`blockRaw` get when
  unreviewed. Those use `rawStyle` as a "this is shown verbatim, not really
  rendered" signal; a quote no longer is verbatim, so borrowing that signal
  would say the wrong thing. The rule is what marks it as a quote, the same
  way a real renderer's left border does the marking while the text itself
  stays normal prose.
- **Nested quotes and a list/fence inside a quote: explicitly not handled.**
  The feedback flagged both as worth knowing about but not worth designing
  for yet. `quoteLinesFor` only strips the outer `>`, so a nested quote comes
  out with its inner `>` still in the text (not corrupted, just not
  beautified — a second rule is the obvious next step if this comes up in
  practice). A list or fence inside a quote gets folded into prose like any
  other text in a paragraph, losing its inner structure — same tradeoff
  RENDER-04 itself made for the common case (prose) over the rare one.
- **Rule colour**: reused `dimStyle` (244), the same colour a collapsed
  thread's own `"│ "` prefix already uses — one glyph, one meaning, rather
  than inventing a second "this is a rule" colour.
