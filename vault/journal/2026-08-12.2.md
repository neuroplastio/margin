# 2026-08-12.2 — shift+enter is a line break, not an exit

Kind: felt
Task: Feedback `2026-08-12-shift-enter-line-break` — "Shift+Enter currently
exits the nvim editor, keeping the draft comment. I want Shift+Enter to be a
line break (muscle memory for non-vim multiline terminal prompts), not exit."
Commit: (this one)

## What changed

Shift+enter in the composer now inserts a line break. It was being forwarded
to nvim as a CSI-u `<S-CR>` (`\x1b[13;2u`), and what the child did with that
was up to the nvim build:

- nvim 0.12.4 (probed on this machine) silently drops an unbound `<S-CR>` in
  insert mode — the keystroke vanished, no newline and no exit.
- The maintainer's nvim turned it into the draft exit. The sequence starts
  with a lone ESC, nvim resolves CSI-u only when a mapping names the key (the
  meta-key catch in F19), so unbound the ESC stands alone — and in normal
  mode ESC *is* the mapped draft-exit.

Neither reading is "a line break", so neither is a fix. The fix is host-side
and is the same shape as the ctrl+enter intercept (F16): `sendKey` catches
`{Code: KeyEnter, Mod: ModShift}` before encoding and forwards the plain `\r`
a bare enter gets — one CR is unambiguous to every nvim, and terminal-prompt
muscle memory ("shift+enter = newline in a multiline prompt") is exactly what
a plain newline is.

Chosen: host intercept over a composer mapping. A `<S-CR>` mapping in
composerInit would only work on nvim builds that decode the CSI-u key at all,
and the whole bug is that the decode is unreliable; the host already owns the
ctrl+enter intercept for the same structural reason, so this is the same
battlefield, not a new one. Rejected: leaving it to `encodeModifiedKey`'s
CSI-u branch (the status quo that produced the exit).

**What I could not reproduce:** the exit itself. On this machine's nvim
0.12.4 the forward produced silence, not an exit — the maintainer's report
names a different nvim, and the ESC-standing-alone mechanics above are the
mechanism F19 already documents. The byte-level and behaviour tests pin the
*new* contract; whether the old exit reproduces on the maintainer's nvim is a
question only their screen can answer (demo recipe).

**Test-infra change:** `composer.wait()` caches the child's exit error once,
so a poll (`waitExitPoll`, new) and a blocking wait (`waitExit`) can both run
without calling `cmd.Wait` twice — the second call errors "already called",
which `outcomeFromExit` read as `discarded`. `waitForChild` (production) and
both helpers now share the cached channel.

## Verification

`make check` green (build, test, vet). `make test-race` green — this is a
composer change and the emulator is written from the pty goroutine and read
from the render goroutine, so the race build is the real gate.

New/changed tests in `internal/review`:
- `TestSendKeyEmitsBytes` — the "shift+enter" case now pins `\r` instead of
  `\x1b[13;2u`.
- `TestShiftEnterInsertsLineBreak` — end to end with a real nvim: types
  "hello", shift+enter, "world", asserts the composer is still alive (no
  exit), then `ctrl+s` submits and the body is exactly `hello\nworld`.

No open questions raised.

## Demo

```bash
make build && ./bin/margin testdata/sample.md
```

1. Open a comment on any block (`c` on a paragraph).
2. Type `hello`, press **shift+enter** — the cursor must drop to a new line
   and the composer must NOT close (it used to exit, keeping a draft).
3. Type `world` on the new line. Submit with `ctrl+s` — the comment posts as
   two lines.
4. Edit an existing comment (`e` on a posted comment), press **shift+enter**
   mid-line — same result: a break, not a close.
