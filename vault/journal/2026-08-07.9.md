# 2026-08-07.9 — STORE-03: live reload of thread files

Kind: mech
Task: STORE-03 (the fsnotify half STORE-02 split off — see `vault/journal/2026-08-07.7.md`)
Commit: (this one)

## What changed

STORE-02 wired thread persistence into the running app in both directions
that don't need a background process: load every thread file on open, save
one on submit. What it deliberately left out was noticing a thread file that
changes on disk *while margin is already running* — an agent replying to a
comment, or writing a brand-new thread, mid-session. That is this leg.

**The watcher.** `threadWatcher` (new file, `internal/review/watch.go`)
wraps an `fsnotify.Watcher` pointed at `.margin/threads/<docPath>/` for the
document currently open. `newThreadWatcher` creates that directory upfront
if it does not exist yet — fsnotify can only watch a directory that is
already there, and a document with no comments yet has no thread directory
at all. One `MkdirAll` either way, since the first locally posted comment
would create the same directory through `threadStore.save`.

`wait()` blocks on the watcher's `Events` channel and turns a create, write,
or rename of a `.md` file into a `threadsChangedMsg` — the same shape
`waitForDamage` already uses for the composer's pty output: a channel
wrapped in a `tea.Cmd`, re-armed by returning `m.watcher.wait()` again after
handling each message, rather than a polling ticker (see F4 in
findings.md — the same reasoning applies here: a redraw should be
event-driven, not scheduled). Anything that is not a qualifying event (a
directory mtime bump, a stray non-markdown file) is filtered out inside the
loop so the model only ever wakes for something it can act on. A closed
watcher or an fsnotify-level error both end the loop by returning a nil
message — live reload stopping silently is preferable to interrupting the
reviewer over it, since the document stays fully readable without it.

**The merge.** `reloadThreads` re-reads every thread file on disk for the
document (`loadThreadsForDoc`, unchanged from STORE-02) and merges it into
`m.threads`: a new anchor is added outright; an existing anchor has its
`quote` and `posted` replaced with what is on disk. Drafts are never
touched, because `writeThreadFile` never represents them — there is nothing
on disk that could clobber one. `reattach` runs again afterward so a
newly-loaded thread whose anchor has since vanished from the document comes
back correctly marked orphaned rather than silently treated as live.

**Wiring.** `model` gains a `watcher *threadWatcher` field, nil wherever
`store` is nil (tests, the seeded document) — mirroring how `store` itself
is scoped. `Init()` batches `m.watcher.wait()` alongside the existing
heartbeat. `Update` gets a `threadsChangedMsg` case that calls
`reloadThreads` and re-arms the watch; a reload error is surfaced through
`m.status` (the same "surface, don't drop" pattern `loadThreadsForDoc`
already documents for a malformed file found on open) rather than silently
swallowed, but does not stop future events from being watched for. `Run`
constructs the watcher after `m.store` is set, non-fatally: a read-only
filesystem or an exhausted inotify watch budget should not stop a review
from opening, so a failed `newThreadWatcher` just leaves `m.watcher` nil,
and every nil-receiver method on `*threadWatcher` degrades to a no-op —
same shape as `threadStore.save`. `defer watcher.close()` releases the OS
watch when `Run` returns, which is also what unblocks the `wait()`
goroutine's channel read on quit (fsnotify's `Close()` closes `Events`).

**What this deliberately does not do.** No visible indication that a
reload happened — no new status message on the success path, no glyph, no
sound. Wording and what-happens-on-a-change are exactly the kind of thing
CLAUDE.md reserves for the maintainer to feel and judge; the data merge is
mechanical and provable, but *how the reviewer learns something changed* is
not, so nothing here invents an answer. The thread reappears using the
already-settled collapsed/expanded rendering (interaction.md), the same as
data loaded on open — this is the same rendering treatment STORE-02 already
gave threads that were on disk before the session started, just applied to
threads that show up mid-session instead. If the maintainer wants a "this
changed" affordance, that is new felt work, not a follow-on to this leg.

Also out of scope: an in-progress edit (a composer open on `posted[i]`)
racing an agent inserting a comment *before* index `i` in the same thread is
not specifically handled — the merge replaces the whole `posted` slice by
value, so a same-session edit only ever reapplies at submit time via
`dismiss`, which already writes its own version through `m.store.save`
afterward. Genuinely concurrent edits to the same thread from both sides at
once are not something this project's single-reviewer model needs to
solve, and nothing observed in testing suggested it needs solving now.

## Verification

`make check` is green. `make test-race` is also green, run because this
leg adds a new goroutine (the watcher's blocking channel read) alongside
the render loop, even though it does not touch the composer or emulator
directly — nvim is installed in this environment, so the composer's own
tests ran for real rather than skipping (confirmed
`TestSubmitPersistsThroughTheStore` and `TestDamageArrivesPromptly` both
executed, not `t.Skip()`d — see F8 in findings.md on why that check
matters).

New dependency: `github.com/fsnotify/fsnotify v1.10.1` (`go.mod`/`go.sum`).

New tests in `internal/review/watch_test.go`:
`TestReloadThreadsAddsANewThreadWrittenExternally`,
`TestReloadThreadsMergesAnAppendedReplyIntoAnExistingThread`,
`TestReloadThreadsPreservesAnUnsubmittedDraft`,
`TestReloadThreadsWithoutAStoreIsANoop`,
`TestReloadThreadsReattachesOrphanState` (the merge logic, no real
filesystem watching involved), plus
`TestThreadWatcherFiresOnAFileWrittenAfterItStarts`,
`TestThreadWatcherIgnoresNonMarkdownFiles`,
`TestNewThreadWatcherCreatesTheThreadDirUpfront`,
`TestNilThreadWatcherWaitIsANoopCmd`, `TestNilThreadWatcherCloseIsANoop`
(the watcher itself, over a real `fsnotify` watch — these `t.Skip()` with a
clear reason if `newThreadWatcher` fails, e.g. no inotify available, rather
than failing the suite over an environment limitation unrelated to the
code under test). inotify was available in this sandboxed environment, so
all of them ran for real rather than skipping.

Nothing here is felt: no key changed, nothing new renders that was not
already reachable through STORE-02's load-on-open path. The board's
`Awaiting review:` stays on **PARSE-02** — this leg did not touch it.
