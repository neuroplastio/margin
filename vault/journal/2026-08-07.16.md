## What changed

`vault/feedback/` held nothing but its README and `vault/questions/` had no
open question, so the leg fell through to the board. The board's `Awaiting
review:` is still **PARSE-02**, so only `[mech]` work was eligible. M2's
backlog listed **THREAD-03** ahead of **EXPORT-05** (both genuinely unblocked
now that THREAD-01 landed `resolved`), so THREAD-03 is this leg; EXPORT-05 is
next in board order.

Read D11 before touching anything: deletion is a tombstone, not a removal — a
deleted comment keeps its author and timestamp, drops its body, so a reply
that answered it does not end up dangling above nothing.

**`comment` (`internal/review/document.go`)** gains a `deleted bool` next to
`author`/`body`/`at`.

**`(*thread).deleteComment(i)`** tombstones `posted[i]`: blanks `body`, sets
`deleted`, and clears any in-progress edit draft targeting that index — editing
a comment whose body was just dropped makes no sense. An out-of-range `i` is a
no-op, not a panic, since a caller could be holding a stale index.

**`(*thread).deleteThread()`** answers the board's "delete a whole thread"
half by applying `deleteComment` to every posted comment. I considered a
separate thread-level `deleted` flag but rejected it: once every comment is
tombstoned there is nothing else per-thread left to distinguish "deleted" from
"never had a comment," so a second flag would carry no information a reader
couldn't already get from the comments themselves. D11's own wording only ever
defines the shape in terms of "a deleted comment," which this reuses rather
than inventing a second shape.

**`marshalThread`/`parseThreadFile` (`internal/review/store.go`)** carry the
tombstone through the file: the `## author — timestamp` header is untouched
(that's exactly what D11 says survives), and the body underneath is replaced
with a new `tombstoneMarker` constant (`*deleted*`) rather than left blank —
blank would be indistinguishable from a comment that was always empty, and the
whole point of a thread file's format (D5) is that it reads plainly to a human
or agent with margin closed. `parseComments` treats a body that is exactly the
marker as tombstoned and reports an empty body with `deleted: true`; anything
else round-trips as before.

**`reloadThreads` (`watch.go`) needed no change.** It already replaces
`existing.posted = t.posted` wholesale on every reload — the same line that
picked up an appended reply or a `resolved: true` edit in THREAD-01 already
picks up a hand-tombstoned comment with no further work.

Also updated a stale comment in `palette_test.go` that cited "no delete
command yet (THREAD-03, unbuilt)" — THREAD-03 is now built, but there is still
no delete command in the registry, so the comment now points at THREAD-04,
which is what wires one in along with the confirmation D11's "explicit and
confirmed" calls for.

## What this deliberately does not do

No command, no keybinding, no rendering. Nothing in `command.go`'s registry
calls `deleteComment` or `deleteThread`, and no renderer branches on `deleted`
— `summary()` and the expanded-thread view read `comment.body` exactly as
before, agnostic to why it might be empty. That is **THREAD-04**: whether a
tombstone renders as something explicit or just an absence, which key deletes,
and what confirms a gesture that destroys the reviewer's own words (goals.md
principle 3).

I checked the felt-half question before closing this out: does something now
render differently, or not render at all? The one place this could bite is
`reloadThreads` picking up a hand-edited tombstone from disk and flowing an
empty `body` into the *existing* renderer with no new branch of its own — the
exact trap CLAUDE.md warns about, where "no branch for a new case" is itself a
decision. I judged this the same class of thing THREAD-01 already established
for `resolved` (an inert field only reachable today by hand-editing a file and
letting the live watcher pick it up, since nothing in the interactive path
calls either method) rather than a new felt surface: no renderer gained a
branch for `deleted`, an empty-bodied comment was already a representable
state the renderer had to tolerate, and the actual decision about what a
tombstone *should* look like is explicitly left to THREAD-04, not quietly
resolved by omission here.
