## What changed

The navigation-feature feedback's first request: `/` opens a search prompt,
matching text is highlighted in the document, and the reviewer jumps between
hits. The interaction is settled by this leg, as the feedback said it should
be, not raised:

- **`/` opens the prompt.** A dim rule above a ` /draft█` line rendered where
  the palette sits, in its style — same rule, same block cursor, same
  count/position line. Opening the prompt cancels visual mode, like `:`
  does, and resets the draft to empty (the previous committed query is not
  prefilled — `esc` on a fresh prompt is how you get back to a clean slate).
- **Typing highlights live.** Matches are recomputed every render from the
  draft, so the highlight tracks the keystrokes before they are committed.
  Matching is **case-insensitive** and runs over the **rendered lines**, not
  the source: the query searches what is on screen — wrapped prose, the
  aligned table, chroma's code — and a hit inside a wrapped paragraph
  highlights the run the reader is actually looking at. The frontmatter is
  excluded, the same call `rebuild` already makes (metadata is not part of
  the document).
- **`enter` commits and jumps.** The draft becomes the active query, the
  prompt closes, and focus jumps to the entry holding the next match
  *strictly after* the current focus line (wrapping to the first when there
  is none ahead) — so searching from a heading whose text matches jumps
  forward, not back to itself. The match line is centred in the viewport and
  `scrollAnchor` is updated so clampScroll does not yank the offset back
  (SCROLL-01's decoupling).
- **`n`/`N` walk the list** (`search.next`/`search.prev`, new registry
  commands) with wraparound at both ends, for as long as the query stays
  active. `esc` cancels the prompt's *edit* without committing — a previous
  committed query and its highlight survive, vim's abandoned-search-command
  behaviour. Backspace deletes a rune and, at an empty draft, cancels like
  the palette.
- **The highlight is a background-only SGR** (`48;5;94` — warm brown,
  distinct from the selection's slate 236 and from the mark colours), opened
  at a match's first rune and closed with a background-only reset, so the
  line's own foreground — paragraph text colour, inline bold/code, chroma
  tokens — is untouched. A full reset *inside* a match (the boundary of a
  bold run split by the query) would clear the background mid-hit, so it is
  immediately reasserted, the same trick `selLine` uses.

**What was rejected:** matching against the markdown source with positions
mapped into the render. The source and the screen diverge the moment a
paragraph wraps or a table re-aligns, and a search highlight that lands on a
different run than the one read would be worse than the two-keystroke
limitation live rendered-line matching costs (a query that spans a wrap
boundary cannot match; re-run it as the piece that fits on one line). Also
rejected: highlighting in the gutter or on the frontmatter, and making the
prompt prefill the previous query — an empty prompt on every `/` is the
simplest thing to reason about.

## Demo

```bash
make build && ./bin/margin testdata/sample.md
```

1. Press `/` — a prompt appears at the bottom, `/█`, over a dim rule.
2. Type `change` — every occurrence lights up with a brown background as you
   type, and the prompt reads the count (e.g. `1/6`).
3. Press `enter` — focus jumps to the first match after wherever you were,
   the match line centred in the viewport.
4. Press `n` a few times — focus walks forward through the hits, wrapping to
   the first at the bottom. Press `N` to go back.
5. Press `/` again, type something that is not in the document (e.g. `zzz`),
   then `esc` — the prompt closes, the old highlight stays. Press `/` then
   `esc` with an empty prompt — the search is cleared entirely.
6. Backspace inside an open prompt deletes one character at a time; past the
   first it cancels like `:`.

Questions for maintainer: is the brown (`48;5;94`) the right highlight — it
must read as "found" without competing with the slate selection or the green
mark rule; is the live-highlight-as-you-type the right behaviour, or should
matches only appear once enter is pressed? Does `enter` jumping *after* the
current focus line feel right, or should it land on the match under the
cursor? Should the prompt prefill the previous query (vim does) instead of
always opening empty? And is the two-keystroke wrap-boundary limitation
acceptable for v1, or does the search want to run over source with rendered
positions after all?
