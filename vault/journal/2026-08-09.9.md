# 2026-08-09.9 — deleted comments disappear; `V` reveals them

Kind: felt
Task: (feedback, `vault/feedback/2026-08-09-todo-review-feedback.md`, §1 first
bullet — "Prefer for deleted comments to disappear altogether, with an explicit
action/command to show deleted comments")
Commit: (this one)

## What changed

THREAD-04 rendered a tombstoned comment as a `[deleted]` marker in both the
collapsed summary and the expanded thread. The maintainer preferred them gone
by default, with an explicit reveal. Feedback preempts the board, and this is
the oldest unaddressed item, so this is the leg.

New behaviour:

- **Hidden by default.** A `[deleted]` placeholder is no longer the default
  view. `visibleComments(t)` (`review.go`) filters tombstoned comments out of
  the render loop, the `j`/`k` focus stop list (`stops`) and the comment
  subspans all at once, so a hidden deleted comment cannot be focused, hit, or
  clicked — cursor and screen never disagree about what exists.
- **`V` to reveal.** A new `thread.showDeleted` command (`command.go`),
  registered in the registry and bound to `V` (uppercase, alongside `R`/`D`/
  `Y` as a view-level verb) and reachable from the palette as `:` + "show".
  Toggling it back off while focus sits on a deleted comment drops focus to the
  thread entry instead of leaving the cursor on nothing.
- **The collapsed summary describes the visible set.** `summary(showDeleted)`
  (`document.go`) skips hidden tombstones and counts only what a reviewer can
  see, so a collapsed line never reads `[deleted]` and its `(+N)` never
  overstates the conversation. A thread whose comments are *all* tombstones
  renders "comments deleted — V to reveal" in place of "no comments yet — c to
  write one", since the comments are not missing, they were deleted.
- When revealed, tombstones still render as `[deleted]`: the tombstone
  replaced the body on disk (D11/THREAD-03), so the marker is all there is left
  to show — the reveal brings back the provenance (author + time), not text
  that no longer exists.

Chose over two rejected alternatives: (a) *no* reveal at all — a reviewer who
wants to know what was deleted loses even the provenance the tombstone kept;
(b) a per-thread reveal toggle — the flag is a document view, one bit, and
thread-scoping it just made navigation state dependent on which thread you last
toggled.

## Verification

`make check` (build, `go test ./...`, `go vet ./...`) green. No composer or
emulator change, so `make test-race` not required.

New tests: hidden-by-default (no `[deleted]` in the thread, no subspan, no stop,
clean summary); reveal-on-`V` (marker and subspan back); the toggle command
(reveal → hide, focus re-anchored off a now-hidden comment); summary counts
visible-not-deleted; and the all-deleted hint. Plus the existing
`TestEveryCommandIsReachableByAKey` now guards `V`.

I cannot see the screen, so I cannot confirm the empty-box rendering of an
all-deleted thread reads well or that `V`'s place in the palette ordering feels
right — that is the maintainer's call.

## Demo

```
margin some-doc.md
```

1. Open a thread, `e` a comment, delete it (`D` twice). The comment should
   vanish from the thread immediately — no `[deleted]` line.
2. `j`/`k` through the thread: the deleted comment should not be a focus stop
   (no pause on it).
3. Press `V` (or `:` then type "show"). The tombstone comes back as
   `author · time  [deleted]`. Press `V` again — gone.
4. Delete the last comment in a single-comment thread. The expanded box should
   now read `comments deleted — V to reveal`, and the collapsed line
   `no comments`, not `[deleted]`.

Questions: does the empty expanded thread (box with just the hint line) read as
"these were deleted", or does it need something more? Is `V` a reasonable key
for reveal, or does it want a different one now that it is on a real screen?
