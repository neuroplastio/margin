D11 already settled the data model back on 2026-08-07: resolution is a single
boolean, settable and clearable by either party. What was left open — and
what this leg builds — is everything about how that boolean reaches the
screen: which key flips it, whether resolving needs the thread expanded
first, and whether a resolved thread dims, collapses, or disappears.

**The key.** A new `thread.resolve` command, bound to `R` (shift-r). `r`
already means "mark this block reviewed" — `R` reads as the same verb aimed
at the thread instead of the block, which seemed like the more mnemonic
pairing than an unrelated letter. Applicable the same way `comment.edit`
already is: a thread has to exist at the focused block, nothing about its
current display state. That answers "reachable from the collapsed line or
only expanded" directly — there is no separate gate, so `R` works either way.
Toggling persists immediately via the same `m.store.save` path a posted
comment takes in `dismiss`, rather than waiting for some other save point;
resolving is small enough that a silent delay before it reaches disk would be
surprising if the reviewer quit right after.

**What I chose for the visual, and what I rejected.** Three candidates were
on the table in `interaction.md`'s "Not settled" list: dim, collapse, or
disappear. I rejected collapse and disappear — a resolved thread whose
comments render (a checkmark, a badge) but do not go away when the flag
flips is a smaller, more reversible change than adding a new display state
that also has to be un-collapsed or brought back by something. It also
matches D11's own export-safety rationale: resolving is meant to be cheap to
undo, and undoing something that vanished from the screen is a worse
experience than undoing something still sitting right there. So:

- **Collapsed** (unfocused): the plain dim `│` rule becomes a dim green `✓`
  (`resolvedTxt`, colour 108) ahead of the summary. The draft/pending-edit
  orange underneath is untouched even on a resolved thread — unsaved text is
  the more urgent of the two signals and should not go quiet just because the
  thread was resolved around it.
- **Expanded** (focused): a two-line `✓ resolved` badge appears ahead of the
  comments, inside the same box. The comments themselves render exactly as
  they did before — same author lines, same wrapping, same focusable spans.
  Resolving says "this is handled," not "this no longer matters"; the
  conversation that got it there is still what the reviewer came to read.

The span math needed care: the badge adds two lines ahead of the comment loop
inside the same box, so `commentStart` and each comment's subspan `end` both
needed a `resolvedOffset` added or a resolved thread's later comments would
report spans that undershoot their actual position on screen — clicks and
`e` would land one comment early. `TestExpandedResolvedThreadSpansStayInsideTheirThread`
pins this the same way the existing (unresolved) `TestCommentSpansSitInsideTheirThread`
already did.

`resolveTarget` (`command.go`) names the palette action as "resolve" or
"unresolve" rather than a bare toggle — CMD-04's precedent (`markTarget`,
`editTarget`) is that a palette row should read as an action, not a state the
user has to already know how to interpret.

## Demo

```
go run ./cmd/margin testdata/sample.md
```

Move focus (`j`/`k`) to a block that already has a thread — or press `c` to
start one and `ctrl+enter` to submit it first — then:

- Press `R`. The status line should say "resolved". Move focus away with `j`
  or `k` so the thread collapses: does the checkmark read as "this is done"
  at a glance, or does it just look like a different bullet?
- Move focus back and expand it. Does the `✓ resolved` badge read as a status
  ahead of the conversation, or does it look like part of the conversation —
  a third comment, say?
- Press `R` again to unresolve. Status line should say "unresolved", checkmark
  reverts to the plain `│` rule.
- With focus on a resolved, expanded thread, press `e` to edit a comment, or
  `c` to reply. Comments should still be reachable and editable exactly as
  before — resolving is not meant to freeze the thread, only to mark it.
- What I chose: dim-with-a-checkmark collapsed, a badge (not a collapse or
  disappearance) expanded, `R` reachable from either state. What I rejected:
  collapsing or hiding a resolved thread, which would need its own
  un-collapse mechanism and is harder to undo at a glance than a badge that
  just goes away.
