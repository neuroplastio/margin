## What changed

The navigation-feature feedback's second request: vim's count-plus-`gg` form.
`42gg` (and `42G`) jumps to source line 42; `gg`/`G` alone are unchanged — still
first/last block, the settled interaction.md bindings.

The feedback left two questions open. Both are settled by this leg, made rather
than raised:

- **"Line number" means the markdown source line, 1-based.** The alternative, a
  rendered row, shifts with the terminal width and has no stable identity. The
  source line is the locator reviewers and agents already use — the `L12-18`
  line-dive payload, the `file:L<n>` yank — so it is the only defensible unit.
  The jump lands focus on the entry whose block's source range contains the
  line, leaving it at block level (a thread row carries no line numbers, so a
  jump can never land on one; the reviewer dives with `l` if they want line
  granularity). Centring and `scrollAnchor` update follow the search jump
  (gotoMatch), so clampScroll does not yank the offset back.
- **The count works with `G` too.** `42gg` and `42G` are vim's two spellings of
  one motion; teaching only one would surprise anyone who uses the other.

**The count is a pure modifier, not a general repeat.** Digits buffer in the
status line (`line 42` as you type — typing blind digits is dead without it),
and only `gg`/`G` consume the buffer. Any other key clears it and acts exactly
as it would with no count typed: `42j` is a plain `j`, not a repeat. Rejected:
count-repetition for j/k and friends — the feedback asked for line-number
navigation, and a repeat-count is a separate feature with its own ergonomics
(vim's `3j` needs no status line; the two line jumps do). Also rejected: a
registry/palette command for the jump. The count is an argument the staged-value
palette model cannot express (`goto` carries a finite value list; a line number
is unbounded), so like the count itself it stays a key-only verb.

**Edge behaviour, all clamped not silently dropped:** a count past the last
line goes to the last block; `0gg` is the first block; a line no block covers (a
blank separator between blocks) lands on the first block strictly after it — and
a clamp reads `no source line N — jumped to the nearest block` in the status
line rather than pretending the jump landed where asked. The buffer caps at six
digits (`maxCountDigits`) so a key-mash cannot grow an unbounded string; digits
past the cap are swallowed, not leaked. Digits are inert in visual mode and do
not leave a buffer behind.

Mechanics: the existing `g` was eager — it ran move.first on the first press and
set pendingKey so a second `g` (or `y`) could chain. A counted first `g` now
becomes a prefix instead: it sets pendingKey and waits for the second `g`, so
the count can complete (`g`, `4`, `2`, `g` works as `42gg`). The `gg`-without-a-
count path is untouched: the eager move.first already lands on the first block.

## Demo

```bash
make build && ./bin/margin testdata/sample.md
```

1. Type `42` — the status line reads `line 42` as you type; nothing moves.
2. Press `gg` (or `G`) — focus jumps to the block whose source range contains
   line 42, the block centred in the viewport.
3. Type `3`, `g`, `g` — a jump to line 3 (g alone still goes to the top; `G`
   alone to the bottom).
4. Type `9999`, `gg` on a short document — it clamps to the last block and the
   status line says `no source line 9999 — jumped to the nearest block`.
5. Type `42`, then `j` — the count vanishes and j moves one block, exactly as
   without the count.

Chose source lines over rendered rows (source is what `L<n>` references already
mean), count-for-both-`gg`-and-`G` (one motion, two spellings), and a pure
modifier that never repeats j/k. Rejected rendered-line numbering (shifts with
terminal width) and count-repetition (separate feature, not asked for).

Questions for maintainer: does the `line 42` echo as-you-type read right, or
should digits be invisible until `gg`/`G`? Is landing on the block (then `l` to
dive) the right granularity, or should the jump place focus inside a multi-line
block's line dive? Should a `G` with no count keep moving to the last block, or
does vim muscle-memory expect `G` to mean "current line" — the interaction.md
binding says last block, kept.
