# 2026-10-23.11 — a frame keeps each block's rendering

Kind: felt
Task: the maintainer's report: scrolling is terrible, keys and the wheel
flood the queue, and margin then takes it step by step.
Commit: (this one)

## What it was

Every frame rendered the whole document again. On plx's ARCHITECTURE.md
(163 blocks) at 160×50:

| | before | after |
|---|---|---|
| render | 50.7 ms | 0.39 ms |
| `j` + View | 44.0 ms | 0.51 ms |
| wheel + View | 42.2 ms | 0.48 ms |
| `j` alone (Update) | 156 ns | 137 ns |
| Update + hotFrame on hottytest | 55.9 ms | 0.93 ms |
| 20 queued `j` on hottytest | 2.23 s | 25 ms |

Key repeat comes about every 33 ms, and a wheel faster, so input queued
behind 43 ms frames. The CPU profile: 44% chroma highlighting (half of it
the lexer lookup), 34% wrapping and lipgloss. On a host, blocks shown as
surfaces drew their cells too, for the search. F39 has the detail.

The wheel throttle (F25) could not help. It reads the clock when a
message leaves the queue, so once frames outlast its 8.3 ms window it
passes everything.

## What changed

- `render` keeps each block's body (`m.bodies`, keyed by entry, width,
  horizontal offset, mark and partial). `drawBody` is the old switch,
  moved out of render, and reads only its arguments. `rebuild` empties
  the cache. Search still reads the unstyled rows (`drawnBody.text`).
- A table or raw block checks for line marks once, not once per row.
- The wheel is no longer throttled. With fast frames, dropping a tick
  only lost scroll distance, and a tick within 8 ms of a motion report
  was dropped too. Motion keeps its throttle.

Rejected: drawing at most one frame per period, with input applied in
between. Update reads the last frame's spans (j/k on a tall block,
paging, jumps), so a skipped frame means stale layout. Cheap frames make
that unnecessary.

## Tests

`make check` and `make test-race` pass. `TestRenderKeepsBlockBodies`
checks four things:
- Moving focus draws no block again.
- A mark draws the marked block, in the reviewed style.
- A new width, and a sideways scroll, draw again.
- `rebuild` empties the cache.

A mutation that leaves the mark out of the key fails it.
`TestInputThrottlePassesEveryWheelTick` replaces the two tests that pinned
the dropped ticks.

The probe, kept out of the tree. Run it as `PROBE_DOC=<big.md> go test
./internal/review -run TestZZPerfProbe -v`, with `-cpuprofile` for a
profile:

```go
func TestZZPerfProbe(t *testing.T) {
	doc, data, _ := loadDoc(os.Getenv("PROBE_DOC"))
	m := newModelAt(os.Getenv("PROBE_DOC"), doc, nil)
	m.src = data
	m.w, m.h = 160, 50
	m.View()
	start := time.Now()
	for range 50 {
		m.Update(tea.KeyPressMsg{Code: 'j', Text: "j"})
		m.View()
	}
	t.Logf("j+view %v", time.Since(start)/50)
}
```

For a host, wrap the model in one that times Update, run it against
`hottytest.New(t)` as `hotRun` does, and type keys into the host.

## Demo recipe (needs a human check)

```
margin ~/code/neuroplastio/plx/main/ARCHITECTURE.md
```

Run it in hottyterm, in a plx pane, and with `--no-hotty`.

1. Hold `j`, then let go. Does focus stop where you let go, or keep going?
2. Spin the wheel hard, then stop. Does the page stop with the wheel?
3. Flick the wheel. Every tick now scrolls three lines, where some were
   dropped before. Is a flick now too far?
4. Drag the window narrower. Each width draws everything once (about
   40 ms here). Does a resize stutter?
