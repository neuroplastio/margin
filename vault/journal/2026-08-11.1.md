# 2026-08-11.1 — review a directory, not just a file

Kind: felt
Task: M3 tree-view item "Review a directory, not just a file" — `margin DIR/`
(or bare `margin`, which opens the working directory) reviews every markdown
file beneath it, with a left file-tree pane to move between documents.
Commit: (this one)

## What changed

D10 settled *that* a tree exists and what it lists; this leg is the first
build of *how it looks and behaves*, which was the felt part.

**The pane.** `margin` and `margin DIR/` walk the directory for markdown
files (hidden directories skipped — `.git` and `.margin` are tooling, and
`.margin` in particular holds thread files that are themselves markdown and
must never appear as reviewable documents) and open the first one. A left
pane lists the files: each directory that has markdown beneath it is a dimmed
header row, its files indented beneath it (D10's "a directory with no markdown
anywhere beneath it does not appear" falls out of building rows only from
markdown files' ancestors). The pane is `treeW` wide — sized to its widest
row, clamped to [16, 36] — and has its own scroll, independent of the
document's.

**Focus.** `tab` moves keyboard focus between the pane and the document
(`tree.focus`). While the pane holds focus it owns the keys: `j`/`k` move
through the files (skipping directory headers — a directory is structure, not
a focus stop), `g`/`G` first/last, `enter` or `l` opens the focused file,
`tab`/`esc`/`h` return to the document, `q` still quits. Entering the pane
lands on the open document's row. The open file carries a `▸` marker, the
focused row a `▌` cursor. A mouse click on a pane row selects and focuses it;
hovering the pane clears the document hover rather than misattributing it.

**Opening a file** (`openTreeFile`) is a fresh review of a fresh document: it
loads the new doc and its threads, re-points the store and the thread watcher
(refusing while a composer is open, the same rule reloadDoc uses), and resets
everything session-local — marks, scroll, raw view, search, selection, the
jumplist — since those name the previous document's blocks. `contentWidth()`
shrinks by the pane width so the document column is untouched, and the
composer box, its cursor, and mouse hit-testing all offset by the pane.

**Arg handling.** `cmd/margin` moved from `cobra.ExactArgs(1)` to
`cobra.MaximumNArgs(1)` (D10). Zero args still resolves to the working
directory. `margin FILE.md`, `--stdin` and `--stdout` are unchanged; the
non-interactive CLI (`export`, `comment add`, `comments wait`) still takes a
single file.

**What I chose and rejected:** left pane over right or a modal (left, beside
the existing left gutter — the eye reads pane→document and `tab` is the
settled window-switch muscle); `tab` over a `ctrl+w` family (margin has no
prefix-key vocabulary, and `tab` was unbound); `enter`/`l` to open, the dive
keys, over a dedicated `o` (reuse before invention); directory headers as
non-focusable rows over a flat list (a tree that shows its shape beats a flat
path dump, and skipping headers in j/k is two lines); resetting marks/scroll
on switch over carrying them per-document (a switched document is a fresh
review; per-doc marks are the tree-progress item's job); no search/palette/
raw while the pane holds focus (it is a modal surface like the composer — one
key returns to the document). `.md` and `.markdown` both count; hidden dirs
are skipped.

## Notes

- Thread storage needed no format change — D9 already keys thread files by
  docPath under `.margin/threads/`, so a tree review reuses the layout with
  zero migration. This is the payoff the D9 layout was built for.
- `tree.focus` is Applicable only when `m.tree != nil`, so the palette never
  offers it in a single-document review.
- The export (`Y` / `--stdout`) still covers one document — the one under
  review — which is the "one document" side of the unsettled export-coverage
  question; nothing here decides it.

## For the maintainer to look at

Whether the pane belongs on the left at all; whether `tab` is the focus key
you want (vs `ctrl+w`, or a dedicated `t`); whether directory headers that j/k
skip feel right or should be focus stops / collapsible; whether `enter`/`l`
opening the file and dropping you into the document is the right landing (vs
staying in the pane); and whether opening a file should keep the session's
marks and scroll per-document (this leg resets them).

## Demo

```bash
make build
mkdir -p /tmp/treeroot/docs
printf '# README\n\nRoot prose here.\n' > /tmp/treeroot/README.md
printf '# Spec\n\nNested prose.\n' > /tmp/treeroot/docs/spec.md
./bin/margin /tmp/treeroot
```

1. **The pane.** On open you see `README.md` (with a `▸` — the open document)
   and `docs/` dimmed with `spec.md` indented beneath it, separated from the
   document by a dim `│`. I chose left, computed-and-clamped width, dimmed dir
   headers. Does the pane read as "the file tree" at a glance? Is it too
   wide / too narrow for your screen?
2. **Focus toggle.** Press `tab` — focus moves into the pane, landing on the
   open README, which now carries `▌`. j/k move through the files (skipping
   `docs/`), `enter` (or `l`) opens the focused file, `tab`/`esc`/`h` return
   to the document. I chose `tab` because it was unbound and is the standard
   window-switch key; does it feel right, or do you want `ctrl+w` / a letter?
3. **Switching documents.** Open `spec.md`, scroll it a bit, mark a block,
   `tab` back, open `README.md`, then open `spec.md` again — note the session
   state (marks, scroll) is fresh each open. Is resetting on switch
   acceptable for now, or does the tree want per-document marks and scroll
   carried across switches? (That is also the tree-progress item's shape.)
4. **Mouse.** Click a pane row — it selects and focuses the pane. Is that the
   behaviour you expect, or should a click open immediately?
