# 2026-08-11.7 — mouse hover is throttled, not flooding

Commit: (this one)

## What changed

A pointer sweep across the document delivers one `MouseMotionMsg` per cell,
and Bubble Tea runs `Update` *and* `View` synchronously for every message —
`View` is margin's whole document layout, the expensive half of the input
path (F25). The renderer's 120fps cap only bounds when a frame is flushed; it
does nothing for the per-message `View()`. So a fast sweep queued renders
faster than the loop drained them, the input queue backed up, and keystrokes
waited for it to clear — the "hover is laggy / focus events replayed" report.

The fix throttles motion at the message source, before Update ever runs, via
`tea.WithFilter` (the hook bubbletea runs ahead of Update/View that drops a
message when the predicate returns nil):

- A `MouseMotionMsg` arriving within one frame period (`motionFramePeriod` =
  8.33ms, matching `WithFPS(120)`) of the last one processed is **dropped** —
  the renderer could never draw it.
- A report restating the cell the pointer already occupies is **dropped**
  regardless of time — nothing on screen would change.
- Everything else — clicks, wheels, keys — passes through untouched, so a
  click or scroll is never delayed behind the hover queue.

The coalescing lives in `motionThrottle` (`internal/review/review.go`), wired
into `runModel` as a program option. Tests drive it with an injected clock so
the coalescing is pinned deterministically (`TestMotionThrottle*`).

**What I chose and rejected:** throttling to one report per frame period over
a "process only when hoveredEntry changes" rule (that rule reduces redundant
state changes but still pays a full `View()` per event — bubbletea calls View
unconditionally, so the only way to save the render is to stop the message
before Update); a frame-period window over a fixed millisecond count (a fixed
count would either lag a slow renderer or throttle below what a fast one can
show; tying it to the frame period is self-scaling); position-dedup as
belt-and-braces over time-only (a terminal that repeats the last position
would otherwise re-render at frame rate while the pointer is still); and the
`tea.WithFilter` hook over touching `handleMotion` (the model-level change
cannot stop bubbletea from rendering).

## Verification

`make check` green (build, test, vet); `make test-race` green too — the
filter sits on the event loop every message travels, composer ones included,
so the race gate was run. New tests in internal/review/motion_test.go: the
first report passes, a same-frame report at a new cell is dropped, a
same-cell report is dropped even after the window, a new-cell report after
the window passes, and non-motion messages (click, wheel, resize, key) pass
through byte-identical.

## For the maintainer to look at

Whether the hover now tracks the cursor smoothly — and whether the
one-frame-of-trailing bound the throttle costs (the hover can lag the pointer
by at most ~8ms, imperceptible in practice) is acceptable. The throttle
applies to all motion, including over an open composer and in a tree review;
there is no drag feature to preserve, so nothing else consumed motion.

## Demo

```bash
make build
printf '# Doc\n\nOne paragraph.\n\nTwo paragraph.\n\nThree paragraph.\n' > /tmp/hoverlag.md
./bin/margin /tmp/hoverlag.md
```

1. **Sweep the pointer fast across the blocks.** Move the mouse in a quick
   zig-zag across the three paragraphs. Before the fix, the gutter hover `▌`
   stuttered behind the cursor and the screen froze briefly while the queue
   drained — keystrokes during the sweep fired late, "replayed". Now the
   hover should track the cursor at screen speed and `j` pressed mid-sweep
   should move focus immediately. Is the lag gone?
2. **Hover one block and hold still.** The `▌` should stay put and nothing
   should repaint while the pointer is still (the position-dedup). If your
   terminal reports motion only on actual movement this is quiet either way —
   the tell is that the freeze from step 1 is gone.
3. **Mouse during a composer.** `c` to open the composer, then sweep over it
   and back over the document. Motion still clears the hover over the pane
   and the document hover returns — does it feel as responsive as before the
   composer opened?
