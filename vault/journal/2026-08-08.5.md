# 2026-08-08.5 — RENDER-06: inline markup for paragraphs

Kind: felt
Task: RENDER-06
Commit: (this one)

## What changed

No open questions blocked the board and `vault/feedback/` was empty, so this
is the next unblocked M1 backlog item in board order.

A paragraph's `**bold**`, `` `code` ``, and `[text](url)` previously rendered
exactly as written in the source — every asterisk, backtick and bracket on
screen, which the board flagged as "a large share of the reading-comfort gap
on a real document." This leg renders the three of them for `blockPara`:

- **`parseInline`** (parse.go) is a small hand-rolled scanner — not a
  regexp, since the three forms need to interrupt plain text at arbitrary
  points — that turns a paragraph's raw markdown text into a slice of
  `inlineRun`s: plain, bold, code, or link, with the markup characters
  stripped from the run's text. An unterminated marker (a stray `` ` `` or
  `**` with no matching close) falls back to literal text rather than
  swallowing the rest of the paragraph.
- **`glueWords`** (review.go) turns those runs into the actual unbreakable
  units `wrapInline` wraps: a run's text is split on whitespace, but
  fragments with *no* whitespace between them — whether from the same run or
  a neighbouring one — glue into one word. This is what stops
  `"en**hanced**"` from picking up a space it never had in the source; naively
  treating each `inlineRun` as its own word would have introduced exactly
  that bug the first time bold landed mid-word.
- **`wrapInline`** (review.go) is `wrap`'s inline-aware sibling: same
  word-wrap algorithm, but each `glueWord`'s fragments are rendered with
  `fragStyle` before being joined, so the output lines are already
  ANSI-styled rather than plain text for the caller to style uniformly.
  `render()`'s shared block-rendering loop gained one `preStyled` bool so it
  skips re-`Render`ing a line that already carries its own styling, instead
  of nesting one style inside another.
- Code spans and links always render in their own fixed colour regardless of
  review state (`codeStyle`, `linkStyle`); bold builds on top of `body`
  (`body.Bold(true)`) so reviewed prose still dims even where it is
  emphasised — the same "the rule marks it, the text stays normal" reasoning
  RENDER-04 applied to block quotes, applied here to "code and links are
  markup, not prose."

**Deliberately scoped to `blockPara` only.** List items and block quotes are
prose too and go through the same reading experience, but they wrap via
`wrapList`/`wrapQuote`, not `wrap`, and extending them is a small, mechanical
follow-up now that `wrapInline`/`glueWords` exist as the reusable primitive —
not a reason to make this leg bigger. Headings are excluded on purpose:
`headingStyle` already claims the whole heading's colour and weight for
level, and bold inside a coloured, already-bold level-1 heading is a
separate visual question this leg does not answer.

**No italics, no nesting, no reference-style links.** `parseInline`'s doc
comment says so explicitly — those are real gaps, not oversights, and
widening the recognised forms is its own felt decision.

`block.text` itself is untouched — still the full raw markdown, `**` and all
— so `anchorFor`'s hashing, `stampID`, and export's `quoteBlock` (which
reconstructs markdown for an agent to read) are all unaffected. Only the
interactive renderer's path to `wrap` changed.

## Choices made without asking, and why

- **Link rendering drops the URL from the screen**, showing only the link
  text, underlined, in a fixed colour (111). The URL is not lost — it is
  still in `block.text` and reaches an agent unchanged via export — this is a
  render-only choice. Rejected: appending a dimmed `(url)` after the text,
  which felt like it would fight the reading measure on anything but a short
  URL; rejected: OSC 8 terminal hyperlinks, which is a real option but a
  bigger, separate decision about terminal-emulator dependence.
- **Code and link colour is fixed, not review-state-dependent**, while bold
  dims along with the rest of reviewed prose. Reasoning: a code span or a
  link is closer to markup than to prose — RENDER-04 made the same call for a
  block quote's rule staying `dimStyle` regardless of the quote's own review
  state.
- **`codeStyle` (216, warm) and `linkStyle` (111, cyan, underlined)** are new
  colours, chosen to sit apart from every colour already in use
  (244/252/114/179/212/209/240/109/183/245) rather than reusing one with a
  different existing meaning.
