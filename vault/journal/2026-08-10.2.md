## What changed

The feedback's final item: "Dive/undive should also bind to `enter`/`esc`:
`enter` = dive, `esc` = undive, in addition to the existing `l`/`h` bindings."

Until now `enter` was dead at document level (nothing in the keymap, nothing in
`handleKey`) and `esc` only cancelled a visual selection. The keymap
(`internal/review/command.go`) now binds `enter` → `move.dive` and `esc` →
`move.surface` — straight aliases of `l`/`right` and `h`/`left`, the same
command ids, so the palette, the raw-mode guards and the existing tests all see
the same behaviour no matter which key fired.

The interplay that had to be checked:

- **esc cancels a visual selection first.** The `handleKey` visual+esc branch
  runs before the keymap lookup, so `V` … `esc` still ends the selection, never
  "surfaces" — vim's rule, and the one thing esc already owned at document
  level. Only outside visual mode does esc become the undive key.
- **A dive in visual mode stays inert.** `move.dive`'s `Run` → `dive()` returns
  early while `m.visual`, so `enter` mid-selection does not yank focus onto a
  comment.
- **On a code block or the frontmatter, enter/esc scroll horizontally**, exactly
  as `l`/`h` already do — the alias means a code block is scrolled right by
  `enter` and left by `esc`, not dived (code blocks and the frontmatter are the
  two kinds `l` reserves for horizontal scroll; they never line-dive).
- **Raw mode is unchanged**: both `Run`s return early on `m.raw`, and raw mode
  cancels dives on entry anyway.
- **Composer untouched**: while a composer is open every key routes to the child
  (the `ctrl+\` carve-out aside), so `esc` in nvim keeps its dismissal meaning.
  Pending `g`/count state is unaffected — `esc` clears a half-typed count
  through the same "any command clears it" path every key already took.

**What I chose and rejected:** straight aliases over a pair of dedicated
dive-only commands. The feedback says "in addition to the existing `l`/`h`
bindings", which reads as "these keys do what `l`/`h` do"; one command id, one
behaviour, zero divergence between the two key pairs, and nothing new for the
palette or the tests to reconcile. The cost of the alias is that `enter`/`esc`
on a code block scroll it horizontally (where a dive-only command would be
inert) — flagged in the demo recipe so a correction is cheap. Rejected adding
`enter`/`esc` only inside a dive (i.e. `esc` surfaces only when there is
something to surface, and `enter` only dives when there is something to dive
into) as a noisier variant with the same net effect, since both commands are
already quiet no-ops at the document level.

## Demo

```bash
make build && ./bin/margin testdata/sample.md
```

1. `c` on a block, type a word, `esc esc` — a thread row appears under it. Now
   `l` onto it if needed, then `enter` — focus steps into the first comment;
   `j` walks the comments; `esc` steps back out to the thread row; `esc` again
   does nothing (no dive left). The whole dive flow is now reachable with
   `enter`/`j`/`esc` and never touches the `l`/`h` keys.
2. `g`, then `enter` twice on a code block — the block scrolls right once per
   press (the `l` alias), and `esc` scrolls it back left. This is the one place
   `enter`/`esc` are not "dive/undive" but horizontal scroll.
3. `V`, `j`, `esc` — the selection cancels exactly as before; `esc` did not
   surface or move focus. `enter` mid-selection stays inert.
4. `esc` inside a live composer still closes nvim exactly as before.

Questions for the maintainer: is `enter` scrolling a code block right (the
`l`-alias behaviour) acceptable, or should `enter`/`esc` be inert on code
blocks and the frontmatter, leaving horizontal scroll to `l`/`h` alone? And
does `esc`-after-`esc` (surfacing, then a quiet no-op) feel right, or should a
second `esc` do something (the composer's double-`esc` never applies here —
the composer owns its own esc)?
