## What changed

A comment body used to be laid out with plain `wrap(c.body, w-6)`
(`appendComments`, review.go), which feeds the whole string through
`strings.Fields` — collapsing every newline into a space and re-flowing, so a
multi-line or multi-paragraph comment read as one run-on paragraph with no
way to show structure. Bodies are now laid out by a new `wrapComment`
(review.go):

- **Every source line stays its own rendered line.** A comment is typed in a
  real textarea, so a line break the reviewer pressed is a break they meant —
  `wrapComment` splits the body on `\n` and wraps each line to the measure
  through `wrapInline`. This deliberately rejects markdown's
  fold-soft-breaks semantics: the fold is *exactly* the "reads as one run-on
  paragraph" complaint this leg exists to fix.
- **A blank source line becomes a blank rendered line** — a paragraph break,
  so a two-paragraph comment reads as two paragraphs.
- **Inline markup renders**, via `wrapInline` — the RENDER-06 treatment the
  document's paragraphs already have: `**bold**`, `` `code` ``,
  `[links](url)` reach the screen styled, never as literal characters.
- Applied to all four places a body shows: a posted comment, an unsaved edit
  draft, a deleted comment's dimmed body, and the new-comment draft preview
  in an expanded thread — the feedback's "does the draft follow the same
  rendering" answered yes.
- **The collapsed thread's summary strips the markup too.** `t.summary`
  (document.go) truncated the raw first line, so a comment that opened with
  `**bold**` read `**bold**` in the gutter while the expanded thread styled
  it. A new `plainMarkdown` helper (the three inline forms stripped, text
  kept) feeds the excerpt, drafts included.

**What I chose and rejected:** the middle of the feedback's three scope
options — line breaks *and* inline markup, but no fenced blocks (a code block
inside a comment needs the chroma + horizontal-scroll machinery and is rare;
defer until feedback asks). Hard line breaks over markdown's soft-break fold
(see above). Inline markup in the collapsed summary over leaving it raw (the
same complaint in miniature). Focused comments build their style onto the
focus colour per word — bold renders bold+focus, code/link keep their own
colours, exactly `fragStyle`'s established rule for reviewed prose.
Rejected: a composer-side hint that markdown is understood (touches the
composer and F2/F22 territory; the reviewer learns the format from the
render), and touching `margin export` — the exported thread file is already
plain markdown, so it was always right.

## Notes

lipgloss renders an underlined link per-rune (`\x1b[4;38;5;111;4mr\x1b[m…` one
escape pair per character). Pre-existing — links already render this way in
document paragraphs — so `wrapComment` just inherits it; a test that
replaces ANSI with a *space* sees "r u n b o o k" and must replace with
nothing instead.

## For the maintainer to look at

Whether styled markup in a thread reads as an improvement or as noise against
the document, and whether a deleted comment dimming only its plain text
(fragStyle keeps code/links coloured) is the right call.

## Demo

```bash
make build
./bin/margin testdata/sample.md
# open a thread (j to the thread row, l/enter to expand, or c on a block)
# edit/post a comment that uses the format, e.g. under "## Options considered":
#   First paragraph — the retry budget is shared, see **the note**.
#   (blank line)
#   Second paragraph with `SessionStore` and a [link](https://example.com/x).
# submit with ctrl+s, then read it in the thread, and quit and reopen
# (q) to see the collapsed gutter line.
```

Judge:
1. **Line structure** — does a multi-line comment now hold its shape (no more
   run-on paragraph)? Is each source line staying its own line right, or did
   you expect markdown's fold (single newlines collapsing into spaces)?
2. **Inline markup** — do **bold**/`code`/links in a comment read like the
   document's own, or do they fight the prose? Should a comment body instead
   stay plain text with only line breaks preserved?
3. **Focused comment** — bold renders bold in the focus colour; is that
   legible, or should bold switch to the focus colour entirely?
4. **Deleted comment** — only its plain text dims; `code`/links stay bright
   (the established fragStyle rule). Right, or should a deleted comment dim
   everything?
5. **Collapsed gutter** — a comment opening with `**bold**` reads `bold` on
   the collapsed line; confirm no literal `**` anywhere.
6. **Scope** — no fenced code blocks in comments. A gap worth a leg, or fine?

(What I chose: every source line its own rendered line + paragraph breaks +
inline markup, summary strips markup too. What I rejected: folding soft
breaks, fenced code blocks, a composer-side markdown hint, touching export.)
