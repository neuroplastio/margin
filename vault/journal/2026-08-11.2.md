# 2026-08-11.2 — cross-document link navigation

Kind: felt
Task: First slice of M3 tree-view item "Navigation between documents, and a
cross-document comment inbox" — `ctrl+]` on a link that names another markdown
file in a directory review opens that file, instead of reporting "links here
point outside this document". The comment inbox remains a separate board item.
Commit: (this one)

## What changed

`jump.follow` (`ctrl+]`) had only an in-document half: a `#fragment` href
jumped to the heading it named, and every other href — a relative file, an
external URL — was reported as outside the document. The in-document half
stays untouched. The new cross-document half lives in `followDoc` (jump.go)
and only exists in a tree review (D10): a single-document review
(`margin FILE.md`) has no tree to switch into, so it keeps the outside report
exactly as before.

- **The path resolves markdown's way.** An href like `docs/spec.md` resolves
  against the current document's *own* directory (the file containing the
  link), and one starting with `/` resolves against the review root — the two
  spellings an agent's links actually use. It is then looked up in the tree,
  so only a file the review can open is ever opened: a file outside the root
  (a `../` that escapes), a non-markdown file, an absolute URL (`://`) and a
  `mailto:` all fall through to the outside-document report.
- **Switching is `openTreeFile`, the pane's own open.** A followed link
  switches documents exactly as `enter` in the pane does: doc, threads, store
  and watcher re-point, every session-local reset (marks, scroll, raw, search,
  selection), the tree's open marker moves to the followed file, focus returns
  to the document. A follow and a pane-open can never behave differently.
- **A `#fragment` lands on the heading it names**, centred like an in-document
  follow, and the new document's jumplist restarts *at the landing* (so ctrl+o
  from a later teleport returns to the followed heading). No fragment, and the
  file opens at its top with openTreeFile's own `opened <rel> — N blocks`
  status. A fragment naming no heading is surfaced: `opened <rel> — no heading
  matches #x`.
- **A link back at the document under review** (`README.md#top` from within
  README) resolves its fragment without switching — no reopen, no reset.
- **First-link-wins still holds**: a block with several links follows the
  first, whatever kind it is, the rule the in-document follow already settled.

**What I chose and rejected:** resolving against the containing file's
directory over the review root (markdown's own rule — a link is relative to
the file it appears in; root-relative `/` is the exception the common spelling
earns); reusing `openTreeFile` over a bespoke switch (one code path for "open
a file", so a follow can never diverge from a pane open); landing centred on a
fragment (the same jump as an in-document follow) with the jumplist seeded at
the landing (the old doc's positions no longer name anything, and
openTreeFile's seed of entry 0 would be a lie); scoping to tree reviews
(a single-document review is one document by D10 — following out of it would
make it a tree review by accident); skipping URL-decoding (`%20` et al.) for
now — a link with an encoded space is not followed, reported as outside, and
that is honest rather than half-handled.

## Notes

- No on-disk format, anchor or thread change — this is pure navigation. The
  fragment resolved after a switch uses the same GitHub-style slug index the
  in-document follow already uses; the new document's slugs are rebuilt by
  openTreeFile's own rebuild.
- The `followLink` loop keeps its semantics: the first `#`-href follows
  in-document; a non-`#` href tries `followDoc` first and only then falls
  through. So a block with `[web](https://x) [local](#y)` still follows the
  in-document link, and a block whose first link is cross-document opens that
  document — first-link-wins, unchanged.
- The command palette row for `jump.follow` (Applicable: "a link exists") now
  means a cross-document link too; the description was widened to "Follow the
  link in the focused block".

## For the maintainer to look at

Whether following a relative link should switch documents at all (vs staying
put and reporting where it points); whether a switched-to document should reset
its session the way a pane open does (it does; per-document marks/scroll is the
tree-progress item's shape); whether root-relative `/x` belongs alongside
relative paths; and whether single-document reviews should eventually follow
too (they deliberately do not yet — see D10).

## Demo

```bash
make build
mkdir -p /tmp/linktree/docs
printf '# Home\n\nRead the [spec](docs/spec.md) and its [setup](docs/spec.md#setup).\n' > /tmp/linktree/README.md
printf '# Spec\n\n## Setup\n\nThe steps.\n' > /tmp/linktree/docs/spec.md
./bin/margin /tmp/linktree
```

1. **Follow a cross-document link:** with focus on the "Read the spec…"
   paragraph, press `ctrl+]` — the review switches to `docs/spec.md` (the
   pane's `▸` moves with it, the status line says `opened docs/spec.md`), and
   focus lands at the top of the new document. I chose to switch the whole
   review, the same action `enter` in the pane performs, over reporting where
   the link points. Is switching what you expected `ctrl+]` to do here?
2. **Follow onto a fragment:** move focus back to README (`tab`, `k`, `enter`)
   and `ctrl+]` again — it follows the *first* link again. To reach the
   `#setup` link, put it first, or use `l`-style editing to reorder; instead,
   press `ctrl+o` now: the new document's jumplist is seeded at the landing
   (it restarts on a switch), so ctrl+o reports "at the oldest jump" rather
   than returning to README. Is restarting the jumplist on a document switch
   right, or should ctrl+o be able to walk back across documents?
3. **The other spellings:** a link `[/docs/spec.md]` (root-relative) follows
   the same; a link to `docs/nope.md` or `https://…` reports `links here point
   outside this document`. Are root-relative links worth keeping followed, or
   should only document-relative ones count?
4. **Single-document reviews:** `./bin/margin /tmp/linktree/README.md` (a file,
   not a dir) — `ctrl+]` on the same link reports `links here point outside
   this document`. A single-document review stays one document (D10); is that
   the call you want, or should it follow too?
