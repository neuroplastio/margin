# 2026-08-07.5 — PARSE-03: recognise leading frontmatter

Kind: mech (from maintainer feedback — `frontmatter-rendering`)
Task: PARSE-03
Commit: (this one)

## What changed

The maintainer's feedback reproduced a real bug: `goldmark.New()` has no
frontmatter extension, so a document opening with

```
---
name: retry-policy
...
---
```

misparses badly. The opening `---` is a thematic break (silently dropped);
the **closing** `---` is read as a setext heading underline for the YAML
above it, so the whole frontmatter block collapses onto one line and becomes
the document's first heading — commentable, markable, counted toward review
progress, and leaking into the export's `Section:` line as the thing an
agent would use to locate a comment. Recorded as **F10** in findings.md,
since it is not actually frontmatter-specific — any paragraph immediately
followed by a lone `---` gets the same treatment, though only the
leading case is fixed here.

**The fix.** `frontmatterExtent` (parse.go) scans for a leading `---`…`---`/
`...` fence before goldmark ever parses the source. When found, `parseDoc`
emits one `blockFrontmatter` block for that whole range and skips whatever
goldmark node(s) fall inside it — the dropped thematic break, the setext
heading — rather than surfacing them. `blockFrontmatter` is a new
`blockKind`, added *after* the existing ones so `anchorFor`'s hash (which
folds in `b.kind`) does not shift for every already-parsed block in a
document with no frontmatter at all.

`commentable()` and `markable()` already work by explicit kind allow-list, so
frontmatter is excluded from both — and therefore from review progress and
from the export's counted/quoted items — with no changes needed there.
`rebuild()` now skips `blockFrontmatter` when flattening `m.doc` into
`m.entries`, so it never reaches the render switch at all; left unhandled it
would have fallen into the `default` case, which assumes a thread entry and
would have misbehaved on a bare block with a nil thread.

**What this deliberately does not do.** How frontmatter should *look* is a
felt decision — the feedback offered three real candidates (hidden until
asked for, a dimmed key/value block, a collapsed line that expands) and
explicitly did not pick one. Rendering it as nothing is a default, not an
answer to that question, so it is not being reported as settled. Filed as
**RENDER-07** on the board for a felt leg once the review gate clears.

Also out of scope: a `---` used as a horizontal rule anywhere other than the
very start of the document has the same setext-heading misparse and is not
touched by this fix. Noted in F10 for whoever hits it next (plausibly
RENDER-04, block quotes, or a table with a `---` separator row nearby).

## Notes

`frontmatterExtent` requires the opening line to be exactly `---` (trimmed)
and the *file's* first line — no blank line or anything else before it. That
matches how Jekyll/Hugo/goldmark-meta all require it, and keeps the fix
narrow enough to reason about. An unterminated opening fence (`---` with no
matching close anywhere in the document) is treated as *not* frontmatter,
so it falls back to today's existing (imperfect but unchanged) handling
rather than swallowing the rest of the file hunting for a closer that
doesn't exist.
