# 2026-08-10.18 — hover lights on a bare pointer move

Kind: felt
Task: (feedback fix) the gutter hover `▌` only appeared while the left mouse
button was held — the view requested cell-motion mouse tracking, so the
terminal never reported a button-less move. Drains
`vault/feedback/2026-08-10-hover-without-lmb.md`; the file is deleted.
Commit: (this one)

## What changed

One line in `View()` (`internal/review/review.go`): the mouse mode is now
`tea.MouseModeAllMotion` (1003) instead of `tea.MouseModeCellMotion` (1002).

That is the whole bug. The handler chain was already right — `Update` routes
`tea.MouseMotionMsg` into `handleMotion`, which hit-tests and sets
`hoveredEntry`, and `gutter` renders the dim `▌` — but the terminal had never
been asked to report motion with no button held. Mode 1002 (cell-motion) only
fires on a *drag*: every event carries a button, which is exactly the "works
while I hold the left button" symptom. Mode 1003 (any-event) reports every
pointer move, button or not. The decode is xterm's standard SGR mode byte and
needs no protocol negotiation on margin's side.

No other mouse path changes: wheel events still arrive as press/release pairs
under 1003 (`handleWheel` branches on `MouseWheelUp/Down`, unaffected), and
`handleMotion` already clears `hoveredEntry` over the composer pane and over
non-document rows, so all-motion tracking does not light stray gutter bars.

**What I chose and rejected:** the mode flip and nothing else. I rejected a
host-side "synthesise a hover from drag events" workaround (the same visual
effect, but it would leave bare hovers dead and re-introduce the bug on the
next drag); I also rejected moving the decision into a flag — hover is the
only behaviour 1003 costs anything for, and the cost is just the terminal's
normal stream of motion reports, which any terminal hover feature pays.

## Notes

No durable finding: this is bubbletea v2's documented contract
(`UPGRADE_GUIDE_V2.md` maps `tea.WithMouseCellMotion()` → `MouseModeCellMotion`
and `tea.WithMouseAllMotion()` → `MouseModeAllMotion`; the renderer emits
`ansi.SetModeMouseButtonEvent` vs `ansi.SetModeMouseAnyEvent`). The trap was
reading the old flag as "mouse support is on" when it in fact meant "motion
while dragging is on".
