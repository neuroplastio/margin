## What changed

The maintainer asked that the composer exit on `esc` from normal mode instead
of vim's `:`-led gestures, with a specific double-esc/single-esc split:

- **Creating a new comment: double `esc`.** A new comment opens in insert mode,
  so the first `esc` leaves insert mode and the second is the exit itself. This
  falls out of the mapping — nothing in nvim or the host has to count presses.
- **Editing an existing comment: single `esc`.** An edit opens in normal mode
  (the settled insert-iff-empty rule, interaction.md), so the first `esc` is
  pressed from normal mode and exits immediately.

The implementation is one nvim mapping swap in `composerInit`: `map('n',
'<Esc><Esc>', draft)` becomes `map('n', '<Esc>', draft)`. The old mapping was
the reason a lone `esc` in normal mode waited out `timeoutlen` before resolving
to nothing; an exact `<Esc>` mapping fires immediately, so there is no wait and
no "the two escs must land within 250ms" sensitivity. The old `<Esc><Esc>`
effectively needed *three* presses for a new comment (one to leave insert mode,
two for the mapping) — the new one needs two, which is what the feedback named.

`esc` keeps a draft, the settled default (dismissal table, interaction.md);
discard is still `:q!` / `SPC c k`, and `:q` / `SPC c d` / `ZZ` / `<C-s>` /
`<C-enter>` are all untouched. The `cnoreabbrev`-based `:q` family stays.

**Blur is unchanged and still one path (F7).** `blur` sends `\x1b:MarginDraft\r`.
In insert or visual mode the leading `\x1b` leaves the mode and the ex command
runs; in normal mode the `\x1b` is now itself the exit, since `<Esc>` is mapped
to draft — same `cquit 2`, same draft outcome. No new code path.

The footer hint now distinguishes the two gestures: `esc esc keep` under a new
comment, `esc keep` under an edit (`escHint`, review.go).

**Not addressed here:** an unchanged edit exited via `esc` still marks an
"unsaved draft" — that is the feedback file's own fifth item, next in the queue.
I noted it in the demo recipe rather than fixing it in this leg.

## Demo

```bash
make build && ./bin/margin testdata/sample.md
```

1. `c` on a block — the composer opens in insert mode (footer reads
   `new comment · esc esc keep`). Type a half-thought, press `esc` once — you
   are in normal mode, the pane stays open, cursor shape flips to block.
   Press `esc` again — the pane closes; status reads `draft kept on ^…`.
2. `c`, type nothing, `esc`, `esc` — closes with `closed`.
3. `e` on an existing comment — the composer opens in normal mode (footer reads
   `editing comment · esc keep`). Press `esc` once — it closes immediately.
4. `e` again, make a change, `esc` — closes with `edit kept unsaved`.

Questions for the maintainer: is single-`esc`-exits-an-edit the right weight,
or do you find yourself pressing `esc` expecting to cancel something first? For
a new comment, does double-`esc` (leave insert, then exit) read as "double
esc", or should the first press from insert also be required to exit? Is the
`esc esc keep` vs `esc keep` footer split informative or noise? And note the
known wart the feedback's own fifth item names: exiting an edit with no changes
still creates an "unsaved draft" — that is the next leg. (What I chose: `<Esc>`
mapped to draft in normal mode only, new-comment double-esc falling out of
insert-mode entry. What I rejected: keeping `<Esc><Esc>`, and any host-side
esc handling — the pane keeps sole ownership of input.)
