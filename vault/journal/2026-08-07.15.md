## What changed

`vault/feedback/` held nothing but its README and `vault/questions/` had no
open question, so per CLAUDE.md's pick order the leg fell through to the
board. The board's `Awaiting review:` is still **PARSE-02**, so only `[mech]`

RENDER-0x heading/inline/list/table/quote/frontmatter items), so there was no
unblocked mechanical M1 item to take; the next unblocked mechanical item in
board order was M2's **THREAD-01**, now pickable because the previous leg
(2026-08-07.14) folded Q-0002's answer into **D11**.

Read D11 before touching anything: resolution is a single boolean, settable
and clearable by either the reviewer or an agent, with no separate
`addressed`/`resolved` split and no record of who last flipped it.

**`thread` (`internal/review/document.go`)** gains `resolved bool`, next to
the existing `orphaned bool`. No dedicated setter — D11's "either party can
flip it" is exactly what a plain field already gives you; a setter would only
make sense if something needed to react to the transition, and nothing does
yet (that reaction, if any, is THREAD-02's territory).

**`marshalThread`/`parseThreadFile` (`internal/review/store.go`)** carry it
through the frontmatter as `resolved: true`, written only when true — an
unresolved thread's file is byte-for-byte what it was before this leg, so
every thread file already on disk keeps parsing the same way. Parsing reads
the field case-insensitively and treats anything other than a literal `true`
(missing, `false`, garbage) as unresolved — there is no third state to get
wrong. Pinned with round-trip tests for resolved-true, resolved-omitted,
resolved-explicit-false, and resolved with mixed case.

**`reloadThreads` (`internal/review/watch.go`)** now merges `resolved` the
same way it already merges an appended reply, so an agent that resolves a
thread by writing `resolved: true` straight to the file — no different from
appending a reply, which STORE-03 already handles this way — is noticed on
the next filesystem event without restarting margin.

Also fixed two comments left stale by the previous leg's D10/D11 fold that
this leg's diff sat next to: `store.go`'s `threadsDir` comment said "a future
tree review (Q-0001)" (the file no longer exists — repointed to D10), and a
`palette_test.go` comment said "blocked on Q-0002" for the absence of a
delete command (repointed to "THREAD-03, unbuilt", which is the actual reason
now).

## What this deliberately does not do

No command, no keybinding, no rendering, no export filtering. `resolved` is
reachable only by constructing or loading a `thread` directly — nothing in
`command.go`'s registry sets or reads it, and no renderer brightens, dims, or
labels a resolved thread differently from an unresolved one. That is
`THREAD-02` (what resolving looks like — key, dim/collapse/disappear,
reachable from collapsed vs. expanded) and stays exactly as felt and exactly
as unbuilt as it was before this leg. `EXPORT-05` (excluding resolved threads
from the export) is now genuinely unblocked — the field it needs exists and
round-trips — but export.go itself is untouched here; that is its own leg.

I checked the felt-half question CLAUDE.md asks before closing a leg like
this: does something now render differently, or not render at all? No new
block kind, message, or mode was introduced, and no renderer gained (or
needed) a branch for `resolved` — the field is inert data until a felt leg
gives it a rendering. So this stays a clean mechanical leg with no accidental
felt half.
