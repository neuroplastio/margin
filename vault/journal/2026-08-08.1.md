## What changed

`vault/feedback/` held four items from the first real review of a real
document. Feedback preempts the board, and the oldest — `2026-08-08-1-
rendering-bugs.md` — says explicitly to take it before the three felt items
filed alongside it, so it is this leg. It names three defects; the third
(inline frame scrolling the terminal on load) was already fixed and answered
in an earlier leg (2026-08-07's alternate-screen work) — the file just kept
the diagnosis for the record. The first two were root-caused but not yet
fixed, each with an exact repro:

**Defect 1 — tables collapsed to one wrapped paragraph.** `goldmark.New()`
(`parse.go`) was constructed with no extensions, and GFM tables are not part
of CommonMark. A table never became an `*ast.Table` — it parsed as an
`*ast.Paragraph`, and `collapse()` did to it exactly what a paragraph's line
breaks are supposed to get: joined into one line and wrapped to the measure.
Fixed with `goldmark.New(goldmark.WithExtensions(extension.GFM))`. GFM also
buys strikethrough, autolinks and task lists — all inline-only, so they change
what a paragraph's text contains, never what kind of block it is, and cost
nothing extra to enable alongside the table fix. Verified against
`testdata/sample.md`'s own table: it now parses as one `blockRaw` with all 6
source lines intact, not a paragraph. Making it *look* like a table is
RENDER-03, still open and still separate.

**Defect 2 — long list items truncated instead of wrapped.** `blockRaw`'s
"show every line verbatim, never re-wrap" rule is correct for a code fence or
a table, where layout is content, and wrong for a list, whose items are
prose. The rule had been applied to the whole bucket on the strength of a
comment that only justified two of its four members. Split lists into their
own kind, `blockList` (`document.go`), with their own items
(`listItemsFor`, `parse.go`) and their own layout (`wrapList`, `review.go`):

- `listItemsFor` splits a list's raw source on `listItemRE` (indentation,
  marker, text) rather than walking goldmark's AST. A nested item is just a
  matching line with more leading whitespace, so nesting depth falls out of
  the indentation for free — a deeper item gets a wider prefix and, at render
  time, a deeper hanging indent, with no separate depth field to keep in
  sync. A non-matching line folds into the current item's text like a
  paragraph's line breaks do; a blank line (loose-list separator) is skipped.
- `wrapList` wraps each item's text independently at `wrap()`, minus its
  prefix's width, and indents every continuation line to that same width —
  so a long item's overflow lines up under its own text, not under the next
  item's marker.
- Export's `quoteBlock` (`export.go`) still renders a `blockList` from its
  verbatim `lines`, same as `blockRaw` always did — the export-side defect
  this replaced (`TestExportPreservesListStructure`) was already fixed
  earlier and untouched here; only the kind name in that test changed.
- `blockList` was added as a new kind *after* `blockFrontmatter`, per the
  existing convention (see that kind's own comment) — a block's kind ordinal
  feeds `anchorFor`'s hash for anything not yet stamped, so appending rather
  than inserting keeps every other kind's anchors unchanged.

Verified against `testdata/sample.md`'s numbered and bulleted lists at a
40-column measure: every item now wraps across as many lines as it needs,
each within the measure, with continuation text hanging under the item's
own prose. See `vault/knowledge/findings.md` **F11** (the extension gap) and
**F12** (the bucket-was-too-broad lesson) for the durable versions of both.

## What this deliberately does not do

Still verbatim, unchanged: code fences, block quotes, and now tables too —
RENDER-02, RENDER-03 and RENDER-04 are the felt legs for how those should
actually look. This leg only stops one class of content (tables) from being
silently misparsed, and stops another (lists) from losing words off the edge
of the screen; neither is a decision about appearance.

I did not reach for task-list checkbox rendering (`- [ ]` → `☐`/`☑`) even
though GFM's tasklist extension is now enabled — the extension only affects
parsing, and rendering a checkbox specially is exactly the kind of felt call
this leg is not making. A task-list item today reads as `- [ ] text`, same
prefix-plus-prose treatment as any other bullet.
