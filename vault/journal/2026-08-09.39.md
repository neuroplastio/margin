## What changed

The feedback: entering edit mode on an existing comment should place the cursor
at the end of the comment text. It did not — `e` on a posted comment opened the
composer with the cursor at `{1,0}`, the first character, so an `a` append
landed after the opening word and `A` was the only append that behaved.

The fix is one branch in the `VimEnter` callback in `composerInit`
(`internal/review/composer.go`): a non-empty buffer no longer sets the cursor to
`{1,0}` but to the end of the buffer — `nvim_win_set_cursor(0, {last, #buf[last]})`,
one column past the last byte, which nvim clamps onto the last character (F22).
That is exactly where normal mode wants it: `a` appends after the text, `A` is
redundant but harmless, `$`/`0` still move.

One change covers both callers of the non-empty branch. The same branch opens a
**resumed draft** (draftAnchor's half-written text), and interaction.md's
settled contract already says "Resuming a draft puts the cursor **after** the
existing text, not before it" — which the code quietly violated until now by
putting the cursor at `{1,0}` for every non-empty buffer. So this leg both lands
the feedback's edit request *and* honours the settled draft rule; the empty and
line-ref-prefix branches are untouched, so a new comment still `startinsert`s
and a bare `L12-18: ` still opens with `startinsert!` past the prefix.

**What I chose and rejected:** chose end-of-buffer in normal mode over
`startinsert!` for edits — an edit wants normal mode (the settled insert-iff-
empty rule, interaction.md), and the feedback asks only where the cursor sits,
not that typing begin immediately. Chose the exact branch in composerInit over a
host-side "this is an edit" flag: the seed already tells the Lua everything it
needs, and the edit and resumed-draft paths share the branch deliberately.
