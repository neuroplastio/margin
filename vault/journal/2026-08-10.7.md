## What changed

Q-0003 asked what `margin comments wait --since <last_known_id>` names. The
maintainer answered with neither option on the table — not the comment's
timestamp (A) and not a new `id:` field in the thread file (B) — but a **new
design**: an event log, stored separately from thread files in the root
`.margin` directory, where every event (comment posted, deleted, restored,
etc.) carries a short time-based id (ULID-style). Listeners fsnotify or tail
it; the wait command reads from it. Recorded as **D13** in
`vault/knowledge/decisions.md`; Q-0003 is closed and its file deleted. Thread
files are untouched and gain no id field.

The smallest first slice of that log, built this leg:

- **`internal/review/events.go`** — the log's writer and reader:
  - `.margin/events.log`, append-only, one event per line, seven
    tab-separated fields: `id at type doc anchor author comment`.
  - **Ids are hand-rolled ULIDs** (26-char Crockford base32 minus I/L/O/U):
    48 bits of millisecond time, 80 bits of `crypto/rand` entropy, encoded
    bit-by-bit so lexicographic string order is chronological. I rejected
    pulling in `oklog/ulid/v2` — the whole encoder/decoder is ~60 lines, it is
    pinned by hand-derived known-value tests, and a format this central is
    cheaper to own than to vendor.
  - `at` is RFC3339Nano UTC (the thread files' own timestamp format), and the
    event's `comment` field is the 0-based index of the comment inside its
    thread (`-` for thread-level events) — comments have no id of their own,
    so the *event* id is the cursor and the index is the locator.
  - Writes are best-effort *after* the thread write they announce: the thread
    file is the source of truth (D5), the log is the notice, and a failed
    notice must not fail — or block — the words. Recorded as part of D13.
  - `readEvents` surfaces a malformed completed line (surface, don't drop) but
    skips a final unterminated line: every write ends in `\n`, so an
    unterminated tail is an append still in flight.
- **Wired into every thread mutation.** The TUI posts/edits a comment
  (`dismiss`), toggles resolve, deletes/restores a comment or thread — each
  emits its event after `store.save`, surfacing an append failure in the
  status line; `margin comment add` (cli.go) emits `comment.posted` the same
  way, best-effort so an event-log failure can never make an agent re-post.
  Ephemeral stdin reviews (`margin -`) emit nothing — they persist nothing.

**What I chose and rejected:** a single `.margin/events.log` file (so "tail
it" means one file) over a `.margin/events/` directory; ULID-style ids over
plain timestamps (they sort by time yet stay collision-safe and short); the
event id as the `--since` cursor with file position resolving same-millisecond
ties (recorded in D13 so the wait leg cannot get it wrong); explicit
per-mutation-site emission over diffing in `store.save` (the save only sees
the whole thread, it cannot tell a post from a delete); `-` for thread-level
comment indexes over omitting the field (always seven fields, one shape).

## Verification

`make check` green (build, test, vet); `make test-race` green (the new
dismiss-path test spawns a real nvim).

Tests in `internal/review/events_test.go` (plus one in review_test.go):

- `TestEncodeULIDKnownValues` — encoder and decoder pinned against
  hand-derived values (all-zero → 26 `0`s; timestamp 1ms → `…004…`; all-ones →
  25 `Z`s + `W`), plus lowercase tolerance. This caught a real bug: the first
  `ulidDec` mapped letters straight through the alphabet (`T`→29), which the
  all-digit known values could not see — only the letter-heavy ones did.
- `TestNewEventIDIsATimeOrderedULID` — 26 chars, valid alphabet, embeds a
  current timestamp, unique, and 200 ids sort lexicographically in
  non-decreasing time.
- `TestEventLineShape` / `TestEventLineThreadLevel` — exact on-disk lines
  round-trip, thread-level events carry `-`.
- `TestMarshalEventSanitizesFreeFormFields` — a `--author` carrying a tab or
  newline cannot split the line.
- `TestAppendEventAndReadEventsRoundTrip` — written events come back in order
  with ids/timestamps filled in.
- `TestReadEventsSkipsTornTail` / `TestReadEventsMissingLogIsEmpty` /
  `TestParseEventMalformed` — the reader contract, both sides.
- `TestThreadStoreEmitWritesEvent` / `TestThreadStoreEmitNilSafe` — emit fills
  in the doc path; a nil store writes nothing.
- `TestAddCommentWritesEvent` — two `comment add`s produce two events with
  indexes 0 and 1.
- `TestSubmitEmitsAnEvent` (review_test.go) — a TUI submit with a store set
  lands one `comment.posted` event carrying the thread's anchor.

## For the maintainer to look at

The on-disk shape is the point of this leg and it is pinned in D13. Judging it
is: do the lines read right, is `.margin/events.log` the file you had in mind,
and are the eight event types the right set? Nothing waits on it — the wait
command is the next leg and reads whatever D13 says.

## Demo

```bash
make build
./bin/margin testdata/sample.md
```

1. `c` on a block, type a comment, `ctrl+enter` — then `R` to resolve the
   thread, `D` twice on a comment to delete and restore it, `q` to quit.
2. Then, from the repo root (where `resolveReviewRoot` found `.git`):
   `cat .margin/events.log` — one line per action, oldest first, each carrying
   a 26-char id, a UTC timestamp, the event type, the document, the anchor,
   the author and the comment index. The ids sort by time — the newest line is
   the largest id.
3. Append an agent reply from outside the TUI and watch the log grow:
   `./bin/margin comment add testdata/sample.md --anchor <id from the log> --text "reply" --author agent` —
   a `comment.posted` line appears for it, index 1 (or next after the thread's
   last).

Questions for the maintainer: does `.margin/events.log` read at a glance, or
is the line too wide? Is the comment-index-the-locator choice right, or should
an event also quote the comment text? And is `comment.updated` worth its own
type, or would a listener rather only hear about posts, deletes and restores?

(What I chose: a single append-only TSV log at `.margin/events.log`, ULID ids
generated in-tree, one event per mutation site emitted after the thread write.
What I rejected: an `oklog/ulid` dependency, a `.margin/events/` directory, a
comment id inside thread files, diffing the thread in `store.save`.)
