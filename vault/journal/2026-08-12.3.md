# 2026-08-12.3 — a threads view, and ]/[ hopping between comments

Kind: felt
Task: Feedback `2026-08-12-threads-view` — "Introduce a new 'threads' view
where the user can discover threads, even if they can't be attached to the
block anymore. Also add next/previous comment actions and bindings."
Commit: (this one)

## What changed

**A threads view in single-document reviews.** The cross-document inbox (the
tree-review half of M3) was the only list-of-threads surface, and it needed a
tree to exist. A single-document review had no way to see what conversations
had accumulated, and a thread whose block had been rewritten away was
invisible — `orphanedThreads()` existed but nothing rendered it. The threads
view is now available everywhere there is a review root (a store): in a tree
review it is the unchanged cross-document list (`loadInbox`), and in a
single-document review it lists the current document's threads — `i` opens,
`j`/`k` move, `enter` lands on the block, `esc` returns, newest activity
first, just like the inbox. `inbox.toggle`'s Applicable moved from `m.tree !=
nil` to `m.store != nil`, and `toggleInbox` builds the list from the
already-loaded `m.threads` when there is no tree (`docThreadItems`) — reattach
has already told it which threads are orphaned, so no disk re-read is needed.

**Orphaned threads are discoverable, not lost.** A thread whose block no
longer exists in the document renders in the single-document threads view with
a `[block gone]` marker, and `enter` on it reports "the thread's block is
gone" rather than pretending to open a vanished anchor. This is the "even if
they can't be attached to the block anymore" half of the feedback: the
conversation itself is still readable in the thread file, and now it is
findable. A single-document review's rows drop the document name (every row is
the same document — the prefix would be a wall of identical noise); a tree
review's rows keep it, since threads span the tree.

**`]` / `[` hop between comments.** `]` moves focus to the next thread in the
document, `[` to the previous. A thread is one focus stop however long it
renders (journal 2026-08-09.18), so the hop walks `m.entries`' thread rows,
skipping the one focus sits on, and lands centred with the landing recorded in
the jumplist (`ctrl+o` walks back). At the ends it reports rather than wraps.
Chosen: the bracket pair over `[c`/`]c` (vim's diff-hunk memory) and over
`n`/`N` (already search) — `]`/`[` were unbound, sit on the home row, and read
as "move forward/backward through the conversation".

**Footer** in the threads view reads `threads — N thread(s)` (was "inbox").

## Demo

```bash
make build && ./bin/margin testdata/sample.md
```

1. Comment on a couple of paragraphs (`c`, type, `ctrl+s`).
2. Press `i` — the threads view opens, newest thread first, each row naming
   its author and first line. `j`/`k` move, `enter` on a row lands on its
   block (centred), `esc` returns. This is new: `i` used to be unbound in a
   single-document review.
3. Close the view, delete the block a thread sits on from the file (edit it
   out, `ctrl+r` to reload), press `i` again — that thread now reads
   `[block gone]`; `enter` reports the block is gone instead of jumping. The
   conversation is still listed and its text still readable.
4. Press `]` — focus jumps to the next thread in the document; `]` again hops
   on, past the last it reports `no more comments below`; `[` walks back, and
   `ctrl+o` after a hop returns to where it started.

Questions for maintainer: is a list of the current document's threads the
right "threads view" for single-document reviews (the same surface the inbox
already is for trees)? Is `[block gone]` the right marker for a thread whose
block vanished — should it be more visible, or should it show the orphan's
full text? Are `]`/`[` the right hop keys, and is not-wrapping at the ends the
wanted reading? Is dropping the doc name from single-document rows right, and
is "threads — N thread(s)" the wanted footer wording?
