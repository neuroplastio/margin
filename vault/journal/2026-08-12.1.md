# 2026-08-12.1 — mark individual lines when diving inside a block

Kind: felt
Task: Feedback `2026-08-11-dive-line-mark-comment` — "Need the ability to mark
and comment individual lines when diving inside a block".
Commit: (this one)

## What changed

Commenting a line already worked — `c` inside a dive prepends `L<n>: ` to the
draft (journal 2026-08-09.28). The missing half was **marking**: `space`/`r`/`f`
inside a dive kept marking the whole block. Now a dive makes the line the unit
of review, the same way a heading makes its section the unit:

- **Line marks.** `space`/`r`/`f` on a dived source line mark that line only,
  stored in a new session-only `lineMarks` map keyed `anchor:line` (`:` never
  appears in an anchor, which are hex). Marked lines each render their own
  gutter rule; a partly-worked table shows exactly the rows that are done.
- **The block reads as its lines' roll-up.** A diveable block's review state
  IS the roll-up of its line marks — the block mark is never consulted for it,
  exactly the way a heading never carries a mark of its own. So marking the
  whole table from block level sets every line, re-pressing cycles/clears
  everything, a partial table reads `·`-partial in its heading's roll-up, and
  a flagged line flags the block.
- **Progress and export follow.** `reviewProgress`, the tree pane's `n/m`
  slots and the tree-wide footer read diveable blocks through the roll-up
  (partial counts neither way; flagged dominates), and `Y`/`--stdout` export
  through the same effective marks so a flagged line surfaces in the review.
- **Tree switches carry line marks** per-document (`lineMarkCache`), matching
  the marks-carrying behaviour of the tree-progress work; the outgoing doc's
  effective marks are folded into the cache *before* the doc is swapped
  (a save-after-swap bug the tests caught: `effectiveMarks` reads `m.doc`).
- **Raw mode** rides the same line marks, rule on the marked source line.

**What was rejected:** a separate block mark alongside line marks — surface +
`space` on a partly-marked table would then cycle the *block* while the lines
kept their marks, an invisible residue the reviewer cannot clear. Making the
lines authoritative (like headings' paragraphs) means block-level marking and
line-level marking can never disagree, at the cost that marking a whole table
writes one mark per line.

Comments on a line are unchanged (the `L<n>` draft prefix + block-anchored
thread): the anchoring semantics are settled, and this feedback's marking half
is what was missing.

`make test-race` was not required.

  the unit; the block itself stays markless.

- `TestLineMarksRollUpPartially`, `TestFlaggedLineRollsUpFlagged`,
  `TestLineMarkCountsInSectionRollUp` — partial/flagged roll-up in progress

  marked line's row only, in both views.
- `TestLineMarkSurvivesSurfaceAndClears` — surface + `space` resolves/clears
  the whole block with no residue.

## Demo

```bash
make build && ./bin/margin testdata/sample.md
```

1. `j` to the table under "### What changes", `l` to dive into its rows.
2. `j` to the `After` column row, press `space` — the status reads
   `reviewed · line N` and a green rule appears on that row only.
3. `j` to another row, press `f` — an orange rule on that row. Surface with
   `h`: the table now shows one green row and one orange row, and the section
   heading above it shows the dimmed `·` (partially reviewed).
4. `l` again, stand on the flagged row, press `c` — the draft is prefixed
   `L<n>: ` as before. Post it and `Y`: the export lists the block flagged.
5. Surface, press `space` on the table — the whole table resolves to reviewed
   (all rows green), and a second `space` flags everything, a third clears it
   all (no invisible residue).

Questions for maintainer: is marking per *source line* right when the dive's
rows are source lines (tables/raw) — and does a partially-marked table read
clearly at a glance, or should the whole block dim/tint until fully reviewed?
Does the "marking a whole table writes a mark per line" model feel right vs a
separate block-level state? Is the tree pane's treatment (a partial table reads
as not-yet-reviewed) acceptable, or should partial show some middle state?
