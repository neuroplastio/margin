# 2026-08-08.6 — RENDER-02: fenced code blocks with chroma highlighting

Kind: felt
Task: RENDER-02
Commit: (this one)

## What changed

No open questions blocked the board and `vault/feedback/` was empty, so this
is the next unblocked M1 backlog item in board order (RENDER-02 was listed
ahead of RENDER-03/RENDER-07).

A fenced code block previously fell into the general `blockRaw` bucket —
shown verbatim, source fence and all, with no colour. This leg gives it its
own kind and real syntax highlighting:

- **`blockCode`** (`internal/review/document.go`) is a new block kind,
  carrying a `lang` field alongside the usual `lines`. Unlike `blockQuote`
  and `blockListItem` before it, this one is a genuine visual upgrade over
  its old bucket, not just a layout fix.
- **`codeLinesFor`** (parse.go) reads a fenced block's content straight from
  goldmark's own `t.Lines()`, which excludes the ``` delimiters — different
  from `extent()`'s range, which `widenFence` deliberately widens to
  *include* the fences, because `stampID` needs to anchor after them. So
  `block.text` (used for stamping/anchoring) still carries the full raw
  markdown, fences included, while `block.lines` (used for rendering and
  export) is fence-stripped content only. Two different callers wanting two
  different slices of the same node is exactly why `extent()` and
  `codeLinesFor` stayed separate rather than trying to make one range serve
  both.
- **`highlightCode`** (review.go) is the new render path: it joins the
  block's lines back into one string and runs it through
  `github.com/alecthomas/chroma/v2/quick.Highlight` with the `monokai` style
  at `terminal256` colour depth, returning one already-ANSI-styled line per
  input line. That output plugs into the exact same `preStyled` mechanism
  RENDER-06 built for inline markup — `render()`'s shared block loop already
  knew how to skip re-styling a line that carries its own colour, so nothing
  there needed to change.
- **Export** (`export.go`) gained a dedicated `quoteBlock` case for
  `blockCode`: instead of flattening the code into a generic blockquote (the
  old `blockRaw` path, `> line` per line), it reconstructs a real fenced code
  block — ```` ```<lang> ```` … ` ``` ` — inside the quote, so an agent
  reading the export sees it as code, not as prose that happens to look like
  code.

**Chroma is a new dependency.** `go get github.com/alecthomas/chroma/v2` plus
`go mod tidy` (which also promoted `fsnotify` from indirect to direct — it
was already imported directly by `watch.go`, `go mod tidy` just hadn't been
run since). No vendoring; it's pulled from the module proxy like everything
else.

**An unrecognised or absent language degrades quietly.** `quick.Highlight`'s
own fallback chain — try the named lexer, then guess from content, then
plain text — means a language chroma does not know (or a fence with none)
never errors; `highlightCode` also has a belt-and-braces fallback to the raw
lines if `quick.Highlight` itself errors, though nothing in testing found a
way to trigger that path (the underlying `Highlight` only errors if the
lexer's `Tokenise` does, and the fallback lexer's does not).

**Highlighting is fixed regardless of review state**, the same call RENDER-06
made for inline code spans and links: chroma's colours are the code's own
markup, not prose that should dim once the block is marked reviewed. A
reviewed code block still shows its full colour — only the gutter's dimmed
glyph and bar communicate the mark, same as they always have.

Rejected: dimming or desaturating the highlighted colours on review — that
would mean either re-parsing chroma's ANSI output to rewrite it (fragile) or
running `quick.Highlight` twice with two different styles (double the work
for a distinction the gutter already carries). Not worth it for a
first pass; worth reconsidering if a maintainer's screen says the fixed
colour reads as "never marked."

## Verification

`make check` (build, `go test ./...`, `go vet ./...`) is green. `make
test-race` is also green — this leg touches the shared render loop, and
while it is not composer/emulator code, the loop is what F5 already flags as
worth keeping honest.

Existing tests that assumed a fenced code block was `blockRaw` were updated
to `blockCode`: `TestParseFindsTopLevelBlocks`,
`TestParseCollapsesParagraphsButNotRawBlocks`,
`TestStampIDInvisibleToOtherRenderers` (both occurrences),
`TestExportQuotesRawBlocks` (renamed target only, kept its name — it is
still about a "raw" family block from the reader's point of view, just no
longer literally kind `blockRaw`). Tables, the other `blockRaw` member, are
untouched — `TestTableExtensionKeepsRowsIntact` still asserts against the
old bucket, correctly.

New tests: `TestParseFencedCodeBlockCarriesLanguageAndStripsFence` (a fence's
`lang` and fence-stripped `lines` are both correct, and `text` still keeps
the fence for anchoring), `TestParseFencedCodeBlockWithNoLanguage` (an
unlabelled fence gets `lang == ""`, not a placeholder),
`TestHighlightCodeAppliesColourForARecognisedLanguage` (a known language
produces at least one ANSI-styled line, and every line's de-styled text
matches the source byte-for-byte), `TestHighlightCodeDegradesForAnUnknownLanguage`
(a made-up language name still returns every line, unstyled or not, with no
error and no dropped text).

I cannot see a screen, so I cannot confirm the `monokai` style actually reads
well against margin's own palette (dimStyle 244, textStyle 252, headings up
to 212, RENDER-06's codeStyle 216 for *inline* code), or that
`terminal256` depth looks right in Ghostty versus `terminal16m` truecolor.
See the demo recipe.

No question raised.

```

Navigate (`j`/`k`) to the "Implementation" section — it has a `go` fenced
code block (a `SessionStore` interface and a constructor). Answer:

- Does the code read as syntax-highlighted — keywords, types and strings in
  distinguishable colours — or does it look flat/monochrome from this
  terminal?
- Does the `monokai` palette clash with anything else margin already uses —
  the gutter, the heading colours, RENDER-06's inline `codeStyle` (216,
  warm peach) or `linkStyle` (111, cyan)? They are drawn from unrelated
  palettes (chroma's own theme vs. margin's hand-picked 256-colour set) and
  have never been checked side by side.
- Mark the code block reviewed (`space` while it's focused). Does staying at
  full colour read as intentional ("this is code, code doesn't dim") or as a
  bug ("why didn't marking it do anything")?
- Copy the review (`Y`) after commenting on the code block, and check the
  clipboard: does the exported fenced block read cleanly as markdown an
  agent could act on?
- What I chose: chroma's `monokai` style, `terminal256` depth, colour fixed
  regardless of review state, export reconstructs a real fence rather than
  a flattened quote. What I rejected: a style closer to margin's own
  existing palette (monokai is chroma's most common default, not a
  colour-matched pick — worth revisiting if it clashes),
  `terminal16m` truecolor (256 was chosen to match the depth margin's other
  colours already assume), dimming highlighted code on review (not worth
  the double-render or ANSI-rewrite cost for a distinction the gutter
  already makes).
