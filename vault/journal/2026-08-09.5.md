# 2026-08-09.5 — SCROLL-02 (page movement)

`[felt]`

## What

Added paging commands (`move.pageDown`, `move.pageUp`, `move.halfPageDown`, `move.halfPageUp`) to navigate documents faster. The open decision from the board was whether to carry focus along with the viewport (like `vim`'s `ctrl+d`) or to keep focus put and scroll underneath it.

I chose to **carry focus along with the viewport**. `pageScroll` (`internal/review/review.go`) shifts `m.scroll` by the viewport distance (or half of it), determines the new focus block at the corresponding scrolled position by running a `hitTest`, and updates `m.at` to match. 

The command bindings added to `keymap` are:
- `ctrl+d` / `ctrl+u` for half-page down/up
- `ctrl+f` / `pgdn` for full page down
- `ctrl+b` / `pgup` for full page up
- `home` / `end` were wired to the existing `move.first` and `move.last`

Additionally, I factored out `paletteHeight` estimation and removed `renderPalette` invocation from `pageScroll`'s path to break an initialization cycle that `go build` flagged between `commands` and `renderPalette`.

## Demo

1. Run `make run` or `margin some-large-doc.md`.
2. Press `ctrl+d` and verify the viewport shifts down by roughly half a screen and focus follows.
3. Press `ctrl+u` and verify you arrive back where you started.
4. Try `pgdn` and `pgup` (or `ctrl+f` / `ctrl+b`).
5. Try `home` and `end`.
6. **Question to answer:** does focus movement matching the viewport feel right, or should it behave like a pager where focus snaps back if you don't manually advance it?
