# 2026-10-02.1 — HOTTY: prose blocks as HTML surfaces on a HOTTY host

Kind: felt (tests prove the surfaces, their heights, events and fallbacks; how
a page of proportional prose beside a cell gutter reads, and how scrolling
feels, needs the maintainer's eyes).
Task: maintainer direction — "Let's implement hotty support in margin. Make
hotty-go repo public and use it as a dependency".
Commit: (this one)

## What changed

On a terminal that is a HOTTY host (hottyterm, the xterm.js addon), margin now
sets its prose in HTML: every heading, paragraph, list item and quote is a
surface of its own, laid out by the host in a sans reading font at an 80ch
measure, with real heading sizes, inline markup, links and images. Everything
that is the review stays in cells around them — the gutter's focus and marks,
threads, the nvim composer, the footer, the tree pane — and so do code
blocks, tables, mermaid and frontmatter, which the cell renderer already does
well. On any other terminal nothing changes: margin detects no host and draws
exactly what it drew before. `--no-hotty` forces cells on a host. D17 records
the architecture; the short version:

- Each block's document is its own source lines rendered by goldmark, with one
  stylesheet sent once as a resource (`hotdoc.go`). Reviewed and selected are
  classes, search hits are `<mark>`s, and none of them moves a line.
- A block's height is the host's answer: it is measured on a throwaway
  `r=auto` surface, nearest the screen first, and shows in cells until the
  reply comes. A host that never answers leaves the document in cells.
- The frame is rendered in `Update` on a host (where Bubble Tea lets a program
  write placements) and `View` returns it, so a placement batch always
  precedes the frame it belongs to (`hotty.go`).
- A press on a surface focuses its block; a click on a `#heading` or
  `other.md` link follows it through `followHref` (split out of
  `followLink`); a web link opens in the terminal's browser. A relative image
  is sent in-band; a web image becomes a link.
- Raw view (`\`) and the threads view (`i`) place no surfaces.

**hotty-go is public.** `neuroplastio/hotty-go` went public for this, and its
CI moved to GitHub's hosted runners (a public repo never runs on yaga).
margin requires `hotty-go`, `hotty-go/hottytea` and `hotty-go/hottytest` at
the pinned `44e207d`. That raised `go.mod`'s `go` line to 1.26.8, which is
hotty-go's; the release workflow reads it from `go.mod`.

## Notes

- **The kitty polyfill is not a target.** Under `hotty run` in kitty the first
  screen is right, but a long scroll loses blocks and leaves a stray rule. Two
  polyfill defects cause it: a frame redrawn after a placement overwrites the
  Unicode placeholder cells, and the polyfill's own DECSC/DECRC clobbers the
  cursor that `hotty.PlaceAt` saved around a placement, so the renderer's
  next write lands in the wrong place. Both belong in hotty-blitz; margin does
  not work around them.
- **Selection on surface rows.** The cell renderer's selection background
  (`selLine`) is skipped on the blank rows under a surface: on the polyfill it
  showed through as a grey band, and on a native host the surface's own
  `.sel` background is the selection.
- **Dead ends.** The block's byte range excludes a heading's `#`, so rendering
  it gave a `<p>`; documents are built from whole source lines instead (with a
  per-document cache, since splitting the source per block was quadratic).
  `.sel { max-width: none }` changed where lines broke, which is exactly what
  review state may not do. Inline `code` at the prose line height made a line
  two rows tall; `code` is `line-height: 1`.
- Pre-existing `gofmt` differences in `review.go`, `tree.go` and others are
  left alone; the gate does not check formatting.

## Verification

`make check` and `make test-race` green (nvim 0.12.4 on PATH via
`mise x neovim@0.12.4 --`). New tests in `internal/review/hotty_test.go`
drive a review against hotty-go's in-process test host (`hottytest`):

- `TestHottyProseIsSurfaces` — headings, paragraphs, list items, quotes and
  an image are surfaces beside the gutter, at the column's width and the
  rows the host measured with `r=auto`; the stylesheet and the PNG are sent
  as resources; links keep their targets; the code block stays in cells; and
  nothing is left placed after quitting.
- `TestHottyPressFocuses`, `TestHottyLinkClickFollows` — a press focuses the
  block; a click on a `#heading` link jumps to it.
- `TestHottyReviewStateAndSearch` — marking a block reviewed resends its
  document with `ok`; a search marks hits inside surfaces and finds them.
- `TestHottyTextTerminal` — with no host, nothing is placed and the frame is
  the cell renderer's.
- `TestMarkMatches`, `TestExternal`, `TestHotName`, `TestHotListItem`,
  `TestHotWebImage` — the HTML side's pieces.

I looked at it myself in hottyterm on a headless display: screenshots of a
test document with headings, a paragraph with bold, a link and inline code,
nested and task lists, a quote, a Go block, a table and a PNG. All of these
were right: proportional prose with sized headings, cells for code and the
table, the image inline, the reviewed dimming, gutter marks and roll-ups,
search `<mark>`s, the visual selection, the composer opened between surfaces,
a posted thread with the surfaces reflowed below it, and raw view and the
threads view with no surfaces. I cannot judge how scrolling *feels*, nor
whether the cells-then-HTML swap on open is a visible flash.

## Demo

Run it in hottyterm (or any HOTTY host):

```bash
make build
./bin/margin testdata/sample.md
# j/k through the document, then G and gg; / for a word in a paragraph;
# space to mark a paragraph reviewed; V and j to select; c to comment;
# \ for raw view and back; click a paragraph; click the runbook link.
./bin/margin --no-hotty testdata/sample.md   # the same document in cells
```

For an image, put a `![diagram](diagram.png)` line in a scratch document next
to any PNG and open that document.

Chosen: sans prose (IBM Plex Sans, then Inter, then system-ui) at 80ch, h1
1.6rem over two rows, h2 1.2rem, h3 and below at body size in the heading
colours, margin's own cell palette throughout. Rejected: prose in the
terminal's monospace font, which would throw away the reason for doing this.

1. Does a page that is half proportional prose and half monospace cells (code,
   tables, threads) read as one page, or as two tools taped together?
2. Is 80ch the right measure, given that the column is wider on a big window?
3. Do the heading sizes give the hierarchy at a glance, and is an h1 over two
   rows too tall?
4. A list's markers are `•` (or the item's number) in a column of their own,
   and tasks are `☐`/`☑`, with a done task's text dimmed. Do they read?
5. Images are capped at 20 rows. Too small, too large?
6. Is the selection (a grey block background, no other change) visible enough
   beside the gutter's focus mark?
7. When a document opens, do you see the blocks flash from cells to HTML? Does
   a long `j`/`k` or wheel scroll feel as quick as it does in cells?
8. A click on a paragraph focuses it, and a click on a web link opens the
   browser with no word from margin. Is that right, or should margin say what
   it opened?
