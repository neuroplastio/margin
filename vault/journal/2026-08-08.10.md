# 2026-08-08.10 — fix: inline markup inside list items and quotes

Kind: mechanical
Task: (from feedback, `vault/feedback/markdown-rendering.md`)
Commit: (this one)

## What changed

`vault/feedback/` held one item beyond its README: `**bold**` inside a list
item or a block quote was showing up on screen as literal asterisks instead
of rendering bold, per a screenshot the maintainer attached. Feedback
preempts the board, so this is the leg.

RENDER-06 gave paragraphs inline markup (`**bold**`, `` `code` ``,
`[text](url)`) via `parseInline`/`glueWords`/`wrapInline`/`fragStyle`, but its
own journal entry (2026-08-08.5) said plainly: "List items, quotes and
headings are deliberately not covered yet." `wrapList` and `wrapQuote` were
still wrapping with the plain, markup-blind `wrap()` and the caller
(`render()`) flattened their output to one uniform `body.Render(l)` — so the
raw `**`/`` ` ``/`[...]()` markers survived untouched, exactly what the
screenshot shows.

This is not a new visual decision — RENDER-06 already settled what bold,
code and a link look like. It is extending that settled treatment to two
more block kinds that were skipped when it landed, which is why this is
`[mech]` rather than `[felt]`: correctness here is "raw markup characters
never reach the screen and no words go missing," provable by a test, not a
judgement call about how bold should look.

**`wrapList`** now takes a `body lipgloss.Style` and wraps each item's text
through `wrapInline` instead of `wrap`, at the same width budget (measure
minus the prefix's own width) it always used. The prefix and hanging indent
stay plain, unstyled strings prepended after wrapping — they are layout, not
part of the source text, so they never go through `parseInline`.

**`wrapQuote`** similarly takes `body` and wraps each folded paragraph
through `wrapInline` instead of `wrap`. Paragraph-break handling (a blank
line inside the quote becomes an empty output line) is untouched, since that
logic never touched markup to begin with.

Both call sites in `render()` (`internal/review/review.go`) now set
`preStyled = true` for `blockList`/`blockListItem` and `blockQuote`, the same
flag `blockPara` already sets, so the shared render loop skips re-wrapping
the output in one uniform `body.Render` and lets the per-fragment ANSI
styling `wrapInline` already applied stand. The list case's existing
"unreviewed list items render in `rawStyle` (109), reviewed ones in
`textStyle`/`reviewedTxt`" behaviour is preserved — `body` is resolved to
`rawStyle` *before* the `wrapList` call now, instead of after, since
`wrapList` needs the final `body` to style bold runs against.

## Verification

`make check` (build, `go test ./...`, `go vet ./...`) is green. `gofmt -l`
clean. Not a composer or emulator change, so `make test-race` was not run.

Updated `TestWrapListWrapsInsteadOfTruncating` and
`TestWrapQuoteWrapsAndKeepsParagraphBreaks` to pass a `body` style and strip
ANSI (`ansiRe`, already used by `TestWrapInlineStripsMarkupAndWraps`) before
measuring line width, since both functions now return pre-styled output.
Added `TestWrapListRendersInlineMarkup` and `TestWrapQuoteRendersInlineMarkup`,
reproducing the feedback's own examples (`**Week 1**`, `**Open question.**`)
as regression guards: no raw `**` survives, the text itself survives, and at
least one ANSI escape is present.

I cannot see a screen, so I cannot confirm the bold now actually reads as
bold inside a real terminal rendering a list or a quote — only that the
markup is stripped and a style escape is present, the same limit RENDER-06's
own journal entry noted for paragraphs. This is a direct fix for a reported
defect rather than a new felt treatment, so no fresh demo recipe or `Needs a
look:` line — the maintainer already told us what was wrong from a
screenshot; the fix is exactly RENDER-06's paragraph treatment applied
verbatim to two more block kinds, and RENDER-06 is not on the outstanding
`Needs a look:` list.

No question raised. `vault/feedback/markdown-rendering.md` is deleted as part
of this commit.
