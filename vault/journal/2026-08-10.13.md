## What changed

The maintainer's agent loop reported a real gap: the skill document taught the
interactive loop but not how a live participant knows the human has finished —
a `comments wait` poll that gets "nothing yet" forever is indistinguishable from
a review nobody is looking at. The pattern the loop actually runs was
undocumented. Now it is the skill's own section.

- **New `## When the review is done` section** (`internal/review/skill.md`,
  between the loop and the contracts). The recipe, taught as the feedback
  frames it: run the launch and the poll as two parallel jobs, and let the
  launch's completion be the done-signal. Launch is `--stdout`, chained to a
  sentinel, as one backgrounded call —
  `margin --stdout FILE.md && echo "__MARGIN_DONE__"` — so a normal quit
  prints the final review to stdout (the same content `Y` and `margin export`
  produce, the agent's own replies included), the sentinel echoes, and the call
  completes: that is "done". While it runs, poll in parallel with the loop's
  own `comments wait`, replying via `comment add`. When the launch job
  completes, stop polling.
- **`&&` is deliberate and explained**: the sentinel fires only on a normal
  quit (Run returns nil → exit 0), so a call that completes with no sentinel
  and a non-zero exit is margin erroring, not the review finishing — a quiet
  `;` would print the sentinel on a crash too and blur the two apart.
- **Step 5 of the loop now points at the section** ("The loop has no end of its
  own — how to know when the human has finished is the next section."), so the
  loop reads as a loop that terminates.
- **Help texts kept in step**: the root command's Long text, `margin skill`'s
  Long text and the README's skill paragraph each gain the done-signal clause.

**What I chose and rejected:** a recipe section over a bare "the loop has no
end" warning (the feedback's ask is a recipe, and a warning alone still leaves
the loop without a termination condition); `&&` over `;` (see above — the
distinction is the whole point, and it is true: `Run` returns nil on a normal
quit); a named sentinel string `__MARGIN_DONE__` over a bare `echo done` (a
grep-able token is the point of a sentinel); keeping the terminal mechanics out
(how the launch job gets its controlling terminal — tmux, a window, the human's
own shell — is the launcher's business, and pinning one would go stale).
Rejected: raising a question — this is content, rename-cheap, and the feedback
names the pattern it wants. And deliberately **not** adding a done-event to the
log: the pattern already closes the loop with no protocol change, and inventing
a `review.done` event would be a format decision the feedback does not ask for.
