# 2026-08-10.6 — raw mode horizontal scroll (H/L)

Kind: felt

`vault/feedback/2026-08-10-raw-mode-horizontal-scroll.md`; the file is deleted
Commit: (this one)

## What changed

The feedback, verbatim: "In raw mode, horizontal scroll should work (like it
does in the regular review view via `H`/`L`)."

`move.hscrollLeft`/`move.hscrollRight` (`H`/`L`) were inert in raw mode —
Applicable returned false and Run no-oped. They now pan the whole raw source
view sideways:

- **A single viewport-wide offset, `m.rawH`.** Raw mode is a flat "the file"
  list, not per-block rows, so a per-anchor offset like `scrollBlock`'s would
  leave half the screen frozen while the other half slides — meaningless when
  every line is already visible. One offset applies to every source line.
  Bounded between 0 and the widest source line minus the content width, so the
  tail of a long line is exactly reachable and no further (same clamp shape as
  `scrollBlock`, 4 columns per press).
- **`renderRaw` clips through the same `scrollCodeLine` the rendered view uses
  on code blocks and tables.** Once any line overflows the measure, every line
  clips at it (not just the wide ones), so a line's length does not jump when
  the offset moves off 0 — the code-block precedent. Short lines scroll off to
  the left and read their tail, exactly as a code block does. The gutter stays
  fixed on the left, focus bar and mark rule included, and search/selection
  still apply on the clipped lines.
- **`toggleRaw` resets `m.rawH` to 0 on entering raw mode.** A stale global
  offset would blank a document whose lines are all shorter than it, and "show
  me the file" should start at column 0.

**What I chose and rejected:** the whole-view scroll (above) over per-block
offsets; the rendered view's clip-at-measure-even-at-0 behaviour over leaving
long lines to the terminal's own truncation (the same 3-column slack both
views share); reset-on-toggle over persisting the offset across `\` flips, on
the "the file opens at column 0" reading. Status messages follow `scrollBlock`'s
wording ("source scrolled to col N", "source scrolled to left edge", "raw
source fits within measure").

## Verification

`make check` green (build, test, vet). Composer and emulator untouched — no
`test-race` run.

Tests in `internal/review/raw_test.go`:

- `TestRawHScrollPansTheSourceView` — a 120-rune line against a 94-rune
  content width clips at the measure at offset 0, `L` moves `m.rawH` to 4 and
  the render shows the 94-rune slice starting at rune 4, `H` returns to 0 with
  the left-edge status, and a short line reads its tail ("tle") instead of
  wrapping.
- `TestRawHScrollBoundsAndReset` — a fitting document reports "raw source fits
  within measure" without scrolling; a 100-rune line clamps at max scroll 6
  however many `L`s; toggling out of raw and back resets `rawH` to 0.
- `TestRawDiveIsInert` updated: it now covers only `l`/`h` (the `L` press moved
  out, since `L` genuinely scrolls now); the comment names the exception.

Existing raw tests pass unchanged — `TestRawRendersSourceVerbatim` and
`TestRawCodeBlockKeepsSyntaxColors` use sources whose lines fit, so the new
clip path is a no-op for them.

No question raised.

## Demo

```bash
make build && ./bin/margin testdata/sample.md
```

sample.md's frontmatter has a 207-column `description:` field (line 7) and the
code block has lines that overflow an 80-column terminal — the two places the
old raw view truncated with no way to see the rest.

1. Press `\` into raw mode, `g` to the frontmatter. The `description:` value
   is cut off at the measure. Press `L` a few times — the whole raw view pans
   right 4 columns a press; the field's tail slides into view; `H` pans back.
   Judge: does panning the *whole* view (every line moves, short ones included)
   read as one gesture, or does the all-or-nothing motion want per-block
   scrolling like the rendered view?
2. Still in raw, `j` down to the go code block (fence at line 62). Its long
   lines scroll with the same `L`/`H`; the chroma highlighting from
   journal 2026-08-10.5 survives the clipping (ANSI is carried, not stripped).
   Judge: is 4 columns per press the right step here too, and does the gutter
   staying pinned to the left (while the text slides) help you keep your place,
   or should the focus bar scroll away with the content?
3. `\` back to rendered, then `\` into raw again — the view reopens at column
   0, not wherever you left it. Judge: is reset-on-toggle the right call, or
   would you rather the raw view remember its scroll across the flip?
4. On a document with no long lines, `L` in raw mode reports "raw source fits
   within measure" rather than doing nothing silently. Judge: is the status
   message the right way to explain a no-op?

Questions for the maintainer: is the whole-view scroll the right model for raw
mode, or should H/L track the focused block like the rendered view? And should
the raw scroll offset persist across the `\` toggle?

(What I chose: single viewport-wide offset, reset to 0 on entering raw, clip
at the same measure the rendered view uses. What I rejected: per-block
offsets, the terminal's own truncation, persisting the offset across toggles.)
