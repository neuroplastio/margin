# 2026-08-08.4 — Lists split into per-item blocks

Kind: felt
Task: feedback/2026-08-08-4-line-level-focus.md
Commit: (this one)

## What changed

`vault/feedback/` held one item — the only one, so it preempted the board by
its own rule.

The feedback's actual ask is bigger than this leg: a general second level of
focus inside *any* multi-line block (lists, fences, tables), with an anchor
that names a line. It flagged its own open questions as worth settling before
building, and named one directly: "lists specifically may deserve to be real
blocks rather than lines... that is worth settling first: if splitting lists
into item blocks covers most of the want, it is a much smaller change than a
second focus level."

That is what this leg builds. `parseDoc` now emits one `blockListItem`
(document.go) per list item — nesting flattened into a wider prefix, the way
`listItemsFor` already flattened it within a single `blockList` — instead of
one `blockList` block for the whole list. Because focus, comments, marks and
export are all already generic over `[]block` (`m.entries`, `stops()`,
`sectionAnchors()`, `exportReview`), splitting the block was close to the
whole leg: a list of six items is now genuinely six focus stops, six
independent comment targets and six independent marks, with no changes needed
to any of that machinery. `render()` needed one change beyond wiring the new
kind into its existing switches: the blank line after a block is now
suppressed for every list item except the last, so a six-item list still
reads as one list with one gap after it, not six blocks each with their own.

**What this leg deliberately does not attempt**: line-level focus inside a
code fence or table, and what an anchor on a *line* (rather than an item)
means when the block is rewritten — the feedback's harder, more general
question. See D12 for why, and F13 (`findings.md`) for the specific technical
wrinkle that makes it harder than it looks: `stampID` inserts a marker at a
block's byte range, and there is no cheap way to give a list item — let alone
a line — a byte range of its own without risking corrupting the structure
around it. Every item of a list currently shares the whole list's range, and
`stampAll` (parse.go) now explicitly skips `blockListItem` rather than
stamping into that shared range and corrupting the list, which is what it did
before this leg's guard (verified by a new test, see below). An item's anchor
is content-derived only — stable while the item's text is, same as any block
was before ID-01, and no worse than any other block is *today*, since nothing
in the running app calls `stampAll` yet regardless of kind.

Also done as part of the same change: `RENDER-01` ("render lists, one block
type, then stop and ask") is moved to Done on the board. Its actual rendering
— wrapping, hanging indent — shipped earlier under the 2026-08-08
rendering-bugs feedback fix; this leg's split into per-item blocks is the
natural conclusion of "one block type" for a list, so the task is complete
rather than still open.

## Choices made without asking, and why

- **Content-derived anchors only for list items, permanently for now** — not
  parked behind a question, because it changes nothing about what the running
  app can already do (see above), and the alternative (blocking this whole
  leg on designing a sub-list marker format) would have parked a smaller, real
  improvement behind a much harder, more general one. If ID-01/02 get wired
  into a live command before sub-list stamping is designed, this becomes a
  real, visible gap — worth a question at that point, not before.
- **`blockList` (the kind) left defined but unused** rather than removed, so
  `blockQuote`'s ordinal — and every existing content-derived anchor computed
  from it — does not shift. Same convention `blockFrontmatter`/`blockQuote`
  already established for themselves.
- **Every item shares the whole list's byte range** rather than getting a
  real one of its own. Nothing needs it except stamping, which is out of
  scope this leg (see above) — computing a genuinely correct nested range
  (clipping neither a continuation line nor a nested sub-list) felt like
  effort spent on a property nothing reads yet.
- **List item text colour**: same `rawStyle`-when-unreviewed treatment
  `blockList` already used, not `blockQuote`'s plain-prose choice — smallest
  visual diff from what a list already looked like before this leg, since the
  actual change here is what is focusable, not what a list looks like.

## Verification

`make check` (build, `go test ./...`, `go vet ./...`) is green. `make
test-race` is also green — not composer/emulator code, but cheap here and
this does touch the render loop.

Updated: `TestParseFindsTopLevelBlocks` (two `blockListItem`s where one
`blockList` used to be), `TestExportPreservesListStructure` (now checks that
commenting on one item quotes only that item, not its sibling — the actual
improvement this leg makes, in place of the old "the whole list is quoted
correctly" check), `TestStampIDRoundTrip` / `TestStampEveryBlockSequentially`
/ `TestStampAllStampsOnlyUnstampedBlocks` (all skip list items, with a comment
pointing at the new test explaining why). New:
`TestStampAllNeverStampsListItems` pins the guard directly — stamping a
document with a list must never split a marker into the middle of it.

I cannot see a screen, so I cannot confirm a six-item list actually *reads*
as one list with items individually focusable rather than as six disconnected
blocks, or that the missing blank lines between items look right rather than
cramped. See the demo recipe.

No question raised. The feedback's harder half — line-level focus for fences
and tables, and line-level anchoring — is left open, not blocked; nothing
stops someone picking it up as its own leg when there is appetite for the
harder problem D12 flags.

## Demo

```
go run ./cmd/margin testdata/sample.md
```

Navigate (`j`/`k`) down into the list. Answer:

- Does each item genuinely get its own focus stop now — does the gutter
  highlight move item by item rather than jumping over the whole list in one
  step?
- Press `c` on a single item and post a comment. Does the export (`Y`, or
  `--stdout`) quote just that item, not its siblings?
- Mark one item reviewed (`space`) and leave its sibling unmarked. Do the two
  items show independent mark glyphs?
- Does the list still *read* as one list — no stray blank line splitting it
  apart — with the usual gap only after the last item?
- What I chose: split lists into per-item blocks, reusing the existing
  per-block focus/comment/mark machinery unchanged. What I rejected: a
  general second focus level inside any block (the feedback's fuller ask) —
  bigger, and blocked on a real anchoring-semantics decision (D12, F13) this
  leg does not make.
