## What changed

The parse/render pipeline no longer throws a cell's inline markup away.
`tableCellsFor` (parse.go) once stripped each cell down to plain text through
`cellText`, and `renderTable`'s `padCell` then padded the plain string — the
widths were right but the styling was gone (document.go's field comment called
the deferral out explicitly: "this first pass renders plain text and defers
colour inside cells"). That deferral is what this feedback collects.

- **Cells keep their markup.** `cellText` now trims only the surrounding
  whitespace; `**bold**`, `` `code` `` and `[links](url)` stay in the cell
  string. On-disk nothing changes — export and the thread files still use the
  block's verbatim source lines, never the parsed table.
- **Widths measure the visible text.** `tableNaturalWidths` goes through a new
  `cellWidth`, which runs `parseInline` and counts the runes of the stripped
  text — so `` `margin` `` measures 6 whether or not it is wrapped in
  backticks, and a bold/link cell still lines up with its column.
- **Rendering styles in place.** `padCell` now renders each run through the
  same `fragStyle` a paragraph's runs use (`codeStyle` for code, `linkStyle`
  for links, `body.Bold(true)` for bold, `body` otherwise) and pads the styled
  result with plain spaces per `align`. Styling adds ANSI bytes but no runes,
  so the padded cell is exactly as wide as its plain sibling would have been —
  columns stay aligned and the padding stays colourless (the `alignRight`/
  `alignCenter` leading spaces carry no style, as before).
- **No truncation path.** `padCell` used to `truncate` to width before padding;
  that path was dead (a column's width *is* the widest cell in it, so no cell
  ever exceeds it) and is gone. Dropped rather than re-implemented across
  styled runs, which would need run-wise truncation; documented in the comment.
- The header row still renders bold (body.Bold(true) builds into the base
  style), and a header cell's own `` `code` `` still renders as code —
  `fragStyle`'s "markup is markup" rule is unchanged.

**What I chose and rejected:** styling runs in place at render time over
storing parsed runs on `tableBlock` (keeps the parse shape and the tests'
plain-string cells, and parseInline is cheap; the cells are already parsed at
render for widths anyway); keeping the plain-space padding over restyling the
padding (coloured padding would smear alignment; this preserves the old
look); dropping the dead truncation rather than carrying it into styled
runs (a rune-count bug no cell can reach).

## Notes

- The header's `.Bold(true)` now applies per-run through `fragStyle` rather
  than by `style.Render`-ing the whole pre-padded cell — net effect is the
  same bold header, but a header `` `code` `` cell now reads as code inside
  the bold row instead of bold-and-unstyled.
- Search, hit-testing and horizontal scroll all operate on the rendered ANSI
  lines, so they are untouched; `scrollCodeLine` already preserves styles
  through a clip.

## Verification

`make check` green (build, test, vet). Updated
`TestTableCellsStripInlineMarkupAndRespectAlignment` → `TestTableCellsKeepInlineMarkupAndRespectAlignment`
(the parse contract flipped from stripped to kept) and added
`TestRenderTableStylesInlineMarkupInCells`, which asserts the rendered row
carries `codeStyle.Render("in")`, `textStyle.Bold(true).Render("TUI")` and
`linkStyle.Render("really")`, and that every rendered line — styled header,
rule, styled body row, padded plain row — is the same de-styled width so the
columns still line up. The existing alignment/width/scroll table tests pass
unchanged.

## For the maintainer to look at

Whether the RENDER-06 colours inside cells read well next to the column
layout — code (216) and links (underlined 111) sit in the same cells as plain
text, and whether right/centre-aligned columns with a long styled cell still
look right.

## Demo

```bash
make build
cat > /tmp/table.md <<'EOF'
# Inline code in tables

| Command | Notes |
| --- | ---: |
| `margin` | Runs `in` a **TUI**, see the [runbook](https://example.com/x) |
| `ls` | plain, aligned right |
| grep | also `` `code` `` here |
EOF
./bin/margin /tmp/table.md
```

1. **The fix itself:** the `` `margin` `` and `` `in` `` cells read in the code
   colour (216) instead of plain text, `**TUI**` reads bold, and `runbook`
   reads as an underlined link — the same RENDER-06 treatments a paragraph
   gives them. Does code-in-cell read as well here as it does in prose, given
   it now shares a column with plain text?
2. **Alignment holds:** the Notes column is right-aligned (`:---:` is
   left-aligned, `---:` right, so the table also exercises centre-vs-right in
   the header). With styled cells the numbers/padding still line up — check
   the column edges align on the styled row, especially any right-aligned
   styled cell. I chose to pad with plain spaces and measure on stripped text,
   rejecting coloured padding and run-wise truncation.
3. **Header interplay:** `` `Command` `` if you edit the table, or a `` `code` ``
   header cell — a code run inside the bold header row renders as code, not
   bold. Right, or should a header's code runs take the bold too?
