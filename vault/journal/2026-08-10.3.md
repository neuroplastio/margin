## What changed

The maintainer's one-theme feedback: width should match what the terminal can
actually show, in four parts.

1. **`contentWidth()` is the terminal's width, not a fixed 76.** It was
   `max(min(m.w-2*gutterW, maxMeasure=76), minPaneCol)`, so a 200-column
   terminal parked ~120 columns while prose wrapped at 76. It is now
   `max(m.w-2*gutterW, minPaneCol)` — the full terminal width, floor still 40.
   This reaches everything the measure reached: prose, lists, quotes, threads,
   the composer pane (which is sized from the same call), and the clip width
   wide blocks scroll within.
2. **Wide blocks are allowed the full terminal width.** Since part 1 already
   makes the measure the full width, code blocks (and now tables) clip at the
   terminal rather than at 76 "for now", exactly the instruction. I did not
   introduce a separate wide-block width: after part 1 the two coincide, and a
   second number that never differed would be machinery with no job. The demo
   recipe asks whether the prose measure should later be re-capped separately
   from the wide-block cap — the two are now the same call and can be split
   when there is a reason.
3. **Tables scroll instead of narrowing.** `renderTable` renders at natural
   column widths — `tableColumnWidths`, the shave-the-widest-column loop, is
   gone (and its two tests with it) — and the render loop clips a table's rows
   through `scrollCodeLine` exactly as it clips a code block, driven by the
   same `m.codeScroll[anchor]` offset. A wide table reads at its true width and
   `L`/`H` walk it sideways; a narrow one is unchanged. `scrollBlock` gained the
   `blockTable` case so the offset is bounded by the widest natural row.
4. **Horizontal scroll is `H` and `L`.** Two new registry commands,
   `move.hscrollLeft`/`move.hscrollRight`, bound to `H`/`L` (both previously
   unbound), applicable on a focused code block, table, or the frontmatter.
   `move.dive`/`move.surface` lost their code-block scroll branches — `l`/`h`
   (and `enter`/`esc`, the aliases) now mean dive/surface everywhere, so `l`
   on a code block is a quiet no-op with the standard "no thread or lines here
   to dive into" hint, and `enter`/`esc` no longer scroll a code block
   sideways — which is the answer to the open question journal 2026-08-10.2's
   demo recipe asked.

**What I chose and rejected:** parts 1 and 2 share one width (above). For the
step size I kept 4 columns per press — the code-block feedback settled that and
nothing in this feedback argues otherwise. I rejected keeping `tableColumnWidths`
around "for later": it is now dead, and dead narrowing invites a future leg to
re-add it when the feedback explicitly removed it. What the feedback did *not*
say — and I did not do — is make the frontmatter or code blocks clip at
something narrower than the terminal; they ride the same `contentWidth`.

## Verification

pane width flows from `contentWidth`, so the race gate was run).

Tests:
- `TestContentWidthAdaptsToTheTerminal` — 200-col → 194, 100-col → 94, 10-col →
  the 40-col floor.

  press `L`/`H` instead of `l`/`h`.

  offset at 0 and says why; the double meaning is gone.

  commands and really scroll a code block.
- `TestTableScrollsHorizontally` — the widest row overflows the content width,

  at that offset (columns did not narrow), `H` returns to 0.

  "stays-in-measure" test, renamed and re-call: columns still line up, just at

  also presses `L`) pass unchanged otherwise; `line_dive_test.go` comments

No question raised.

## Demo

```bash
make build && ./bin/margin testdata/sample.md
```

sample.md has a 207-column frontmatter field (line 7), long prose, a code block
with long lines, and a table that overflows an 80-column terminal — good for
all four parts. Run it at a few widths: a narrow terminal (~80 cols, `resize`
in a 200-col pane or a fresh window) and a wide one (~200 cols).

1. **Prose width:** open the file at 200 columns. A paragraph wraps at the
   full terminal width now, not at 76 — the extra columns are prose, not empty
   gutter. Judge: does full-width prose read well, or is a re-capped measure
   (with code/tables still capped at the terminal) what you actually want?
2. **Code blocks:** `j` down to the first code block (fence at line 62), then
   `L` — it scrolls right 4 columns per press; `H` back left. Then `l` — it no
   longer scrolls; it dives (no-op here with a hint), and `h` no longer scrolls
   left. Judge: is `H`/`L` on the home row comfortable, and does losing
   `l`/`h`-scroll (now `enter`/`esc`-scroll too — `enter` on a code block no
   longer scrolls right) cost you anything?
3. **Tables:** `j` to the session-migration table (line 46). On an 80-col
   terminal it overflows; with focus on it press `L` — the columns keep their
   natural widths and the table slides, instead of the old behaviour of
   shaving "Session write" down until it was cut off. Judge: does a scrolled
   table read better than a narrowed one? Is 4 columns per press the right step
   here too?
4. **Frontmatter:** `g` to land on the frontmatter, `L`/`H` on the long
   description field (207 cols) — scrolls as before, but now on `H`/`L`; `l`
   no longer scrolls it. Judge: consistent enough?

Questions for the maintainer: is prose at full terminal width the right call,
or should the prose measure be re-capped while code/tables keep the terminal?
Is `H`/`L` (with `l`/`h` restored to pure dive/surface, even on code blocks)
the binding you asked for? And does a scrolled table at natural width read
better than the narrowed one?
