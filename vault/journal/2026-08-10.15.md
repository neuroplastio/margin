# 2026-08-10.15 — the reviewer is told when the document or the conversation changes

Kind: felt
Task: (feedback feature) visually notify the reviewer when the document
changes on disk or a new comment lands. Drains
`vault/feedback/2026-08-10-review-change-notification.md`; the file is deleted.
Commit: (this one)

## What changed

The feedback named two silences. First: the `.md` file itself was **not
watched at all** — nothing re-read the document until the next open, so an
agent rewriting the prose mid-review left the reviewer staring at a stale
copy with no signal. Second: comments posted by an agent *did* reload live
through the thread watcher, but silently.

- **The document file is watched now.** `newThreadWatcher` adds the
  document's containing directory (not the file — see F23 for why that
  misses temp-file-then-rename saves) and attributes events to it by base
  name, so a sibling `.md` edited next door never wakes the reviewer. On a
  change it sends a `docChangedMsg`: the footer gains a persistent
  `● file changed — ctrl+r reload` marker (`flagStyle` orange — it is the
  one signal competing against the dim hint line), and the status line
  spells the affordance out once.
- **`ctrl+r` (`doc.reload`) re-reads the document.** `loadDoc` again,
  threads reattach the way they do on open, marks survive because they are
  keyed by anchor, focus follows the block it was on *by anchor* (a stamped
  block keeps focus even when everything around it was reworded), the raw
  view's `m.src` is refreshed, and the notice clears. It refuses while a
  composer is open — the prose is being written to, not read, and swapping
  it out from under a live edit would be the D7 "lose the user's words"
  failure.
- **A new agent comment is announced.** The thread reload already updated
  the screen; now, when it fires, the event log (D13/D14 — the feedback's
  own suggested oracle) is read strictly after `m.lastEventID`, a cursor
  seeded at open from the log tail. A new `comment.posted` reports
  `new comment from <author> on <anchor>` in the status line. The cursor
  advances on every emit the reviewer makes (`threadStore.emit` now returns
  the id it wrote), so the reviewer's own comments are never announced back
  to them by the watcher they just woke.

**What I chose and rejected:** a footer marker *and* a status line over a
one-shot status alone (the next verb would overwrite it), an explicit reload
over auto-reload (a change landing mid-read must not yank the prose out from
under the reviewer, and an editor's save-storm would be a reload-storm), the
event-log cursor over diffing thread files before/after reload, and
announcing only `comment.posted` — not thread-level events or every thread
write, since the feedback explicitly freed that case from "any thread write".
Rejected: a flash (no flash machinery exists and a persistent marker is
calmer), and reload-while-composing. The two bound choices (the `ctrl+r`
key, the notice's look) are felt and deliberately not recorded in
`interaction.md`.

## For the maintainer to look at

Whether a real reviewer would notice and act on the two notices: the footer
marker's placement and colour when the document changes, and whether the
status line survives contact with the next keypress for a new comment.

## Demo

```bash
make build
# Document change + reload:
./bin/margin testdata/sample.md
# in a second terminal, edit the file (any edit — append a paragraph):
printf '\n## A new section\n\nFresh prose.\n' >> testdata/sample.md
# back in margin: the footer should show ● file changed — ctrl+r reload
# press ctrl+r: the new section appears, the ● clears, status reads "reloaded"
# New comment while watching:
#   in a second terminal: margin comment add testdata/sample.md \
#     --anchor ^a1 --text "agent reply" --author agent
#   back in margin: status line should read "new comment from agent on ^a1"
```

Judge:
1. **The doc-change notice reads at a glance** — is the orange `●` in the
   footer notice-able without hunting, or is a footer line the wrong place
   (too easy to miss while reading)? Is `ctrl+r` the right key, or does a
   plain key (not a chord) read better?
2. **Reload behaviour** — after `ctrl+r`, does focus staying on the block you
   were on (by anchor) feel right, or should the viewport move to where the
   change actually is? Is the status `reloaded — N blocks` enough?
3. **The new-comment notice** — is a status line the right treatment, or does
   the collapsed thread's row need a more urgent cue too?
4. **Auto-reload, revisited?** — the explicit reload is the safe default; is
   it *annoying* in practice, or fine? If the notice is frequently a
   non-event, auto-reload (or a reload-on-the-change-when-idle) becomes worth
   a leg.

(What I chose: explicit `ctrl+r` reload + persistent footer marker for the
document; a status-line notice via the event-log cursor for new comments.
What I rejected: auto-reload, a flash, announcing thread-level events, and a
reload that disturbs an open composer.)
