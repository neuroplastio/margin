## What changed

j/k used to walk a flat stop list — block, thread row, every comment — so
getting past a two-comment thread cost three presses, and a one-comment
thread stopped focus twice. The maintainer called for a dedicated "dive"
navigation type instead. There are now two levels:

- **Block level (default).** j/k walk entries — blocks and thread rows — and
  never stop on a comment. A thread is exactly one stop however long its
  conversation, and a one-comment thread eats focus exactly once, the
  feedback's literal ask. The thread row keeps its stop: it is where the
  conversation renders expanded and where the thread-level verbs (`c`, `e`,
  `R`, `D`) already resolve their target by anchor.
- **Dived.** `l` (or `right`) on a block with a thread, or on its thread
  row, moves focus onto the first visible comment — the only way j/k ever
  reach a comment. Inside, j/k walk the thread's comments, `h` (or `left`)
  surfaces back to the thread row. Registered as `move.dive` /
  `move.surface`, so the palette and any future rebinding get them for free.

Decisions made, and what they replaced:

- **Pop-out at the ends, not a clamp.** j past the last comment lands on the
  next entry; k past the first lands back on the thread row. Rejected:
  clamping inside the thread until `h` is pressed — a j that goes nowhere is
  the feedback's own complaint, re-created inside the dive. This way every
  j/k press moves focus somewhere visible, and linear reading (dive in, read
  the thread, keep pressing j) never stalls on a thread boundary.
- **`l` works from the block and from its thread row.** Both name the same
  anchor, and `c`/`R`/`D` already resolve the thread at focus that way —
  dive follows the same rule rather than inventing a second targeting
  convention. No visible comments (or no thread) is a quiet no-op with a
  status hint, not a wedge.
- **Visual mode needed no special case anymore.** Entering visual already
  lifts focus off comments, so the dive branch can never fire mid-selection;
  the old entry-filtering special case in `moveFocus` became dead code and
  went. `l` in visual mode is inert (and does not cancel the selection).
- **Clicks and page landings still dive implicitly.** A click on a comment
  or a page key landing on one focuses it directly, as before — the dive
  rule constrains j/k, not the mouse or the hit-test. `editFocused`'s stale
  hint ("select a comment with j/k") now says to dive with `l`.
- **Diving into multi-line blocks is deferred.** The feedback named threads
  and multi-line blocks; this leg builds threads. A per-line focus inside a
  long block would be a stop with no verb — nothing acts on a line today —
  and the L12-18 line-reference work in the visual-mode feedback file is
  what will define what a line stop means. The dive mechanism extends to it
  without rework: one more cursor granularity and a payload. A residue
  bullet says so in the feedback file.

## Verification

`make check` green (build, test, vet). Host-side focus-movement change — the
pty writer and render reader are untouched — so `make test-race` is not
required by the gate.

New tests (`dive_test.go`): block-level j/k never land on a comment across a
full document walk; a single-comment thread eats exactly one press (block →
thread row → next block); `l` dives from the block and from the thread row
onto the first visible comment; dived j/k walk the comments in order and pop
out at both ends (down → next entry, up → thread row); `h` surfaces and is
inert at block level; `l` with no thread, or no visible comments, is a no-op
with a status hint; l/h/right/left keymap pinning and keypress routing; `l`
in visual mode neither dives nor cancels the selection.
`TestFocusVisitsEveryComment` pinned the rejected flat-stop model and was
replaced by `TestDivedMovementVisitsEveryComment`.

What I cannot verify: whether `l`/`h` are the keys your hands expect for
this, whether pop-out at the bottom reads as "continuing" or as "falling
out", and whether the thread row still earns its stop — that is the demo
below.

## Demo

```
make build && ./bin/margin testdata/sample.md
```

1. `c` a comment onto a paragraph, submit (`ctrl+s`), then `j` past it —
   focus goes block → thread → next block, one press for the thread whatever
   it holds. Add a second comment (`c` again on the thread row) — still one
   press to pass. Is that the fix you asked for?
2. On a thread, `l` — focus lands on the first comment (pink `▌` on its
   author line). `j` walks the comments; `j` past the last lands on the next
   block; `k` past the first lands back on the thread row; `h` surfaces from
   anywhere inside. Does pop-out read as continuing, or would you rather j
   clamp at the last comment until `h`?
3. On a thread row, `e` still edits (draft/pending edit first, else it now
   hints "l to dive into the thread…"), `R` still resolves, `D` still
   deletes the thread; dived onto a comment, `e` edits it and `D` deletes
   just it.
4. `V` then `j`/`k` — the selection stays blockwise and `l` does nothing
   mid-selection.
5. Click a comment — focus dives straight to it, as before; `h` steps back
   out to the thread row.

Questions: are `l`/`h` the right keys (over `enter`/`esc`, or tab/shift-tab)?
Is pop-out the right end behaviour (over clamping)? Does the thread row
still earn its own stop, or should j/k skip straight block → block and
expand the thread for the focused block instead? Chose `l`/`h` with pop-out
and a kept thread-row stop, over `enter`/`esc` (esc already cancels things;
enter is unclaimed but reads as "open"), over clamping (re-creates the eaten
press inside the dive), and over dropping the thread-row stop (it is where
the thread verbs and the expanded reading view already live).
